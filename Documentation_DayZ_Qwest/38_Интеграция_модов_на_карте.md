## 2. Executive summary

**RECOMMENDATION: вариант B — отдельная вкладка Map и дополнительное синхронизированное окно той же карты; редакторы модулей остаются самостоятельными.** Карта получает пространственные проекции данных, а редактирование направляет владельцу доменной сущности. Отдельное окно является клиентом основного Workshop, а не вторым редактором файлов.

Принять следующие границы:

1. Один изменяемый editor state на модуль; числовая форма и Map меняют его через одинаковые проверяемые операции.
2. Доменный модуль владеет данными, валидацией и сериализацией. Map владеет отображением, геометрическими жестами и пространственной навигацией.
3. Вкладка на экране, модуль редактирования, выделение и видимые reference-слои — разные состояния.
4. JSON/config — сохранённый результат, не транспорт синхронизации окон.
5. Detached Map появляется после доказанного одноконного цикла изменения и сохранения. При потере владельца окно блокирует редактирование.
6. Quest ссылается на Migration ACTIVATION; параметры групп и исполнения не переезжают в Quest.
7. Zones описывает территорию и воздействие; Medicine — заболевание и медицинское состояние. Карта не переопределяет эту границу.
8. Внешние источники сначала read-only. Write-back разрешается отдельно для конкретного формата и конкретной цели.
9. Сохранение требует проверки ревизии и внешних изменений; backup не заменяет защиту от перезаписи.
10. Первый slice — одна существующая группа Migration: минимальная числовая форма, карта, общее состояние, undo и безопасное сохранение существующего контракта.

Хорошая часть исходной идеи — общая геометрическая среда без слияния runtime-модов. Плохая — попытка одновременно построить универсальный adapter API, второй writer, полный Migration Editor и межмодульный конструктор сценариев. Такая последовательность превращает проверку карты в распределённую систему раньше, чем проверен один безопасный drag.

## 3. Подтверждённое состояние Workshop

### 3.1. Оболочка и Quest Editor

**CONFIRMED CURRENT STATE.** `index.html` содержит Quest, Migration, Zones, Map. Quest работает, Migration и Zones представлены заглушками. Переключение вкладок реализовано внутри `map.js / bindWorkshopTabs`: меняются активные кнопки и `hidden` секций, DOM редактора сохраняется. Скрипты подключены как обычные `app.js`, затем `map.js`; framework, общий store и пространственные adapters отсутствуют.[^1]

`app.js` хранит глобальный изменяемый `state.data` с Quest JSON, выбором `{kind, index}`, dirty и дополнительными UI-состояниями. Stack Rules и Item Reference имеют отдельные состояния и отдельные операции сохранения. `handleEditorInput` изменяет объект по `data-path`; `touchState` синхронизирует роли и запускает валидацию/черновик. Более того, `renderAll` тоже вызывает синхронизацию role blocks и `triggerActions`: отрисовка пока не является чистой функцией.[^2]

Следствие: нельзя подключить карту через вторую копию Quest JSON и затем периодически «склеивать» её с формами. Первый Quest adapter должен обращаться к фасаду существующего состояния. Очистку побочных эффектов render следует выполнять постепенно, с регрессионной проверкой ролей, NPC equipment, выдачи предметов и сохранения.

### 3.2. Map MVP

`map.js` — изолированный IIFE с приватным `mapState`. Он лениво загружает один MedicalAttention TXT, разбирает активные `DeclareZone`, рисует SVG, обеспечивает pan, zoom, selection и информационную карточку. Изоляция полезна для сохранения Quest Editor, но общего механизма обмена состоянием ещё нет.[^3]

Текущий MapFeature содержит `id`, порядковый номер, имя, category, source/path/status/lineNumber, `center{x,z}`, circle geometry с массивом radii, zoneType и rawValues. Это полезная начальная проекция, но не контракт редактирования:

- ID вида `medical-attention-N` зависит от порядка строк; после изменения источника это не долговечный ключ.
- Нет owner/module/source-instance identity, revision, edit capabilities, Y-policy и адреса доменной сущности.
- Нет ordered route/point identity; source.status описывает snapshot, не состояние runtime.
- Parser пропускает ошибочные строки и сообщает о них. Частично прочитанный источник допустим для диагностики viewer, но непригоден для полного write-back.

Ожидаемые 78 зон зашиты в коде. `renderFeatures` пересоздаёт слой; `selectFeature` обходит маркеры; `applyViewBox` вызывает `updateSymbolScale`, который проходит по SVG-элементам даже при pan. Пример с одной окружностью имеет четыре узла на feature: group, radius circle, center circle, text; 78 features дают 312 узлов без подложки и оболочки. Это не измеренный предел SVG.[^3]

Подложка ChernarusPlus отображается в квадрате 15360 × 15360 м; преобразование X/Z — `mapX = X`, `mapY = 15360 - Z`. Статическая `verifyCalibration` проверяет арифметику контрольных точек, не реальное совпадение местности с пикселями. Наличие Y в DayZ нельзя заменить этой 2D-проекцией.[^3][^4]

### 3.3. Сохранение, черновики и локальный сервер

| Участок | Подтверждённое поведение | Архитектурное следствие |
| --- | --- | --- |
| `handleDirectSave` | Сериализует state, ожидает POST, затем снимает dirty и очищает draft без сравнения revision | Правка во время save может остаться только в памяти, но считаться сохранённой |
| `handleProfileExport` | Сначала dev-save, затем profile export | Два файла не образуют атомарную операцию; возможен частичный успех |
| `scheduleDraftSave / saveDraftNow` | Debounce 180 мс, localStorage и асинхронная запись одного `editor-draft.json` | Нет изоляции нескольких источников/окон и порядка in-flight запросов |
| `restoreDraft` | В HTTP-режиме выбирается файловый draft с положительным timestamp; при его отсутствии локальная копия не служит полноценным fallback | Timestamp не доказывает соответствие текущему файлу; восстановленный draft загружается с dirty=false |
| `saveDraftToProjectFile / clearDraftStorage` | Нет проверки HTTP `response.ok`; старый POST может пересечься с DELETE | Успешный fetch не равен сохранённому черновику; возможно «воскрешение» старой копии |
| `normalizeData / normalizeQuest / normalizeTrigger` | Создают объекты из перечисленных полей | Неизвестные поля не сохраняются универсально; этот normalizer нельзя переносить на чужие форматы |

Это выводы из конкретных веток `app.js`, а не утверждение, что все пользователи уже потеряли данные.[^2]

`server.ps1` обслуживает loopback HTTP на 4173. `/api/current-json` возвращает настроенный файл без версии источника; `/api/save` проверяет синтаксис JSON и пишет через `WriteAllText`, без доменной проверки, expected hash и атомарной замены. Пути из `/api/config` разрешаются как произвольные абсолютные/относительные пути; существующий endpoint не является шаблоном безопасного write-back для внешних модов. MedicalAttention, напротив, имеет фиксированный read-only endpoint.[^5]

`start-editor.ps1` создаёт backup при запуске и перезапускает локальный сервер; это не backup каждой операции Save. `editor-config.local.json` перекрывает обычный config. В текущем `editor-config.json` стоят абсолютные P:-пути, несмотря на описание переносимости в PROJECT_CONTEXT. В локальной настройке также обнаружена отдельная сетевая profile-цель. При аудите она не читалась и не изменялась.[^5][^6]

## 4. Требования и критерии архитектуры

Карта должна позволять видеть контекст мира, выбирать сущность, переходить в её редактор, задавать координаты и редактировать поддержанную геометрию. Полные диалоги, условия, loot, поведение AI, баланс и медицина остаются в своих формах. Второй монитор нужен для одновременной работы с формой и пространством, а не для независимого запуска ещё одного writer.

Система должна сохранять рабочий Quest Editor, поддерживать сотни quests и тысячи reference features, различать редактируемое и справочное, не подменять snapshot телеметрией. Возможность редактировать конфигурацию не должна зависеть от запуска DayZ-мода.

Критерии выбора: минимальный риск для текущего Quest, один владелец записи, стоимость добавления следующего adapter, пригодность для многомониторной работы, понятный Save/Undo и отсутствие ненужного runtime coupling. Наличие красивой центральной карты само по себе не является критерием.

## 5. Сравнение архитектурных вариантов

Оценки сложности качественные, относительно текущего vanilla JS/PowerShell Workshop, а не оценки человеко-дней.

| Вариант | Польза и UX | Сложность, maintenance, стоимость перехода |
| --- | --- | --- |
| A. Карта внутри каждого editor | Контекст сразу рядом с формой; проста для одного модуля. Несколько больших форм конкурируют с картой за место | Низкий вход для первого editor, затем дублирование handlers, слоёв и поведения. Общая библиотека уменьшает код, но не число UI-контуров |
| B. Отдельная Map + synchronized detached window | Полные формы сохраняются; общий world context; второй монитор решает соседство формы и карты | Средняя суммарная сложность. Дешёвый переход к общей вкладке, отдельная стоимость lifecycle окна. Один renderer и набор adapters |
| C. Map-first, постоянный центральный canvas | Удобна для массовой расстановки spatial объектов; плохо использует площадь при диалогах, наградах и таблицах | Высокая стоимость перестройки рабочего Quest. Сложные панели рискуют воспроизвести старый editor вокруг карты |
| D. Самостоятельное Map-приложение | Независимый выпуск и применение вне Workshop; естественное отдельное окно | Высокая стоимость: отдельный bootstrap, версии, доступ к данным, discovery, протокол, потенциально auth/CORS. Преимущества независимого продукта сейчас не востребованы |

| Вариант | Ownership и риск дублирования | Multi-monitor, adapters и долгосрочная пригодность |
| --- | --- | --- |
| A | Доменные данные можно сохранить едиными, но легко получить независимые spatial caches в каждом editor | Несколько окон модулей тоже потребуют синхронизации; adapters часто разрастаются в отдельные UI. Уместен маленький read-only preview, не основная архитектура |
| B | Store каждого модуля — единственный mutable owner; Map — проекция. Риск появляется только если detached окно получит самостоятельную загрузку/запись | Общие adapters и renderer; лучший баланс для второго монитора и существующего проекта |
| C | Единый state возможен, но canvas начинает диктовать модель всем доменам | Несколько экранов возможны, однако формы всё равно придётся отделять. Adapter может превратиться в универсальный editor |
| D | Без серверного координатора возникают два источника истины; с ним — новый backend state layer | Гибко для нескольких клиентов/пользователей, избыточно для одного администратора. Adapters и версии нужно согласовывать между приложениями |

**Выбран B.** Вариант C не становится лучше только потому, что Map — общая: большая часть Quest не пространственная. Вариант D следует пересмотреть лишь при подтверждённой потребности в самостоятельном продукте или нескольких одновременных администраторах. Вариант A допустим как небольшой preview общего renderer, но не как четыре самостоятельных Map Editor. Отдельный вариант E не нужен: переиспользование renderer внутри B — реализация выбранного варианта, а не новая архитектура.

## 6. Рекомендуемая архитектура

Следующая схема описывает ответственность, не файловую структуру и не утверждённый API:

```text
Module forms ── domain commands ──┐
                                 v
                         Workshop coordinator
                         /        |         \
                   Quest state Migration state Future domain states
                         \        |         /
                          Spatial adapters
                                 |
                       Read-only projections
                           /             \
                    Map tab       Detached Map mirror
                           \             /
                         edit intents / selection
                                 |
                         Workshop coordinator
                                 |
                Module validation / serializer / persistence
                                 |
                  Explicit development file / export target
```

Coordinator маршрутизирует команды и согласует UI-контекст; он не знает правил награды, поведения infected или болезни. Доменный фасад разрешает конкретную операцию, проверяет revision и изменяет state. Adapter переводит доменные значения в spatial features и геометрический intent обратно в доменную команду.

Нативный JS остаётся исходным выбором. На первом этапе достаточно небольших модулей с явными зависимостями, подпиской на изменения и тестируемыми чистыми преобразованиями. Framework, глобальный plugin registry, event sourcing и новый сборочный стек не решают автоматически ownership и save-race. Переход на ES modules или иной способ подключения потребует отдельного решения о сохранении существующего `file:`-режима; для интегрированного редактирования целевым режимом является локальный HTTP.

Самое первое выделение ответственности — перенос shell navigation из Map в оболочку, без изменения поведения вкладок. Затем новый Migration state и adapter можно добавить независимо от глубокого переписывания `app.js`. Quest подключается позже через фасад и совместимые проверки.

## 8. Adapter architecture

### 8.1. Граница adapter

**RECOMMENDATION.** Adapter должен уметь перечислить spatial projections, сопоставить feature с владельцем, описать доступные операции и перевести move/resize intent в доменную команду. Проверка координат и геометрии может быть общей, но бизнес-ограничения проверяет модуль.

Не следует помещать в один adapter всё: загрузку произвольного файла, полный serializer, render всей формы, окно браузера, undo history, runtime запуск и Save. Такая конструкция станет «god adapter» с зависимостью Map от каждого домена.

Разделение операций:

- Module repository/persistence: загрузка конкретного источника, исходные bytes/hash, запись по whitelist.
- Module store/facade: команды, dirty, revision, validation, undo.
- Spatial adapter: projection, capability, domain identity, interpretation of edit intent.
- Map renderer: geometry, hit-testing, handles, preview.
- Shell navigator: `open entity`, `focus map`, переход к конкретной роли/полю.

Это логические обязанности, не требование немедленно создать пять классов для каждой точки.

### 8.2. Что добавить к идее MapFeature

Нужны owner module, source instance/workspace/world, stable entity reference, spatial part, geometry, capability, source revision и provenance. Отдельно — display metadata и состояние доступности. Для маршрута нужны различимые точки и их порядок; для окружности — смысл радиуса и центр, для прямоугольника — ориентация и размеры, для polygon — вершины.

Не следует сейчас утверждать универсальный сериализованный MapFeature JSON. Проекция может быть внутренним типом редактора, эволюционирующим после двух реальных adapters. Нераспознанная геометрия остаётся unsupported, а не превращается в круг с придуманным radius.

Editor-only point IDs можно хранить в draft metadata, сопоставляя их с исходным массивом. В runtime JSON их добавлять нельзя. После внешнего изменения массива старые point references должны считаться устаревшими, пока источник не перечитан и не сверено соответствие.

### 8.3. Capabilities и состояния

`readOnly/editable/reference` — полезные UI-ярлыки, но не одна взаимоисключающая характеристика данных. Разделить:

- назначение слоя: authored/reference/observation;
- разрешённые операции: inspect/select/move/resize/add/delete/reorder/write;
- доступность: readable/missing/parse-error/unsupported;
- состояние записи: clean/dirty/saving/conflict;
- runtime observation: unknown/observed с timestamp и сроком актуальности.

Reference может принадлежать отключённому моду. Edit capability должна проверяться владельцем, а не только скрытием кнопки на карте.

## 9. Editor state, canonical files и транзакции

**RECOMMENDATION.** Для каждого открытого источника держать исходный снимок, редактируемые доменные данные, revision, сохранённую revision/hash, validation и undo history. В основном Workshop это один экземпляр. Map projections вычисляются из него, detached копия не authoritative.

Не создавать универсальный merged JSON из Quest, Migration и Zones. Workspace объединяет ссылки на источники, а не их runtime-схемы. Формы и карта должны видеть изменения сразу через события состояния, без Save и без перечитывания диска.

Один drag — одна транзакция:

1. На pointerdown проверить owner, capability и исходную revision; захватить старое значение.
2. Pointermove обновляет временный preview, не файл и не сотни записей undo.
3. Pointerup отправляет одну команду; owner проверяет актуальность и публикует новую revision.
4. Escape, pointercancel, потеря контекста или связи отменяют preview.
5. Undo/redo работает над той же историей, что числовая форма. Pan/zoom и выбор слоя в неё не входят.

Смена числового поля должна объединяться в осмысленный edit, а не сохранять каждую цифру отдельной командой. Пока выполняется drag, конфликтующее изменение той же сущности из формы либо блокируется, либо отвергает drag по revision. Автоматическое слияние координат по принципу «последний победил» не рекомендуется.

Revert восстанавливает выбранный доменный источник после подтверждения потери несохранённых изменений; это не скрытое перечитывание всех модулей. После Save undo может оставаться доступным: возврат к старой геометрии тогда снова делает state dirty.

## 10. Detached Map / multi-monitor

### 10.1. Полезность и цена

**RECOMMENDATION.** Detached Map полезна как второе представление: на основном экране остаётся полная форма, на втором — большая карта. Она не должна открывать полноценный `index.html` с повторным init Quest, загрузкой draft и собственным Save.

Основное окно владеет состоянием и сохранением. Дополнительное окно получает snapshot, затем изменения и подтверждения команд. Выбор сущности синхронизируется; camera по умолчанию локальна каждому view. Команда «показать на карте» явно переносит focus, а произвольный pan не заставляет другой монитор прыгать. Два одновременно открытых map views используют одну реализацию renderer.

### 10.2. Сравнение транспорта

| Механизм | Применимость | Решение |
| --- | --- | --- |
| Общий объект / event bus в памяти | Хорош для формы и Map в одном JS realm; разные окна не получают автоматически тот же store | Использовать локально, не считать detached-решением |
| Прямые вызовы через `window.opener` | Просты, но связывают окна с внутренними функциями и lifecycle | Не использовать как публичный интерфейс; ссылка на окно годится для bootstrap |
| `postMessage`, при необходимости MessageChannel | Адресное взаимодействие известной пары окон, явный набор сообщений | Предпочтительный старт detached-прототипа |
| BroadcastChannel | Обмен между контекстами одного origin/storage partition без прямой ссылки на окно | Возможный поздний discovery/reconnect, не второй одновременно действующий transport |
| SharedWorker | Может владеть общей памятью независимо от одного view | Отложить: меняет жизненный цикл, усложняет текущий стек |
| HTTP polling / backend coordinator / WebSocket | Подходит, если authoritative session переезжает на сервер или появляются несколько администраторов | Не строить для пары окон; текущий PowerShell server хранит файлы, не editor sessions |
| JSON file / localStorage events как шина | Смешивают persistence, черновики и синхронизацию | Отклонить |

Проверка origin и формата сообщений необходима для `postMessage`; bootstrap должен дождаться готовности получателя. Для известного дочернего окна также проверяется `event.source`, а `targetOrigin` задаётся точно, без `*`. Эти требования следуют из модели cross-document messaging.[^9]

BroadcastChannel ограничен origin и storage partition, передаёт структурированные копии; сам API не задаёт бизнес-протокол согласования. Он не превращает несколько stores в один и не предоставляет истории для нового подписчика. Рекомендация для проекта — явно реализовать snapshot/revision handshake, если такой транспорт позднее понадобится.[^10]

### 10.3. Минимальный lifecycle-протокол

Следующее — **RECOMMENDATION**, концептуальные категории сообщений, а не зафиксированный API.

При открытии согласуются protocol version, случайная session identity, window identity, owner epoch, workspace/source/world и capabilities. После ready основное окно передаёт snapshot с revision. До подтверждённой синхронизации разрешён просмотр, но не редактирование.

Каждый edit intent содержит уникальный request ID, ожидаемую revision, entity/part reference и тип разрешённой операции. Owner последовательно принимает команды, проверяет их и отвечает accepted/rejected с новой revision. Повтор request ID не должен повторять изменение; ответ на уже обработанную команду воспроизводится. Разрыв последовательности изменений вызывает запрос полного snapshot, а не применение неизвестного patch.

Нельзя гарантировать «exactly once» одним транспортом. Дедупликация относится к текущей owner session; смена epoch делает старые сообщения недействительными. Если ответ потерян, окно запрашивает результат известной команды/новый snapshot, а не повторяет произвольное изменение как новое.

При закрытии или недоступности owner detached Map показывает «связь потеряна», отменяет неподтверждённый preview и блокирует mutation/save. Никакого автоматического повышения mirror до writer. Owner после reload восстанавливает совместимый draft, получает новую epoch, а окно проходит handshake заново. До явного восстановления нельзя обещать сохранность последнего неподтверждённого drag.

Liveness-проверка нужна для UX, но timeout не доказывает смерть вкладки: фоновый браузер может задерживать обработку. Консервативная реакция — пауза редактирования. При повторном открытии фокусировать известное map window; случайную вторую копию оставлять viewer до регистрации owner.

Два полноценных Workshop, открытых на одном source, опаснее двух mirrors. До разрешения detached edits требуется исключительное право записи для owner session на локальном сервере: второе основное окно открывается read-only либо предлагает явную передачу владения после разбора dirty. Сервер проверяет актуальную owner epoch при Save и draft write, чтобы старое окно после передачи не записало данные. Это небольшой write-ownership guard, не перенос всего editor state в backend. BroadcastChannel discovery и одно имя окна не заменяют такую проверку. Принудительное восстановление после падения owner — явное действие со сверкой source/draft, не автоматический leader election.

`window.open` может быть заблокирован, а opener-связь может отсутствовать из-за политики открытия/изоляции. Поэтому detach запускается явным кликом, с проверкой результата и сохранением работающей встроенной Map. Автоматический выбор физического монитора не обещается: окно переносится пользователем.[^11] `file:`-режим не следует использовать как baseline синхронизируемого редактора; поведение localStorage для file URL не стандартизовано одинаково между браузерами.[^12]

**NEEDS PROTOTYPE:** фактические Edge/Chrome окружения администратора, popup/reload/закрытие owner, sleep/resume, reconnect, неправильный workspace, два одинаковых окна и отдельный owner. До этой проверки detached остаётся направлением, не готовой функцией.

## 11. Quest + Map

### 11.1. Фактические сущности и роли

**CONFIRMED CURRENT STATE.** В dev JSON находятся 12 quests и 7 triggers. Поля ролей называются `offerTriggerIds[]`, `completionTriggerIds[]`, `rewardTriggerIds[]`, хотя текущая редакторская модель допускает один Offer, несколько Completion и один Reward. `triggerActions[]` связывает `triggerId + actionType` с диалогом и наградами действия; в текущем нормализаторе action нет отдельного массива objectives. Основные objectives, giveItems и rewards находятся на уровне quest.[^7][^13]

Например, `quest_hunter_2` берётся у `hunter_trigger`, имеет Completion у `Rasputin_1_trigger` и Reward снова у `hunter_trigger`. Это два физических trigger и три ролевых блока, а не три NPC. `quest_hunter_1` использует одного hunter для Offer и Reward без Completion. Один и тот же NPC обслуживает несколько quests; перенос его координат влияет сразу на все такие связи.[^7]

`getQuestFlowActiveBlocks` строит блоки в порядке Offer → Completion[] → Reward; ключ включает роль и triggerId. `syncQuestTriggerActions` ищет первое действие по той же паре. Даже если массив содержит повтор triggerId, независимой идентичности двух одинаковых role blocks нет. Следовательно, схема «посетить того же NPC дважды как разные Completion одного quest» не получает независимые stage IDs автоматически. Это отдельная доменная задача, не повод добавить runtime stageId через Map.[^2]

QUEST_LOGIC_SPEC требует выполнения всех Completion перед Reward, но не задаёт универсальный маршрут обязательного посещения Completion строго в порядке массива. Карта может показывать порядок редакторских блоков; стрелки не должны обещать несуществующее правило выполнения.[^13]

### 11.2. Spatial и non-spatial

| Часть Quest | На карте | В редакторе Quest |
| --- | --- | --- |
| `trigger.position`, `radius` | Маркер и радиус trigger; move/resize после подключения adapter | Точные X/Y/Z, ограничения и подтверждение влияния на связанные quests |
| `npcPosition`, `npcOrientation` | Отдельная позиция и, при проверенном преобразовании, направление NPC | Полный вектор ориентации; class/loadout/equipment |
| `focusRadius`, `focusHeight` | Выделенный вспомогательный overlay/подпись, не общий радиус zone | Значения и объяснение игрового фокуса |
| Offer / Completion / Reward | Badges и связи выбранного quest с trigger | Назначение ролей и `triggerActions` |
| `requiredQuestIds` | Опциональная ссылка/индикатор зависимости, не пространственный маршрут | Зависимости и проверка доступности |
| objectives / giveItems / rewards / dialogText / cooldown | Краткое summary по запросу | Полное редактирование и валидация |

`position` и `npcPosition` нельзя неявно считать одним полем: значения сейчас могут совпадать, но принадлежат разным аспектам trigger. Для совместного перемещения нужен явный режим «перенести trigger и NPC», показ старых/новых значений и одна составная команда. NPC orientation не нормализуется разрушительно при просмотре: например, текущий hunter имеет первое значение 380; отображение стрелки по модулю 360 не является разрешением переписать исходный вектор.[^7]

2D-круг focus не доказывает полную 3D-область взаимодействия. Overlay должен быть помечен как проекция; `focusHeight` не превращается в радиус.

### 11.3. Навигация, маршруты и много quests

Click по общему NPC открывает список связанных quests/ролей; выбранная роль подсвечивает существующий блок, а не создаёт новый. «Открыть в Quest» передаёт стабильные `questId + role + triggerId`, разрешает их в текущем store, выбирает подходящий NPC flow mode и фокусирует форму. Текущий индекс массива используется только внутри старого editor, не как долговечная ссылка.

При удалённой сущности показать «ссылка устарела»; нельзя молча открыть соседний индекс. При смене ID обновляются доменные ссылки по существующим правилам и пересчитывается projection.

На обзорной карте отображаются уникальные NPC/triggers, не маркер на каждый role block каждого quest. Для 100/150/300 quests сначала нужны поиск по ID/имени/NPC, фильтр выбранного quest и агрегированные badges. Все линии всех quests одновременно создадут нечитаемую сеть. Маршрут выбранного quest — условное соединение role locations, не navmesh, не проверка проходимости и не гарантия порядка Completion.

Создание quest через карту допустимо как **guided Quest workflow**: выбрать существующий trigger или явно создать новый в Quest, затем заполнить обязательные роли и условия в форме. Map задаёт место, но не генерирует готовую игровую логику. Неполный skeleton остаётся draft с понятными ошибками, не экспортируется как валидный quest. Автоматическое назначение всех nearby NPC этапами отклоняется.

## 12. Migration + Map

### 12.1. Что уже существует

**CONFIRMED CURRENT STATE.** Canonical config содержит `groups`, `events`, `activations`; в текущем примере — две группы, один event и две activation: STARTUP и EXTERNAL. Legacy `scenarios` поддерживается загрузчиком в памяти, но не является целью новой записи. Полноценного Migration Web Editor пока нет.[^8][^14]

GROUP — blueprint параметров и геометрии. EVENT объединяет groupIds. ACTIVATION указывает targetType GROUP/EVENT и targetId. `S77MigrateAPI` имеет bool-фасады `Activate`, `StartGroup`, `StartEvent`; это runtime API, не endpoint локального Workshop.[^15]

| Поле/сущность | Пространственная интерпретация | Ограничение |
| --- | --- | --- |
| `spawnPosition` | Центр spawn formation | Не фактическая позиция каждого infected |
| `routePoints[]` | Упорядоченные контрольные точки | Не рассчитанный движком путь |
| `targetPosition` | Центр назначения formation | Индивидуальные цели имеют offsets |
| `routePointReachRadius` | Допуск достижения точки отдельным unit | Не радиус группового AI stimulus |
| `routeActivationRadii[]` / fallback `routeActivationRadius` | Радиус вокруг raw route point для группового порога | Индексы связаны с `routePoints[]`; не независимый список кругов |
| `finalActivationDistance` | Радиус группового порога у центра final target | Отличается от arrival tolerance |
| `finalHoldRadius` | Дистанция от общего final target center, после которой рассматривается возврат | Показывать только с правильной подписью и enabled-состоянием |
| `finalHoldReturnRadius` | Допуск возвращения к индивидуальной `m_MigrationTarget` | Не гарантированно концентрическая внутренняя окружность общего hold center |
| EVENT / ACTIVATION | Логическая группа/ссылка; подсветка связанных GROUP | Не придумывать им собственные координаты |

Различие центров подтверждено `StartGroupBlueprint`, `SpawnMigrationInfected`, `UpdateHoldFree`, `FollowPath`: hold проверяется относительно `m_FinalTargetCenter`, возврат — относительно target с formation offset. Поэтому красивое изображение двух концентрических «точных» колец вводило бы в заблуждение. Допустим подписанный schematic overlay с объяснением, а не ложная точность.[^16]

`spawnChancePercent`, infectedCount/types, weather, lifetime, spacing/jitter, recovery/watchdog, stimulus strength и timers — настройки Migration Editor. Не каждое поле с distance/seconds следует превращать в draggable handle.

### 12.2. Последовательность создания редактора

Сравнение: полный form editor до карты даст долгую отсрочку проверки общего state; карта без формы создаст второй неполный editor. **RECOMMENDATION: минимальная форма и spatial adapter одновременно над одним новым Migration store.** Это локально проверяет архитектуру, не затрагивая сразу большой Quest state.

Далее расширяются доменные формы GROUP/EVENT/ACTIVATION, ссылки и validation. Наличие Map не отменяет числовой ввод, копирование DayZ X/Y/Z и обзор всех скрытых полей.

### 12.3. Геометрические операции и высота Y

Drag spawn/target/route point меняет X/Z; исходный Y сохраняется как исходное значение, но после переноса помечается «высота требует проверки». Новая точка без достоверного Y остаётся неполным draft. Автоматический Y=0 и угадывание высоты по соседним точкам отклоняются.

**RECOMMENDATION для первой реализации:** разрешить корректировку Y числом или вставкой проверенного DayZ-вектора; перед каноническим Save перемещённой точки требовать явного подтверждения высоты. Это friction, но оно не позволяет карте изображать terrain service, которого нет. `ECE_PLACE_ON_SURFACE` используется при spawn infected, однако это не универсальная гарантия правильности route/target/NPC Y и не источник высот для Workshop.[^16]

**DEFER:** terrain provider с version/world identity, правила для зданий, мостов и многоуровневых позиций. Даже достоверная высота земли не всегда равна требуемому этажу.

Для add/delete/reorder route необходимо одной командой перемещать или удалять соответствующий per-point radius. При отсутствии элемента `GetRouteActivationRadius` использует fallback; editor обязан различать «унаследовано» и «явно задано», а не материализовать все defaults при чтении. Неизвестные и legacy-поля сохраняются; сознательная миграция формата — отдельная операция.[^14]

Radius handle меняет только подтверждённый тип радиуса, имеет числовой эквивалент, ограничение допустимого диапазона, preview и cancel. Пустой маршрут, duplicate ID, несогласованный радиус и координата вне мира требуют domain-aware диагностики. Большой радиус может легитимно выходить за границу подложки; это предупреждение, а не автоматическое обрезание данных.

## 13. Quest → Migration

### 13.1. Выбор ссылки

| Связь | Достоинство | Недостаток / решение |
| --- | --- | --- |
| Quest → GROUP | Самый короткий путь к одному blueprint | Quest знает нижний уровень композиции; неудобно заменить запуск набором групп |
| Quest → EVENT | Скрывает состав групп | Всё ещё связывает quest с содержимым события, минуя внешнюю точку запуска |
| Quest → ACTIVATION | Стабильная именованная точка входа; за ней GROUP или EVENT | Требует проверки типа, enabled и target chain; **рекомендуется** |
| Quest → preset + LaunchContext | Гибко передаёт параметры конкретного запуска | Такой контракт ещё не подтверждён API; переносит runtime-настройки в Quest; отложить |

Предпочтительная цепочка: Quest condition → разрешённая EXTERNAL ACTIVATION → Migration target. Quest хранит ссылку на activation, не spawn/route/infectedCount/weather. Точное новое поле Quest JSON здесь не утверждается.

Старые идеи документов 14/16 допускают GROUP/PRESET и контекст запуска; приоритетные планы 31/32 уже обсуждают EVENT/ACTIVATION. Рекомендуется в будущих задачах согласовать их с текущими `GROUP/EVENT/ACTIVATION` и выбрать activation-only для первого bridge, не поддерживать одновременно три конкурирующих варианта ссылок.[^17]

### 13.2. Runtime-ограничения, которые нельзя скрыть картой

`RequestActivation` разрешает target по ID, но сам по себе не ограничивает публичный вызов только типом EXTERNAL. Следовательно, требование «quest может запускать только EXTERNAL» должно стать явным правилом будущего bridge и его validation, а не предположением о готовой защите API.[^16]

Bool `true` не значит «все существа появились»: `RequestGroup/RequestEvent` возвращают true и при нуле выбранных групп после chance. Spawn выполняется отдельной логикой; классы и создание объекта могут не пройти проверку. `LAUNCH_BUSY` возвращает false, а не ставит запрос в гарантированную очередь. Карта не должна маркировать группу «запущена» по наличию корректной activation или accepted-команды.[^16]

`SpawnMigrationInfected` проверяет наследование от `DayZInfected`. Обычные животные не становятся совместимыми с этим контроллером. Собака/мутант может быть допустим только после проверки конкретного mod classname и базового класса; общую поддержку таких существ нельзя обещать по пользовательскому названию.

Будущий bridge должен отдельно определить:

- точный серверный момент вызова: принятие, подтверждённый Completion или другое проверенное условие;
- scope запуска: на игрока, группу игроков, прохождение quest либо глобальный cooldown;
- idempotency key и хранение факта запроса для повторных RPC/reconnect/restart;
- реакцию на absent/disabled Migration, неверный target, busy и chance miss;
- блокирует ли ошибка игровой этап или оставляет его завершённым;
- журнал request/result с quest/activation и различением accepted, skipped, failed, spawned, если runtime позже даст такие наблюдения.

Повтор не должен бесконтрольно создавать мировые группы. Обёртка не должна автоматически вызывать API при редактировании или Save. Веб-bridge между редакторами и серверный Quest→Migration bridge — разные задачи и разные границы доверия.

### 13.3. Создание Migration skeleton из Quest workflow

Идея допустима только как явная команда «Создать в Migration и связать». Карта сама не создаёт чужую сущность при клике на quest stage. Первый bridge MVP связывает **уже существующую** EXTERNAL activation; создание межмодульного skeleton откладывается.

Позже guided workflow может открыть Migration с draft GROUP, собрать spawn/route/target через общий map picker, заполнить обязательные параметры и явно создать activation. Quest получает ссылку только после успешной validation. Event нужен лишь для нескольких групп, а не как обязательный пустой wrapper.

Для такого workflow потребуется coordinator составного черновика:

1. Зарезервировать уникальные ID без переименования существующих сущностей.
2. Показать созданные GROUP/ACTIVATION и будущую Quest-ссылку до подтверждения.
3. Cancel до подтверждения удаляет только собственные несохранённые drafts.
4. Undo не удаляет сохранённую/reused сущность другого модуля без проверки обратных ссылок.
5. Перед Save проверить всю цепочку; сначала сохранить Migration dependency, затем Quest.
6. Если Quest-save не удался, сохранить его draft и показать «Migration сохранена, ссылка ещё нет». Не заявлять атомарность двух файлов.
7. Orphan может быть допустимой самостоятельной activation; предлагать inspect/cleanup, не удалять автоматически.

Без такого управления отменой идея создаёт сильную связанность и скрытые side effects. Поэтому она не входит ни в первый spatial slice, ни в первый runtime bridge.

## 14. Zones + Map и граница Medicine

**CONFIRMED CURRENT STATE.** Zones ещё не имеет окончательного canonical JSON. Реальный lighting prototype вычисляет центр на 25 м впереди начальной позиции игрока; outer/inner радиусы 20/8 м находятся в коде. Это клиентская проверка lighting transition, не готовый набор постоянных world zones. Проецировать такой центр на карту как фиксированную canonical территорию нельзя.[^18]

**RECOMMENDATION.** Map должна поддерживать геометрические capabilities, а не навязать Zones единственный `center + radius`. Один zone может иметь несколько spatial extents компонентов; отображать их следует с названиями и legend. Circle/rectangle/polygon допускаются только после подтверждения соответствующего domain contract и проверки ограничений самопересечения, ориентации и высоты.

Environmental Visual/Audio/Hazard/exposure и территориальные правила защиты остаются в Zones Editor. Но старое перечисление Disease как внутренней настройки Zones уже не соответствует выделенной Medicine: заболевание, стадии, симптомы, лечение и persistence принадлежат Medicine. Медицинские visual/audio симптомы не дублируют ambient-эффекты зоны. Редактирование exposure связывает направления, но не переносит disease state в Zones.[^19]

Рекомендуемое раннее подключение Zones — read-only adapter к подтверждённому источнику либо mock fixtures для технического prototype, ясно отделённые от runtime. Сначала требуется утверждение минимального Zones source contract в отдельной задаче; геометрический интерфейс Map не должен сделать этот выбор задним числом.

## 15. Внешние моды и server-profile источники

### 15.1. Read-only прежде write-back

**RECOMMENDATION.** Каждый источник имеет format-specific parser, provenance, version/hash, coordinate interpretation и capabilities. Не нужно преобразовывать все TXT/XML/JSON в один runtime JSON и затем экспортировать его обратно.

MedicalAttention `DeclareZone`, Night/Sound zones, Radiation, Trader, territory XML и cache spawner могут сосуществовать как projections одного мира. Похожая координата не доказывает одинаковую семантику, а совпадающее имя не является разрешением объединить сущности. В server reference есть и активные конфиги, и справочные/старые варианты; статус определяется источником, а не цветом маркера.[^20]

Write-back допускается только при выполнении всех условий: источник явно выбран как editable; конкретный путь зарегистрирован сервером; parser распознаёт полный редактируемый документ; известна семантика поля; round-trip сохраняет неизвестные поля; есть hash/conflict check, backup, validation и ручной diff preview. Неполный parser остаётся read-only.

JSON parser должен сохранять не редактируемые объекты и числовые значения; нормализаторы Quest для этого не подходят. Для TXT/XML могут быть существенны комментарии, порядок, пробелы и чужие секции. Нужен lossless patch/token-aware подход либо явно согласованный форматтер. Если round-trip не доказан, запись запрещена; «успешно показали 80% точек» не означает «можно сохранить весь файл».

При отсутствии native ID временный feature key составляется из source identity, locator и source revision. После изменения source hash связь считается требующей пересопоставления. Координаты и номер строки не выдаются за вечный ID.

### 15.2. Конкретный пример CacheSpawner

**CONFIRMED CURRENT STATE.** `Config_CacheSpawner.json` содержит `CacheList[]` с `Classname`, `Min_Caches_In_Map`, `Max_Caches_In_Map`, `Coords[]`, `Time_Wait_Spawn`, `Time_Respawn`, `ItemsInside`. В `Coords[]` есть `Position[X,Y,Z]` и `Orientation`. Две записи содержат 62 позиции ShronGreenBox и 48 ShronRukzak. У первой min/max=61, то есть количество возможных точек не равно объявленному числу cache в мире.[^21]

Adapter показывает 110 **configured candidate positions**, тип объекта и исходный locator. Timer, min/max и contents остаются в карточке исходного модуля. В `ItemsInside[].ItemCharacteristic` действительно есть `Chance_Spawn`; это настройка содержимого, а не доказательство вероятности выбора каждой координаты. Её шкалу и алгоритм нужно подтвердить исходником CacheSpawner, не угадывать по числу. В том же snapshot встречаются разные написания `Temperature` и `Themperature`: adapter не должен самовольно исправлять чужие ключи. Карта не утверждает, что все 110 тайников сейчас существуют.

Для будущего spatial edit достаточно translate Position и отдельной ориентации. Специальной логики cache в Map core не требуется. Write-back этого snapshot в live profile не разрешается автоматически даже после появления adapter.

## 16. Layers, filters, selection, focus и UX

### 16.1. Независимые состояния

`activeView` отвечает за открытую вкладку; `editModule` — за доменные команды; `selection` — за выбранную сущность; `visibleLayers` — за пространственный контекст; camera — за область обзора. Map не является `editModule`.

Пример: основной editor — Migration, Map открыта на втором мониторе, видны Migration + Quest NPC + MedicalAttention. Click по MedicalAttention показывает справочную карточку и источник, но не даёт move и не переключает доменный owner молча. «Открыть в Quest» — явная навигация; «Редактировать Migration» — явное возвращение режима.

Выбор скрытого объекта через форму может временно показать его feature с пометкой «показано по выбору», не перезаписывая сохранённые фильтры. Фокусировать следует bbox геометрии с margin, а не только центр больших зон.

### 16.2. Layout и sub-modes

Текущая Quest workspace использует широкую трёхколоночную сетку; Map — квадратный viewport и информационную колонку 300 px. У большого широкого окна квадрат по ширине может не помещаться по высоте 1080p. При detach нужен viewport, ограниченный доступной высотой, а не просто растянутая текущая страница.[^1]

Рекомендуемый layout: сверху компактный toolbar с owner/source/world, режимом и dirty; слева сворачиваемые слои и поиск; центр — карта; справа сворачиваемый inspector. В обычной вкладке второстепенные панели можно закрыть, в detached — оставить карту и краткие свойства. Не требуется всегда держать три широкие колонки.

Базовые sub-modes: Browse, Select, Edit geometry, Pick position, Measure. Они должны иметь явный индикатор и Escape для выхода. Pick position вызывается модулем для конкретного поля; обычный click не создаёт сущности. Measure — editor-only расстояние X/Z, не доказательство длины игрового пути.

Drag handle активен только у выбранной редактируемой geometry. В остальных случаях click выбирает, pan двигает карту. Большие залитые окружности не должны перекрывать все точки внутри: нужны приоритет handles/markers, прозрачный hit-test или список объектов под курсором. Для совпавших NPC/зон показывать disambiguation, а не выбирать случайный последний SVG-элемент.

### 16.3. Производительность

**HYPOTHESIS:** нынешний SVG достаточен для первого slice; bottleneck при тысячах features вероятнее проявится в DOM churn, подписях и hit-testing, чем в нехватке нового framework. Это требует измерения.

Сначала включить выбранные маршруты и радиусы, фильтрацию слоёв, ограничение подписей по zoom, виртуализацию длинных списков и обновление изменённых features. Pan не должен массово пересчитывать символы, если scale не изменился. Preview ограничивается animation frame, не сериализует все данные на каждом pointermove.

Позже — bbox-culling с учётом радиуса/сегментов, spatial index и clustering точек. Отбор только по центру ошибочно скроет зону, пересекающую viewport. Не объединять редактируемые handles в cluster; раскрывать cluster перед mutation. Canvas/WebGL рассматривать лишь после benchmark и с учётом стоимости hit-testing, текста и доступности.

**NEEDS PROTOTYPE:** сценарии 100/300 quests и 100/1000/4000 mixed features, несколько маршрутов, большие перекрывающиеся радиусы. Записывать время initial projection/render, select/filter, pan/drag, DOM count и память на целевой машине. Предварительные acceptance targets, не результаты замеров: выбор до 100 мс, drag без заметных пауз свыше 50 мс; окончательные бюджеты согласовать после baseline. 4000 — стресс-сценарий, а не утверждение о числе текущих активных объектов.

## 17. Save, validation, conflicts и безопасность

### 17.1. Единственный владелец записи

**RECOMMENDATION.** Только основной Workshop инициирует module save; detached кнопка, если появится, отправляет owner запрос. Запись принимает логическую source identity, expected revision/hash и данные разрешённого домена, не произвольный клиентский путь.

Минимальный безопасный цикл:

1. Зафиксировать snapshot state revision R и hash прочитанного source.
2. Проверить типы, конечность чисел, геометрию, ID, references и ограничения домена; запретить Save при blocking errors.
3. На сервере заново разрешить whitelist-цель и сверить текущий hash.
4. При несовпадении — conflict: оставить draft, показать внешнюю и локальную версии, предложить сравнение/reload; не перезаписывать молча.
5. Сохранить восстановимую копию, записать временный файл на том же томе, проверить результат и заменить целевой файл подходящей атомарной операцией.
6. Вернуть подтверждённый hash/версию. Clean становится только сохранённая revision R; изменения R+1 остаются dirty.
7. Удалять/обновлять draft только до подтверждённой revision, не затрагивая более свежий черновик.

Операция замены и поведение на Windows/сетевом файловом ресурсе требуют отдельного теста; нельзя обещать одинаковую атомарность везде. Повторная проверка непосредственно перед replace уменьшает окно внешней гонки, но несогласованный внешний writer всё ещё требует осторожной стратегии locking/version checks.

### 17.2. Валидация и round-trip

Синтаксически корректный JSON не обязательно допустим для runtime. Общая validation проверяет numeric/finite, тип вектора, допустимый world, ID и ссылки. Domain validation проверяет Quest роли и equipment, Migration GROUP/EVENT/ACTIVATION, семантику radii и enabled/default. UI и сервер не должны доверять друг другу как единственной проверке.

Существующая runtime normalization Migration умеет подставлять defaults; editor должен показывать effective value отдельно от исходного отсутствующего поля. Нельзя незаметно «починить» malformed файл созданием default config. Для unsupported schema/version — read-only с объяснением.

Сохранение одной spatial правки должно сохранить остальные поля. Проверка — round-trip comparison исходного/выходного объекта и diff ожидаемого поля; для внешних TXT/XML дополнительно проверяется текстовая сохранность. Shared adapter model не разрешает стирать незнакомые данные.

### 17.3. Manual Save и drafts

Manual Save — явная публикация в development config; autosave — восстановимый черновик. Эти статусы визуально различаются. Autosave canonical файлов на каждый drag отклоняется.

Draft должен знать workspace/source identity, source hash, schema/version, owner epoch и revision. In-flight записи сериализуются или сервер отвергает старые revisions. UI показывает draft persistence failure и сохраняет доступную локальную копию; не снимает dirty после HTTP ошибки. Recovery старого draft поверх изменившегося source требует сравнения и выбора, не автоматического «новейший timestamp победил».

Закрытие окна с dirty требует предупреждения там, где это допускает браузер; оно не заменяет своевременное сохранение draft. Сохранность последнего события при аварийном завершении не гарантируется.

### 17.4. Trust boundary и export

Текущий loopback server не следует считать универсально безопасным файловым API. В write-маршрутах нужны ограничения методов/content type/размера, session token и проверка допустимого origin, серверная validation, логирование целевой операции и защита от path traversal. Политика static serving также должна исключать конфиги с приватными путями и черновики из произвольной раздачи.[^5] Это требования будущего hardening, а не реализованные изменения TASK 171.

Explicit source whitelist должен разрешать точные зарегистрированные цели и проверять итоговый путь, включая обход через ссылки/reparse points. Факт нахождения пути «где-то в profiles» недостаточен.

Dev Save и profile export — разные кнопки, права и результаты. Deployment показывает target и diff/backup; read-only repository snapshot никогда не становится live source сам по себе. Cross-module Save не обещает общей атомарности: сохранять зависимости раньше потребителей и показывать частичный результат с возможностью завершить операцию.

## 18. Workspace / multi-server и роль admin tool

Уже сейчас нужен минимальный контекст: workspace identity, logical source identity, resolved target, world identity/size/coordinate convention, source revision. Это позволяет не применить сообщение от другого проекта и не восстановить чужой draft. Имя файла `MigrationConfig.json` и порт 4173 не уникальны между копиями проекта.

**RECOMMENDATION.** Для первого slice выбрать один локальный workspace, один ChernarusPlus и зарегистрированные dev-источники. Сервер должен сообщать свою workspace identity; одного `/api/health {ok:true}` недостаточно, чтобы доказать, какая копия Workshop обслуживается. При смене source/world сбрасывать stale projections/selection после разрешения dirty, не смешивать 15360-метровую карту с другим terrain.

**DEFER:** UI нескольких серверов, одновременное редактирование несколькими администраторами, сетевой backend coordinator, role-based access, live telemetry. Минимальные source/workspace keys нужны до detach, но полноценная workspace-платформа не нужна до первого drag.

Map остаётся административным инструментом `JSON_Quvest`, не компонентом DayZ PBO. Runtime получает только свои config/команды через отдельно утверждённые механизмы. Доступность мода, enabled config и фактическое выполнение — независимые вещи: offline configuration editing разрешено, runtime state без телеметрии отображается как unknown.

## 19. Failure modes и безопасное поведение

| Сбой | Реакция системы | Что не делать |
| --- | --- | --- |
| Adapter parser failed / malformed config | Изолировать слой, сохранить raw source и diagnostics, запретить write-back | Не сохранять только распознанную часть файла |
| Unknown fields / version | Сохранить неизвестное; unsupported version — read-only | Не прогонять через Quest normalizer |
| Unsupported coordinates / другая карта | Показать причину и source/world; не разрешать move | Не угадывать порядок осей и не ставить нули |
| Source missing | Пометить missing; оставить несохранённые локальные изменения для recovery | Не создавать default-файл поверх выбранной цели молча |
| Mod disabled / не установлен | Разрешить config inspection/edit при наличии прав, runtime пометить unknown/disabled по конкретному свидетельству | Не прятать слой и не объявлять объекты активными |
| Stale profile/snapshot | Показать provenance, timestamp/hash и отдельный deployment status | Не считать snapshot текущим сервером |
| External file changed | Conflict, diff, reload/merge по явному выбору | Не last-write-wins |
| Detached disconnected | Заморозить edits, отменить preview, затем handshake/snapshot | Не повышать mirror до writer |
| Save error / timeout | Dirty сохраняется; проверить результат запроса по hash/ID перед повтором | Не выдавать download fallback за успешную запись target |
| Partial multi-file save | Показать каждый успешный/неуспешный шаг, сохранить drafts и plan recovery | Не утверждать «всё сохранено» |
| Orphan cross-module link | Blocking validation для отсутствующего target; обратные ссылки для cleanup | Не удалять чужую reused entity |
| Stale selection / удалённый point | Отвергнуть intent, обновить projection, предложить повторный выбор | Не использовать соседний array index |
| Duplicate commands / поздний ACK | Dedup по request ID и epoch, сравнение revision | Не повторять mutation как новую |
| Недостаток прав / backup failure / диск заполнен | Остановить запись и показать причину; оставить draft | Не удалять исходный файл ради «успешного» сохранения |

## 20. Что не делать

Не делать Map главным владельцем Quest/Migration/Zones JSON, второй независимый writer в detached окне или универсальный редактор любых путей. Не переносить полные доменные формы на canvas и не дублировать Quest editor под видом inspector.

Не использовать периодический Save/reload файла для синхронизации UI. Не делать runtime-запуск побочным эффектом изменения конфигурации. Не выводить runtime active из enabled, а количество configured points — как количество живых объектов.

Не включать в первый slice terrain service, генератор cross-module skeleton, runtime bridge, новый Zones contract, live telemetry, произвольные polygon tools и замену SVG. Не переписывать весь `app.js` до появления проверяемого небольшого цикла.

Не выдавать предложенные имена сообщений, структуру adapter или editor-only IDs за уже принятый публичный API. Документы приоритетов 31/32/33 требуют последующего согласования, а не массовой правки внутри этого аудита.

| Высокий | Y и неверная семантика radius | Явная Y-policy и подписи spatial parts, не универсальный radius handle |
| Средний | Старые планы GROUP/PRESET/LaunchContext и новая activation-модель | Согласовать один первый bridge; runtime acceptance не считать spawn result |
| Средний | Map owns shell navigation, hardcoded Medical source/count | Выделить shell и source descriptor без широкого framework migration |
| Средний | SVG full rebuild, symbol rescale при pan, перекрытие hit areas | Измерения, selected-only overlays и инкрементальные обновления |
| Средний | Широкая CSS-сетка и квадратный viewport | Height-constrained Map, корректная screen/world матрица на неквадратном viewport |
| Средний | Преждевременная универсализация Zones/external schema | Два реальных adapters до стабилизации внутреннего spatial contract |
| Низкий на первом slice | Multi-server UI, workers, plugin registry | Отложить, сохранив source/world identity |

Отдельная геометрическая ловушка текущей карты: pan вычисляет смещение через размер DOM rect и view width/height, тогда как `screenToMap` использует SVG CTM. После изменения пропорций viewport и появления letterboxing эти пути могут расходиться. Будущий detach/layout prototype должен использовать согласованное преобразование экранных точек и проверить zoom/pan при разных соотношениях сторон.[^3]

**HYPOTHESIS:** минимальный новый Migration store будет дешевле и безопаснее, чем первое внедрение транзакций непосредственно в большой Quest editor. Проверяется выбранным slice. Если он потребует сотен новых абстракций ради одной координаты, архитектуру следует упростить, а не расширять до «универсальной платформы».

## 22. Рекомендуемая последовательность реализации

Сначала выполнить ровно один slice из раздела 23. После него — пять следующих этапов с самостоятельными gates:

1. **Полный Migration Editor.** GROUP/EVENT/ACTIVATION forms, route add/delete/reorder с радиусами, domain validation, round-trip и ссылки. Gate: сохранить существующий config без непредусмотренных изменений.
2. **Quest spatial adapter.** Сначала read-only роли, selection и deep links; затем move/resize через фасад существующего state. Gate: сохранены роли, диалоги, rewards, objectives, NPC equipment и старый экспорт.
3. **Detached Map.** Один owner, точечный transport, lifecycle/recovery и window registration. Gate: потеря связи не приводит к записи, два окна не конфликтуют.
4. **Минимальный Quest→Migration runtime bridge.** Только существующая EXTERNAL activation, серверный trigger moment, idempotency и обработка ошибок. Gate: повторные запросы и busy/chance miss не нарушают quest progression.
5. **Zones и внешние adapters.** Zones — после отдельного contract prototype; внешние sources — read-only, затем один доказанный whitelist write-back. Gate: unknown fields и исходная семантика сохраняются.

Detached read-only prototype можно исследовать раньше, если второй монитор станет ближайшим приоритетом, но не переносить его риски записи в первый slice. Создание Migration skeleton из Quest — отдельное продолжение после доказанного bridge, а не скрытая часть этапа 4.

## 23. Первый vertical slice

### 23.1. Выбор и scope

**RECOMMENDATION: «Одна существующая Migration GROUP — координаты в форме и на Map из одного state».**

Загрузить существующий canonical Migration config через узкий зарегистрированный dev-source, показать список существующих GROUP, выбрать одну. Для выбранной группы отобразить spawn, существующие route points, target и линии порядка; невыбранные данные сохранить неизменными. Минимальная форма редактирует X/Y/Z существующих точек; Map drag меняет X/Z в том же store, Y требует подтверждения. Включить dirty, одну транзакцию на drag, cancel, undo/redo, explicit Save, conflict и draft recovery.

Это не полный Migration Editor. Достаточно existing points: создание групп, EVENT/ACTIVATION editing, add/delete/reorder route и radius handles не входят. Read-only MedicalAttention остаётся доступным рядом как независимый reference-слой.

Такой slice доказывает основную архитектуру: два UI над одним доменным state; проекция не является source of truth; данные сохраняются обратно без нового runtime-контракта. Он полезнее второго read-only viewer, но намного меньше одновременного построения detached/bridge/полных форм.

### 23.2. Предполагаемые файлы будущей implementation TASK

Перечень ниже — **кандидаты**, не изменения TASK 171 и не утверждённый новый API:

| Файл / зона | Будущая минимальная ответственность |

| `JSON_Quvest/map.js` | Общий projection input, selection, point preview/intent; сохранение существующих map controls |

`app.js` не должен подвергаться глубокой переделке; предпочтительно не менять его в этом slice. Если shell extraction требует небольшой связки, будущая задача должна явно назвать её и ограничить. `editor-config.json`, launcher, profile export и runtime config schema не расширяются «заодно». Изменение стартовой регистрации dev-source, если потребуется, следует заранее включить в точный allowlist будущей задачи.

Тестовые записи — только в созданную для теста копию MigrationConfig. Canonical config является источником чтения; ручной Save в рабочий dev-file допустим лишь в специально разрешённой будущей implementation TASK и после просмотра diff. Production export исключён.

### 23.3. Что намеренно исключить

Нет нового Quest JSON поля, Migration runtime кода, генератора GROUP/EVENT/ACTIVATION, автоматической нормализации legacy, полной формы поведения AI, редактирования Zones, внешнего write-back, detached окна, многопользовательского режима, terrain height API и runtime-команд из браузера.

Не сохранять editor-only IDs в MigrationConfig. Не записывать reference MedicalAttention. Не запускать `S77MigrateAPI` из Save.

### 23.4. Критерии успеха

- Одна загрузка создаёт один authoritative Migration state; форма и Map показывают одинаковые значения без промежуточного Save.
- Смена X/Z числом двигает тот же point; drag обновляет форму. Другие группы/поля не меняются.
- Escape и pointercancel возвращают исходное значение; один завершённый drag отменяется одним Undo, Redo его восстанавливает.
- Перемещение не обнуляет Y; unconfirmed height блокирует canonical Save.
- Projection и обратное преобразование сохраняют оси и порядок route; непредусмотренной потери precision нет.
- No-op round-trip семантически сохраняет config, неизвестные поля и отсутствие optional defaults; пространственный Save меняет только разрешённую позицию.
- Ошибочный vector, duplicate ID, missing target reference, malformed source и unsupported version не публикуются.
- Изменение формы во время Save оставляет новую revision dirty.
- Внешнее изменение source вызывает conflict, не overwrite.
- Save/backup/draft failure оставляет исходный файл и восстановимый draft; UI не сообщает ложный успех.
- Reload восстанавливает только draft нужного source; несовпадение hash явно разобрано.
- Quest сохраняет прежнее поведение вкладки и данных; MedicalAttention viewer и pan/zoom не регрессируют.

### 23.5. Ручная проверка пользователем

Открыть будущий Workshop с тестовой копией config, выбрать GROUP 001 и сверить spawn/route/target с числами файла. Изменить X, затем перетащить другую точку, отменить drag через Escape, проверить Undo/Redo и Y confirmation. Скрыть/показать reference-слой, вернуться в Quest и обратно без потери draft.

Далее сохранить и посмотреть diff: одна ожидаемая координата, остальные settings/группы/activation без изменений. Перезагрузить и проверить значения. На тестовой копии отдельно воспроизвести external-edit conflict, ошибку записи и изменение во время задержанного Save. В этой проверке не запускать группу в DayZ: slice доказывает редакторский цикл, а не navmesh или игровой spawn.

## 24. Какие решения можно принять сейчас

Принять вариант B и сохранение отдельных module editors. Принять один mutable owner на источник, command-based geometry edits, derived projections, stable entity references и отдельные UI/domain states. Принять explicit Save, revision/hash conflict checks и read-only по умолчанию для внешних sources.

Принять Migration existing-point slice первым. Зафиксировать направление activation-only для первого Quest bridge, но не JSON-поле и не поведение runtime при ошибках. Сохранить границу Zones/Medicine. Ввести source/workspace/world identity в foundation без полной multi-server платформы.

Native JS/SVG/PowerShell остаётся baseline; новые зависимости должны доказывать пользу конкретным prototype, не абстрактной «масштабируемостью».

## 25. Какие решения нельзя ещё фиксировать

Не фиксировать окончательные MapFeature/adapter/message API до реализации и тестов двух доменных adapters. Не утверждать canonical Zones JSON, arbitrary geometries, terrain Y semantics или универсальный serializer чужих configs.

Не обещать arbitrary dogs/mutants в Migration, runtime monitoring, exactly-once launch или транзакцию между Quest и Migration files. Нельзя выбрать idempotency scope Quest→Migration без решения о игровом моменте и числе запусков.

Не закреплять количество поддерживаемых SVG features без измерений на целевой машине. Не фиксировать самостоятельное Map-приложение, SharedWorker/backend-owner и concurrent admin editing без соответствующего требования.

## 26. Открытые вопросы

Блокирующие для будущих этапов, но не для аналитического решения:

1. Какой игровой момент Quest вызывает activation и является ли запуск общим для сервера или отдельным для прохождения игрока?
2. Что должно произойти с quest при busy, отсутствующей Migration или chance miss: блокировка, пропуск, deferred retry? Кто владеет persistence этого результата?
3. Достаточно ли manual Y confirmation для редакторского MVP; какой авторитетный источник высот доступен для последующего terrain prototype?
4. Какой минимальный runtime-tested Zones contract утвердит собственная ветка, не Map?
5. Какой конкретный внешний source первым получит write whitelist, и возможно ли доказать его lossless round-trip?
6. Требуется ли только один owner на workspace или действительно несколько администраторов? Последнее изменит архитектуру persistence/session ownership.
7. Какой browser/version и размер второго монитора составляют acceptance environment detached Map?
8. Какие реальные объёмы слоёв следует включить в benchmark и какой допустимый UI budget нужен на машине администратора?

Вывод: отдельная Map полезна, если остаётся пространственным инструментом доменных редакторов. Основной риск не в рисовании маршрута, а в сохранении владения данными при переходе от viewer к editor и от одного окна к двум. Первый implementation slice должен проверять именно это.
