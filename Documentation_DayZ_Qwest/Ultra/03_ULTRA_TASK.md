# ULTRA LAUNCH PAYLOAD — интеграционный аудит ROUTE: ULTRA

## Статус и режим

- Это одноразовый технический payload текущего запуска Ultra, полностью сформированный Codex непосредственно перед вызовом.
- Пользовательский источник задачи: актуальный БЛОК 1 файла `P:\Silver_77_Quests\Documentation_DayZ_Qwest\11_Задача_агенту.md`.
- Режим текущего запуска: `EXECUTOR: ULTRA`.
- Тип работы Ultra: `ANALYSIS ONLY`.
- Ultra не должна изменять repository, документацию, Git, конфигурацию или внешнее состояние. Нужны только независимый аудит и текстовый отчёт.
- Текущий bridge передаёт Ultra только текст этого файла и не предоставляет файловых инструментов. Весь необходимый контекст приведён ниже; открывать файлы по указанным путям Ultra не может и не должна предполагать, что открыла их.

## Цель

Провести независимый архитектурный аудит новой цепочки:

`БЛОК 1 -> Codex -> 03_ULTRA_TASK.md -> gigachat_file_task -> Ultra -> 04_ULTRA_REPORT.md`

Определить, является ли схема внутренне непротиворечивой и пригодной для постоянной работы. Не ограничиваться общей оценкой. Каждый вывод должен называть участвующее правило, объяснять совместимость или конфликт, указывать затронутый сценарий и классифицировать наблюдение как реальную ошибку, потенциальный риск либо допустимое поведение.

## Каноническое разделение ответственности

1. `11_Задача_агенту.md`, БЛОК 1 — единственный пользовательский источник текущей задачи.
2. `Ultra/03_ULTRA_TASK.md` — одноразовый технический launch-payload конкретного вызова, который формирует только Codex.
3. `Ultra/04_ULTRA_REPORT.md` — текстовый результат конкретного вызова Ultra.

Пользователь вручную `03` не поддерживает. Пустой `03` между запусками допустим. Перед каждым вызовом Codex обязан полностью пересобрать файл, не дописывать поверх старого содержимого, не переиспользовать старый payload, проверить существование и непустоту и убедиться, что внутри находится текущая задача без остатков предыдущей.

Попытка вызвать Ultra с пустым или не пересобранным `03` — ошибка. Передавать `11_Задача_агенту.md` напрямую в bridge запрещено.

## Три режима EXECUTOR

### 1. EXECUTOR: CODEX

- Codex читает БЛОК 1 и необходимые правила.
- Codex самостоятельно выполняет содержательную задачу.
- Ultra не запускается.
- `03_ULTRA_TASK.md` не используется.
- `04_ULTRA_REPORT.md` не открывается и не используется.

### 2. EXECUTOR: ULTRA

- Codex является техническим диспетчером.
- Codex читает БЛОК 1 и REQUIRED-документы только в объёме, необходимом для сборки полного payload.
- Это чтение не делает Codex содержательным исполнителем; задачу вместо Ultra он не выполняет.
- Codex полностью формирует новый `03`, включая задачу, обязательные правила, ограничения, входные данные, критерии результата и необходимые сведения.
- Codex не полагается на старое содержимое `03` и проверяет существование и непустоту нового файла.
- Codex вызывает Ultra только через каноническую пару `03 + 04`.
- После завершения прямого вызова Codex не открывает и не читает `04`, не пересказывает и не проверяет выводы Ultra. Результат отдельно проверяет пользовательский цикл.

### 3. EXECUTOR: CODEX + ULTRA

- Codex остаётся основным исполнителем.
- Codex определяет точную отдельную подзадачу для Ultra.
- Codex полностью формирует новый непустой `03` и вызывает ту же каноническую пару `03 + 04`.
- После успешного вызова Codex обязан открыть и прочитать `04`, сопоставить ответ с отправленным payload, проверить полноту и соответствие подзадаче, при необходимости критически проверить выводы и только затем использовать результат.
- Если основная задача предусматривает реальные изменения repository, только Codex может применить проверенный результат в пределах разрешённого scope.

Если поле `EXECUTOR` отсутствует, неизвестно или dispatch-header повреждён, Codex не угадывает режим и не начинает выполнение. При `AUTO-DELEGATION: OFF` Codex самостоятельно не меняет назначенного исполнителя.

## Канонический bridge-контракт

Единственные допустимые аргументы запуска:

- `task_file`: `P:\Silver_77_Quests\Documentation_DayZ_Qwest\Ultra\03_ULTRA_TASK.md`
- `report_file`: `P:\Silver_77_Quests\Documentation_DayZ_Qwest\Ultra\04_ULTRA_REPORT.md`

Оба файла находятся в одной родительской папке `Ultra`, поэтому существующая защита bridge/server по одинаковой родительской папке соблюдается. Изменение `server.py` для этой схемы не требуется.

Bridge предоставляет Ultra текст задачи и принимает текстовый ответ. Поэтому через него Ultra выполняет интеллектуальную и содержательную часть и возвращает анализ, готовый текст, инструкции, diff или patch. Без файловых инструментов bridge это не означает, что Ultra физически изменила repository.

## Актуальные правила routing

- `REQUIRED` означает обязательный источник выбранного маршрута; его нужно прочитать до изменения или вывода.
- `REFERENCE` открывается только при необходимости доказательств или диагностики.
- `NAVIGATION` — карта, не вызывающая рекурсивного чтения.
- `HISTORY` — прошлое решение или исследовательский срез, читаемый адресно.
- Обычная Markdown- или wiki-ссылка не означает автоматического чтения всего графа.
- Для AGENT EXECUTION обязательны текущий БЛОК 1, короткий стартовый документ, явно назначенные документы и обязательные зависимости выбранной операции.
- БЛОК 2, БЛОК 3, TASK_HISTORY, прошлые отчёты, review и планы автоматически не читаются.
- Каноническим владельцем алгоритма трёх режимов и правил чтения `04` является `20_SplitDoc/CONTEXT_ROUTING.md`.
- `12_Старт_агента.md` содержит только короткий указатель на этот routing и не должен дублировать полный dispatcher-алгоритм.
- Предметные документы остаются владельцами предметных правил; маршрутизатор определяет только, кто и когда их читает.

## Актуальные постоянные правила Ultra

Карта ветки Ultra:

`00_Главная -> 01_Старт_Ultra -> 02_Правила_Ultra -> 03_ULTRA_TASK -> 04_ULTRA_REPORT`

- `01_Старт_Ultra.md` и `02_Правила_Ultra.md` содержат постоянный контекст и правила.
- `03` содержит одноразовый payload текущего запуска, сформированный Codex. Пользователь вручную его не поддерживает.
- `04` содержит результат запуска.
- Ultra не запускается автоматически от чтения этих документов.
- Ultra — вспомогательный субагент Codex. Кто читает и проверяет результат после вызова, определяет dispatcher-маршрут, а не сама Ultra.
- Канонический проект: `P:\Silver_77_Quests`.
- Каноническая документация: `P:\Silver_77_Quests\Documentation_DayZ_Qwest`.
- Только payload текущего запуска задаёт работу Ultra. Старое содержимое предыдущего запуска нельзя считать актуальной задачей.
- После постоянных правил Ultra читает лишь боевые документы, необходимые текущей задаче. Для предметных задач нужны актуальные документы соответствующей подсистемы; пять Ultra-файлов их не заменяют.
- Legacy-документы, старые копии, случайные worktree и `D:\GitHub\rabota\Ultra` не являются каноническими источниками.
- Ultra выполняет только текущий launch-payload и соблюдает scope.
- `ANALYSIS ONLY` запрещает любые изменения проекта, документации, Git, конфигурации и внешнего состояния.
- Разрешение на чтение или анализ не является разрешением на правки.
- Соседние проблемы не исправляются; их можно отметить, если они непосредственно влияют на вывод.
- В отчёте нужно отделять подтверждённые факты, документационные требования, результаты проверок, исторические сведения и предположения.
- При конфликте источников нельзя угадывать: нужно описать противоречие и источники.
- Результат записывается только в `04_ULTRA_REPORT.md`.
- Правила Ultra не должны определять, будет ли Codex читать `04`; это ответственность dispatcher.
- При недостатке сведений нужно честно указать ограничение и необходимые проверки, не восстанавливая факты по памяти.

## Что требуется проверить

Проверь всю схему на:

- логические противоречия и циклические правила;
- двух владельцев одного действия;
- риск случайного чтения `04` Codex в режиме `EXECUTOR: ULTRA`;
- риск непрочтения `04` Codex в режиме `EXECUTOR: CODEX + ULTRA`;
- неоднозначность владельца `03`;
- риск ручного обслуживания `03` пользователем;
- риск повторного использования старого payload;
- риск запуска пустого `03`;
- риск прямой передачи документа 11 вместо `03`;
- конфликт между утверждениями «БЛОК 1 — пользовательский источник» и «03 — фактический вход Ultra»;
- противоречия между routing-правилами и постоянными Ultra-документами;
- требования, которые текущий текстовый bridge физически выполнить не может;
- любые логические пути, по которым старая архитектура может вернуться.

Не придумывай проблемы ради заполнения отчёта. Если конкретный участок непротиворечив, скажи это прямо.

## Обязательный формат отчёта

### A. КРАТКОЕ РЕЗЮМЕ АРХИТЕКТУРЫ

Своими словами опиши новую цепочку и разделение трёх слоёв.

### B. ПРОВЕРКА ТРЁХ РЕЖИМОВ

Отдельно для `EXECUTOR: CODEX`, `EXECUTOR: ULTRA` и `EXECUTOR: CODEX + ULTRA` укажи:

- кто читает БЛОК 1;
- кто выполняет содержательную работу;
- используется ли `03`;
- кто и когда создаёт `03`;
- запускается ли Ultra;
- имеет ли Codex право или обязанность читать `04` после вызова.

### C. ПРОВЕРКА 03_ULTRA_TASK.md

Оцени владельца, момент создания, запрет повторного использования, отсутствие ручного обслуживания пользователем и совместимость ролей БЛОКА 1 и `03`.

### D. ПРОВЕРКА 04_ULTRA_REPORT.md

Оцени однозначность правил чтения отчёта, различие режимов ULTRA и CODEX + ULTRA и отсутствие управления Codex из Ultra-документов.

### E. ПРОВЕРКА BRIDGE

Оцени соответствие пары `03 + 04` текущему bridge-контракту, необходимость или отсутствие необходимости менять `server.py` и выполнимость требований при текстовом bridge без файловых инструментов.

### F. НАЙДЕННЫЕ ПРОБЛЕМЫ

Для каждой реальной проблемы укажи:

- источник правила;
- суть;
- затронутый режим;
- серьёзность `CRITICAL`, `IMPORTANT` или `MINOR`;
- минимальную рекомендуемую корректировку.

Если проблем нет в конкретном участке, зафиксируй это без искусственного замечания.

### G. ИТОГ

Чётко перечисли:

- какие части схемы однозначны;
- какие места требуют корректировки, если они есть;
- можно ли использовать схему как постоянный dispatcher-контракт сейчас либо после конкретных исправлений.

## Финальное ограничение

Ничего не изменяй. Не выполняй Git-команды и не предлагай считать repository изменённым. Выполни только независимый анализ приведённого контракта и верни полный текстовый отчёт для записи bridge в `04_ULTRA_REPORT.md`.
