# CONTEXT ROUTING

Каноническая маршрутизация документационного контекста по роли, стадии, операции и предметной области.

## 1. Категории ссылок

- `REQUIRED` — обязательный источник выбранного маршрута; прочитать до изменения или вывода.
- `REFERENCE` — открыть, когда нужны доказательства, детали или диагностика.
- `NAVIGATION` — человеческая карта; не означает автоматического чтения.
- `HISTORY` — прошлое решение, отчёт или исследовательский срез; читать адресно.

Обычная Markdown- или Obsidian wiki-ссылка является навигацией, если документ прямо не обозначен как `REQUIRED`. Нельзя рекурсивно читать весь граф ссылок «на всякий случай».

Все обязательные зависимости выбранного маршрута читаются полностью или в указанном самодостаточном разделе. Повторы дедуплицируются. Произвольный предел глубины ссылок не используется.

## 2. Маршруты по роли и стадии

### TASK PREP

`REQUIRED`: `TASK_PREPARATION_RULES.md` и относящиеся к задаче строки этого маршрутизатора.

ChatGPT выбирает предметные документы, baseline и проверки. Для крупной межмодульной или архитектурной задачи добавляет `30_Единая_система_проекта.md`, а при выборе глобального этапа — `39_Глобальный_план.md`.

### AGENT EXECUTION

`REQUIRED`: текущий БЛОК 1, короткий `12_Старт_агента.md`, явно назначенные документы и обязательные зависимости выбранной операции.

БЛОК 2, БЛОК 3, TASK_HISTORY, прошлые отчёты, review и планы автоматически не читаются.

#### Маршрутизация по EXECUTOR

БЛОК 1 документа `11_Задача_агенту.md` — единственный пользовательский источник текущей задачи. Поле `EXECUTOR` задаёт один из трёх режимов:

- `EXECUTOR: CODEX` — Codex читает БЛОК 1 и необходимые правила, выполняет содержательную задачу самостоятельно, Ultra не запускает и файлы `Ultra/03_ULTRA_TASK.md` и `Ultra/04_ULTRA_REPORT.md` не использует.
- `EXECUTOR: ULTRA` — Codex работает только как технический диспетчер. Он читает БЛОК 1 и `REQUIRED`-документы в объёме, необходимом для сборки полного launch-payload, но не выполняет содержательную задачу вместо Ultra. Непосредственно перед вызовом Codex полностью пересобирает `Ultra/03_ULTRA_TASK.md`, включает в него задачу, обязательные правила, ограничения, входные данные, критерии результата и необходимые пути, затем проверяет существование и непустоту файла. Старое содержимое `03` повторно не используется. Вызов `gigachat_file_task` выполняется только с парой `Ultra/03_ULTRA_TASK.md` + `Ultra/04_ULTRA_REPORT.md`. После прямого вызова Codex не открывает и не читает `04`.
- `EXECUTOR: CODEX + ULTRA` — Codex остаётся основным исполнителем, определяет отдельную подзадачу для Ultra, полностью формирует для неё новый `03`, проверяет его непустоту и вызывает ту же пару `03` + `04`. После успешного вызова Codex обязан прочитать `04`, сопоставить ответ с payload, критически проверить полноту и выводы и только затем использовать результат в своей работе.

Пустой `03_ULTRA_TASK.md` между запусками допустим. Ошибка — попытка вызвать Ultra без предварительной сборки непустого payload. Пользователь не поддерживает `03` вручную, и этот файл не является вторым пользовательским источником задачи.

Канонические аргументы bridge:

- `task_file`: `P:\Silver_77_Quests\Documentation_DayZ_Qwest\Ultra\03_ULTRA_TASK.md`;
- `report_file`: `P:\Silver_77_Quests\Documentation_DayZ_Qwest\Ultra\04_ULTRA_REPORT.md`.

Текущий bridge передаёт Ultra текст задачи и принимает текстовый ответ. Поэтому Ultra возвращает через `04` анализ, готовый текст, инструкции, diff или patch, но не считается физически изменившей repository, если bridge не предоставил ей файловые инструменты.

Если `EXECUTOR` отсутствует, неизвестен или dispatch-header повреждён, режим не угадывать и выполнение не начинать. `AUTO-DELEGATION: OFF` означает, что Codex самостоятельно не меняет назначенного исполнителя.

### REVIEW

`REQUIRED`: `GIT_REVIEW_RULES.md`, исходная TASK и принятые уточнения, AGENT REPORT, exact result SHA/diff и критичные изменённые файлы. Предметные контракты добавляются только для проверки заявленного результата.

### DOCUMENTATION

`REQUIRED` для создания/реорганизации документов, переноса правил и изменения архитектуры: `DOCUMENTATION_RULES.md`, `ENCODING_RULES.md`, изменяемые документы и их прямые входящие ссылки.

Штатная запись AGENT REPORT, одной строки TASK_HISTORY и очистка БЛОКА 1 выполняется по `TASK_LIFECYCLE_RULES.md` и сама по себе не превращает code-задачу в полноценную Documentation TASK.

### ON DEMAND

История, исследования, аварийные протоколы, большие планы и справочники читаются при конкретной необходимости, а не постоянно.

## 3. Тематические маршруты

### DayZ Enforce Script

Любое изменение `.c` / Enforce runtime-кода:

- `REQUIRED`: `DAYZ_ENFORCE_SCRIPT_RULES.md`;
- добавить предметный контракт соответствующей подсистемы;
- `ENCODING_RULES.md` — только при кириллице, неясной кодировке, текстовом восстановлении или прямом назначении.

### Quest data и логика

- Quest JSON, rewards, objectives, NPC Offer/Completion/Reward: `REQUIRED` `QUEST_JSON_CONTRACT.md` и относящиеся к операции самодостаточные разделы `21_Project_Docs/QUEST_LOGIC_SPEC.md`.
- Создание или изменение quest/trigger ID: дополнительно `REQUIRED` `TRIGGER_RULES.md`.
- Не добавлять автоматически UI, Trader, profile и весь Quest-набор, если операция их не затрагивает.

### Quest Editor / JSON_Quvest

- UI или поведение Quest Editor: `REQUIRED` `QUEST_EDITOR_RULES.md`.
- Если меняется структура quest data: дополнительно `QUEST_JSON_CONTRACT.md`.
- Sources/export/profile/runtime config: дополнительно `SERVER_PROFILE_RULES.md`.

### Quest runtime UI и layout

- QuestMenu / QuestJournal / игровой quest UI: `REQUIRED` `QUEST_UI_RULES.md`.
- Изменение данных UI: дополнительно `QUEST_JSON_CONTRACT.md`.
- Геометрия `.layout` или viewer compatibility: дополнительно `DAYZ_LAYOUT_VIEWER_RULES.md`.
- Неверный progress/sync: дополнительно `DAYZ_RPC_SYNC_RULES.md` после диагностики источника данных.

### RPC / client-server sync

`REQUIRED`: `DAYZ_RPC_SYNC_RULES.md` и контракт затронутой подсистемы.

### Server profile / dev JSON / export

`REQUIRED`: `SERVER_PROFILE_RULES.md` и точное описание целевого source/dev/runtime пути. Чтение не разрешает запись в production/server profile.

### Trader

`REQUIRED`: `TRADER_RULES.md`; `SERVER_PROFILE_RULES.md` добавляется при работе с profile/export/runtime target.

### Migration / Web Workshop

Читать актуальные документы и код только для выбранной операции Migration. Не подтягивать автоматически Quest rewards, NPC roles, Trader или всю архитектуру Map. При изменении общего Workshop state/Map дополнительно читать принятые действующие инварианты соответствующего раздела, а не весь исторический корпус без причины.

### Zones / Lighting

Для Zones выбирать актуальный документ состояния/структуры по операции. Для Visual/Lighting `20_Silver_77_Zone_Освещение.md` остаётся обязательным предметным источником.

### Map / Server World / Events

Выбирать `27_Контроль_событий_сервера.md`, `28_Источники_данных_сервера.md` или `29_Карта_мира_сервера.md` по конкретной операции. Не читать все три автоматически.

### Medicine

Для границ и текущего контракта использовать `31_Silver_77_Medicine.md`; аудит, идеи, структура, история и roadmap читаются только по соответствующей операции.

### Изображения и ЛОР

Генерация сюжетной иллюстрации или продолжение серии:

- `REQUIRED`: `IMAGE_GENERATION_PRESET.md`, `IMAGE_SCENE_CONTINUITY.md` и конкретный сюжетный эпизод/ЛОР.

### Encoding

Полный `ENCODING_RULES.md` обязателен при реальном encoding-risk, восстановлении кириллицы, неясной кодировке, документационных файлах с кириллицей и при прямом требовании TASK. Для чистого ASCII-only изменения логики действует минимальная защита из `12_Старт_агента.md` без автоматического чтения аварийного протокола.

### Git / REVIEW

`REQUIRED`: `GIT_REVIEW_RULES.md` только для Git-задач, review, commit/push/history/diff/status или явно разрешённой Git-проверки.

### История

`TASK_HISTORY.md` — `HISTORY`. Искать конкретный TASK ID или решение и читать найденную запись. Полный журнал не является обязательным контекстом обычной задачи.

### Legacy / обратная совместимость

Если задача затрагивает legacy-код или старый контракт, совместимость не считается безусловно вечной: когда она мешает развитию, нужно предложить чистую новую схему, миграцию или отдельное удаление. Самовольно удалять legacy без прямой задачи и allowlist нельзя.

## 4. Правила расширения маршрута

Если в ходе проверки обнаружена реальная зависимость ещё одного контракта, агент дочитывает его и называет причину. Это не разрешает менять дополнительные файлы.

Если обязательный источник отсутствует, архивный одноимённый документ не подставляется молча. Конфликт требования, реализации и результата проверки фиксируется явно.

Предметные документы остаются владельцами предметных правил. Этот маршрутизатор определяет, кто и когда их читает, но не копирует их технические контракты.
