# TASK LIFECYCLE RULES

Канонические правила завершения TASK: AGENT REPORT, TASK_HISTORY, BLOCKED, очистка БЛОКА 1 и сообщение об обновлении модов.

## 1. Когда читать

Документ читается перед завершением implementation/documentation-задачи и когда БЛОК 1 прямо требует обновить рабочий цикл.

`ANALYSIS ONLY` сам по себе не запускает этот lifecycle: без прямого разрешения не записывать отчёт в документ 11, не добавлять историю и не очищать БЛОК 1.

Штатное выполнение lifecycle после code/FIX-задачи не превращает её в полноценную Documentation TASK и не требует автоматического чтения `DOCUMENTATION_RULES.md`.

## 2. Условия успешного завершения

Перед записью результата проверить:

1. основной результат выполнен;
2. разрешённые проверки завершены;
3. нет нерешённой критичной ошибки;
4. фактические изменения соответствуют scope;
5. пользовательские и посторонние изменения не перезаписаны;
6. разрешение задачи включает lifecycle-обновления.

Если результат неполный, задача `BLOCKED` или критичная проверка не пройдена, БЛОК 1 не очищать. В отчёте указать выполненную часть, блокирующую причину и что требуется дальше.

## 3. AGENT REPORT

После успешной задачи записать новый отчёт в `БЛОК 2 — ПОСЛЕДНИЙ ОТЧЁТ АГЕНТА` документа `11_Задача_агенту.md`, заменив предыдущий отчёт, но не изменяя БЛОК 3 без прямого требования.

Базовые разделы:

- `TASK` и `STATUS`;
- `BASELINE`, если он задан или проверен;
- `CREATED FILES`;
- `CHANGED FILES`;
- `DONE` / `MOVED RULES` / `REMOVED DUPLICATION` по типу задачи;
- `CHECKS`;
- `ENCODING CHECK` для текстовых файлов;
- `PROBLEMS` и `QUESTIONS` только для реальных ограничений;
- `CONCLUSION`.

Отделять требования, прочитанные факты, выполненные проверки и пользовательскую runtime-проверку. Не выдавать static check за runtime acceptance.

Git-факты указывать только если они реально проверялись. Агент не пишет финальный `СТАТУС КОММИТА` за ChatGPT reviewer.

## 4. TASK_HISTORY

После успешного завершения добавить в `20_SplitDoc/TASK_HISTORY.md` ровно одну короткую запись текущей TASK:

- основной подтверждённый результат;
- существенные границы и что не менялось;
- обязательная оговорка о runtime/manual проверке, если она осталась;
- без копирования полного БЛОКА 1 или AGENT REPORT.

Для поиска предыдущего решения читать конкретную запись по TASK ID, а не весь журнал автоматически. Исторические записи не переписывать без отдельной задачи.

## 5. Очистка БЛОКА 1

Очищать только после успешной записи отчёта и истории.

В `11_Задача_агенту.md` найти единственный заголовок:

`# БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА`

и следующий служебный разделитель перед:

`# 🟩 БЛОК 2 — ПОСЛЕДНИЙ ОТЧЁТ АГЕНТА`.

Удалить только содержимое завершённой TASK между ними. Заголовки и разделитель не удалять, не переносить и не создавать повторно.

Под заголовком БЛОКА 1 оставить ровно три смысловые строки:

```text
Активной задачи нет.
Предыдущая задача выполнена.
Ожидается новая задача от пользователя.
```

Self-check:

1. активный заголовок БЛОКА 1 существует ровно один раз;
2. номер и текст завершённой TASK внутри БЛОКА 1 отсутствуют;
3. присутствуют три стандартные строки;
4. БЛОК 2 и разделитель сохранены;
5. БЛОК 2 содержит новый отчёт;
6. БЛОК 3 не изменён без разрешения;
7. при `BLOCKED` БЛОК 1 не очищен.

Если маркеры неоднозначны, автоматическую очистку не выполнять: безопаснее остановиться и сообщить проблему.

## 6. Моды, build и runtime

В отчёте явно писать, требуется ли обновление модов.

- Менялись клиентские/shared структуры или клиентские скрипты — указать `Silver_77_Quests_Client`.
- Менялась серверная логика/runtime — указать `Silver_77_Quests_Server`.
- Менялись обе стороны — указать оба мода.
- Менялись только документация, JSON или локальный редактор `JSON_Quvest` — написать: `Моды обновлять не нужно.`

Не выполнять build, packing, deployment или перенос output без прямого разрешения.

## 7. Остановка после отчёта

После AGENT REPORT остановиться и ждать пользователя. Commit/push и независимый review выполняются отдельной стадией по `GIT_REVIEW_RULES.md`; lifecycle не разрешает Git write-команды.
