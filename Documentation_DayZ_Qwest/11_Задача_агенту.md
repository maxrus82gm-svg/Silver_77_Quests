===============================================================================
7. ОБЯЗАТЕЛЬНАЯ ДИАГНОСТИКА TASK 141
===============================================================================

Главная цель текущего runtime-теста — доказать,
что конкретный лежащий/застрявший infected действительно проходит detector.

Когда создаётся новый sample:

`STUCK_SAMPLE_START`

Логировать:

- scenario;
- runtimeGroupId;
- infected ID;
- mode;
- sample world position A;
- sample time;
- configured detection seconds;
- threshold.

Через полный interval:

`STUCK_SAMPLE_CHECK`

Логировать:

- scenario;
- runtimeGroupId;
- infected ID;
- mode;
- position A;
- current position B;
- elapsed seconds;
- horizontal moved distance X/Z;
- threshold;
- result.

Result:

`MOVING`
если `movedDistance >= threshold`.

`STUCK`
если `movedDistance < threshold`.

КРИТИЧНО:

Не менять сам алгоритм TASK 141.

Сейчас он должен оставаться:

A = `GetPosition()`
→ wait 6 sec
→ B = `GetPosition()`
→ `HorizontalDistance(A, B)`
→ `< 2 m` = STUCK
→ `>= 2 m` = MOVING.

===============================================================================
8. SAMPLE RESET DIAGNOSTICS
===============================================================================

Поскольку runtime-проблема может оказаться не в формуле,
а в преждевременном reset sample,
при `stuckDebugLoggingEnabled = 1` добавить диагностическую возможность понять,
ПОЧЕМУ sample был сброшен до завершения 6 sec.

Не обязательно логировать каждый технический reset без причины.

Но для важных переходов желательно видеть:

- `AGGRO`;
- `BUILD_PATH`;
- `ROUTE_POINT_CHANGED`;
- `STUCK_RECOVERY`;
- `HOLD_FREE`;
- death/release;

которые сбрасывают или приостанавливают detector.

Если это можно сделать чисто,
логировать:

`STUCK_SAMPLE_RESET reason=...`

с infected ID и mode.

Главная цель:
если у лежащего infected никогда не появляется `STUCK_SAMPLE_CHECK`,
мы должны увидеть, что именно постоянно сбрасывает его sample.

23. RUNTIME CHECKLIST
===============================================================================

С `loggingEnabled=1`,
`stuckDebugLoggingEnabled=1`:

1. Запустить migration.
2. Убедиться, что появился `$profile:Silver_77_Migrate/Migration.log`.
3. Выбрать конкретный infected ID.
4. Найти `STUCK_SAMPLE_START`.
5. Через ~6 sec найти соответствующий `STUCK_SAMPLE_CHECK`.
6. Проверить A/B и `moved`.
7. Если `<2 m`, получить `STUCK_DETECTED`.
8. Затем:
   `STUCK_RECOVERY_RELEASE`.
9. Затем:
   `STUCK_RECOVERY_STIMULUS_ATTEMPT`.
10. Получить ровно один итог:
   `..._OK`,
   `..._FAILED`
   или `..._SKIPPED`.
11. После recovery увидеть CALM/resume либо WAIT_BUSY.
12. Проверить повторный incident того же infected.
13. Проверить `cause=ROUTE_PROGRESS_LOST`.
14. Выключить `stuckDebugLoggingEnabled=0` и убедиться,
    что SAMPLE spam исчез,
    но важные recovery events сохраняются.
15. Поставить `loggingEnabled=0` и убедиться,
    что обычные INFO logs отключились,
    но ERROR не исчезают.

PERSISTENCE MODEL:
- Расширен существующий roadmap-пункт `Persistence migration infected`; новый дублирующий пункт не создавался.
- Persistent source of truth описан как структура `runtime groups → living members`, относящаяся только к infected, созданным `Silver_77_Migrate`.
- Active и уже `RELEASED` members должны продолжать lifecycle после restart с сохранённой group identity, world position и logical route state.

GROUP / MEMBER IDENTITY:
- Для группы предусмотрены `runtimeGroupId`, `scenarioId` и при необходимости будущий `eventId` плюс данные продолжения event.
- Для living member предусмотрены устойчивый ID внутри группы, class name, saved world position, route progress, offset/target и долгосрочный movement intent.
- Пара `runtimeGroupId + infectedId` должна быть проверена до введения глобального UUID; погибшие members и empty groups не восстанавливаются.

A/B SNAPSHOT MODEL:
- Зафиксированы два чередующихся slot A/B, концептуально `MigrationState_A.json` и `MigrationState_B.json`; точные имена остаются `TBD`.
- Запись идёт `A → B → A → B`; бесконечная история и отдельные файлы на каждого infected не создаются.
- Новый snapshot готовится в inactive/older slot без уничтожения последнего хорошего snapshot.

GENERATION / VALIDATION:
- Snapshot содержит `schemaVersion`, монотонный `generation`, groups и optional diagnostic timestamp.
- Startup проверяет оба slot и выбирает валидный snapshot с максимальным generation.
- Повреждённый newest slot откатывается к предыдущему valid slot; политика двух invalid slot и atomic write semantics остаются `TBD`.

PERIODIC SAVE:
- Interval configurable; около `5 sec` зафиксировано только как runtime-кандидат, а не окончательный default.
- Используется один manager-level cadence и один coherent snapshot всех tracked groups.
- Нагрузку нужно измерить при ориентировочно `100`, `200` и `500` infected; per-infected timers и FileIO в movement loop не предусматриваются.

DEATH PRIORITY:
- Подтверждённая смерть немедленно удаляет member из active in-memory persistent state.
- Death инициирует urgent durable save, не ожидая periodic interval, чтобы погибший не попал в следующий restore.

CRASH-DURING-DEATH RISK:
- Честно зафиксирован риск crash ровно между death и успешным urgent save: previous valid snapshot ещё может считать member живым.
- Для строгого `dead never resurrects` необходимо отдельно исследовать forced A/B save, tombstone/death journal либо другой transaction mechanism; абсолютная гарантия пока не заявляется.

STARTUP RESTORE ORDER:
- Config загружается первым, затем читаются/проверяются A/B, выбирается newest valid generation и восстанавливаются surviving groups/members.
- Manager state и новые paths создаются до разрешения scheduler, `StartEvent(...)`, `StartScenario(...)` и fresh groups.

DUPLICATE SPAWN PREVENTION:
- Restore использует saved `runtimeGroupId`, membership и positions, не создаёт новый event instance и не возвращает members в исходную `spawnPosition`.
- Группа не дополняется до исходного `infectedCount`, погибшие не возвращаются, а восстановленный member не считается новым spawn для counters.

ROUTE STATE RESTORE:
- Heading и runtime navmesh waypoints не сохраняются; после restore manager строит новый path от saved position.
- Transient `AGGRO`, vanilla target, `STUCK_RECOVERY`, cooldowns, samples и watchdog baseline не продолжаются буквально.
- Точное mapping transient modes остаётся `TBD`; `HOLD_FREE`, `RETURN_TO_HOLD` и `RELEASED` должны сохранять долгосрочный lifecycle intent.

PERFORMANCE:
- Один periodic pass формирует один coherent snapshot и одну запись в выбранный A/B slot.
- Death update событийный; обычный snapshot логирует summary, а не каждого member.

SERVER PROFILE:
- Persistence является server-owned runtime state в `$profile:Silver_77_Migrate/...`, отдельно от `$profile:Silver_77_Migrate/MigrationConfig.json`.
- Snapshot не копируется из source/PBO как default и не перезаписывает пользовательский config.
