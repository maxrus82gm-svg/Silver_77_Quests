2. MIGRATION / RETURN_TO_HOLD
===============================================================================

- `RETURN_TO_HOLD`

===============================================================================
3. STUCK_RECOVERY
===============================================================================

`STUCK_RECOVERY` уже находится без наших movement overrides.

Поэтому нельзя получать target/mind каждые 250 ms.

Перестроить flow так, чтобы обработка `STUCK_RECOVERY` происходила ДО общего получения:

- `GetTargetEntity()`
- `GetMindState()`

Внутри `STUCK_RECOVERY`:

1. Пока `now < m_RecoveryFreeUntilTime`:
   - только сохранять vanilla freedom;
   - `GetTargetEntity()` / `GetMindState()` для recovery resume не нужны.

2. После окончания free period:
   - если ещё не наступил `m_NextRecoveryStatusCheckTime`, ничего не проверять.

3. Только когда наступил очередной configured check:
   - получить `GetTargetEntity()`;
   - получить `GetMindState()`.

4. Если busy:
   - оставить vanilla AI;
   - сбросить calm confirmation;
   - назначить следующую проверку примерно через `stuckRecoveryStatusCheckSeconds`.

5. Если CALM + target null:
   - запустить/продолжить protective calm cooldown.

6. Перед фактическим `BuildPath()` / возвратом manager control ОБЯЗАТЕЛЬНО иметь свежую gated проверку состояния.
Нельзя возобновить movement на основании старого CALM, если infected успел снова сагриться.

То есть фактическая частота expensive/logical recovery status checks должна соответствовать configured interval, а не 250 ms.

===============================================================================
4. HOLD_FREE
===============================================================================

`HOLD_FREE` полностью принадлежит vanilla AI и может существовать очень долго.

Его обработку также выполнять ДО общего получения target/mind.

Flow:

1. Если `now < m_NextHoldCheckTime`:
   - сразу return;
   - target/mind не запрашивать.

2. Когда наступил `finalHoldCheckSeconds`:
   - сначала вычислить X/Z distance до `finalTargetCenter`.

3. Если infected всё ещё внутри `finalHoldRadius`:
   - оставить `HOLD_FREE`;
   - target/mind вообще не нужны;
   - следующая проверка через configured hold interval.

4. Только если infected реально находится СНАРУЖИ `finalHoldRadius`:
   - тогда получить свежие target/mind;
   - проверить vanilla busy.

5. Если busy:
   - не возвращать;
   - следующая проверка через `finalHoldCheckSeconds`.

6. Если CALM + target null:
   - использовать существующий protective cooldown.

7. Перед `RETURN_TO_HOLD` состояние должно быть снова подтверждено свежей gated проверкой.
Нельзя начать return, если за время cooldown infected снова получил target/aggression.

Таким образом infected, который часами спокойно находится внутри hold radius, не должен опрашиваться по target/mind каждые 250 ms только ради final hold.

===============================================================================
5. ДОПУСТИМЫЙ РЕФАКТОР
===============================================================================

Разрешается добавить небольшой helper вроде:

`IsVanillaBusy(controller)`

который внутри получает target/mind.

Но важно не само наличие helper, а МЕСТО его вызова.

Helper нельзя безусловно вызывать для всех unit states каждые 250 ms.

Фактическая схема должна стать:

- MIGRATION / RETURN_TO_HOLD -> быстрый vanilla busy check;
- STUCK_RECOVERY -> gated check после free period примерно раз в 3 sec;
- HOLD_FREE inside radius -> вообще без target/mind check;
- HOLD_FREE outside radius -> vanilla check только примерно раз в 5 sec.
