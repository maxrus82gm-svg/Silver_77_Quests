# Глобальный план

Статус: `LIVE / CANONICAL GLOBAL ROADMAP`.

Каноническая архитектурная основа: `Documentation_DayZ_Qwest/38_Интеграция_модов_на_карте.md`.

Завершённые крупные этапы: [[40_Выполненные_задачи_глобального_плана|Выполненные задачи глобального плана]].

## Как используется план

- Здесь находятся только крупные незавершённые этапы, влияющие на развитие общей системы.
- Локальные идеи конкретного мода хранятся в документации этого мода, а его ближайшая цель — в документе «Приоритетная задача».
- Полная история обычных TASK хранится в `Documentation_DayZ_Qwest/20_SplitDoc/TASK_HISTORY.md`.
- Принятый пользователем завершённый глобальный этап удаляется отсюда и переносится в документ 40.
- Новая глобальная ветвь добавляется отдельной документационной задачей или по явному решению пользователя.
- Агент не меняет порядок этапов самостоятельно. Сознательное отступление от текущего плана должно быть явно указано пользователем или ChatGPT либо сначала оформлено обновлением плана.
- Мелкий bugfix, диагностика или техническая необходимость не обязаны становиться глобальным этапом.

Medicine остаётся самостоятельной веткой со своим roadmap и текущим приоритетом. Если её развитие должно войти в общую последовательность, в этот документ добавляется отдельный этап; Medicine не смешивается с Zones.

## Согласованный порядок

### 1. Минимальная Migration + Map

Одна существующая Migration GROUP. Форма и Map работают с одним editor state.

Входят:

- существующие `spawnPosition`, `routePoints` и `targetPosition`;
- изменение X/Z из формы и drag X/Z на Map;
- мгновенная синхронизация без промежуточного Save;
- сохранение старого Y и явное подтверждение высоты после переноса;
- dirty, cancel drag / Escape, undo / redo;
- explicit Save, revision/hash conflict protection и draft/recovery;
- безопасный round-trip существующего `MigrationConfig.json`;
- ключевые Migration radii только как read-only reference geometry;
- MedicalAttention как независимый read-only reference layer.

Не входят terrain-height service, новые GROUP, add/delete/reorder route points, изменение radii, EVENT/ACTIVATION Editor, полный Migration Editor, detached Map, Quest → Migration и runtime launch.

Этот этап — ближайшее implementation-направление и блокирующая проверка общей editor-state архитектуры.

### 2. Полный Migration Editor

После успешного первого slice:

- создание и редактирование GROUP;
- маршруты и add/delete/reorder route points;
- spatial radii editing;
- EVENT и ACTIVATION;
- остальные Migration parameters в обычных формах;
- domain validation и безопасный round-trip.

### 3. Quest + Map

Сначала показать NPC, triggers и роли выбранного quest, добавить Map → Quest navigation и Quest → Map focus. Затем разрешить поддержанные move/radius edits через Quest state.

Objectives, rewards, dialog и equipment не переносятся на canvas.

### 4. Detached Map / второй монитор

После доказанного одноконного edit/save cycle добавить отдельное синхронизированное окно. Основной Workshop остаётся owner состояния и Save, detached Map — mirror/client, а не второй writer.

Проверить закрытие, reload, reconnect и потерю owner. Owner epoch, deduplication и recovery вводятся в необходимом для проверенных failure modes объёме, не задним числом в первый slice.

### 5. Quest → Migration

Первый runtime bridge: Quest → существующая EXTERNAL ACTIVATION. Quest не хранит spawn, route, infectedCount или weather Migration.

Проверить момент запуска, idempotency, повторные запросы, busy, chance miss, disabled/absent Migration и влияние ошибки на quest progression. Автоматическое создание GROUP/EVENT/ACTIVATION из Quest пока не входит.

### 6. Zones + Map

Сначала определить минимальный canonical contract `Silver_77_Zones`, затем подключить его геометрию к Map.

Граница остаётся:

```text
Zones → territory / exposure
Medicine → disease state / stages / symptoms / treatment
```

Внутренняя болезнь не возвращается в Zones.

### 7. Внешние серверные слои

Подключить cache/spawn points, Trader, territories, legacy zones и другие server-profile/reference sources сначала только для чтения.

Write-back разрешается по одному формату после доказанного round-trip, whitelist, validation и conflict protection.

### 8. Общий конструктор сценариев

Только после доказанной работы предыдущих систем объединить workflow создания quest, выбора или создания Migration, назначения зон и связей между системами.

Составной workflow обязан безопасно отменяться, контролировать orphan entities и сохранять зависимости в правильном порядке. Этот уровень не строится раньше базовых редакторов и runtime bridge.

## Правило перехода между этапами

Следующий этап не считается начатым только потому, что предыдущий описан или частично реализован. Переход выполняется после проверки критериев соответствующей implementation TASK и решения пользователя продолжать по плану.
