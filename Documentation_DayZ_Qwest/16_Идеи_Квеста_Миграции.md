# Идеи квеста миграции

## Назначение

Документ является накопительным списком идей, будущих улучшений и требований для системы `Silver_77_Migrate_server`.

Записи ниже не являются описанием уже реализованных функций. У каждой идеи отдельно указан её текущий статус.

## Идея 1. Два режима выбора типов заражённых

Статус:

- `ИДЕЯ`;
- `ТРЕБУЕТ ИССЛЕДОВАНИЯ`;
- `НЕ РЕАЛИЗОВАНО`.

В будущей конфигурации миграции предлагается предусмотреть два режима выбора типов заражённых.

### Режим 0 — автоматический

Условная настройка:

`infectedTypeMode = 0`

Миграционная система должна пытаться использовать типы заражённых, соответствующие vanilla-системе DayZ, Central Economy и infected territory в районе исходной точки миграции. Состав группы должен максимально соответствовать местности, из которой начинается миграция.

Точный способ получения через публичный Enforce API набора infected, соответствующего конкретной CE/infected territory, пока не известен и не подтверждён. Перед реализацией требуется отдельное исследование.

Также необходимо определить fallback для случая, когда точка миграции не относится к подходящей infected territory или публичный API не позволяет надёжно определить её состав.

### Режим 1 — ручной

Условная настройка:

`infectedTypeMode = 1`

Используется список классов из настройки `infectedTypes`. В этом режиме администратор сервера самостоятельно определяет, какие infected могут входить в миграционную группу.

Текущая тестовая система фактически работает по ручному принципу, но отдельное поле `infectedTypeMode` пока не реализовано.

## Идея 2. Дополнительный лут у миграционных заражённых

Статус:

- `ИДЕЯ`;
- `НЕ РЕАЛИЗОВАНО`.

В будущем предлагается предусмотреть специальный дополнительный лут только у заражённых, созданных системой миграции.

Возможные требования:

- каждый migration infected может иметь шанс получить дополнительный предмет;
- вероятность задаётся конфигурацией;
- пример значения `0.5` означает вероятность `50%`;
- одним из вариантов награды могут быть патроны;
- возможный пример — небольшое количество патронов 9 мм россыпью;
- позднее список можно расширить другими типами патронов и предметов.

Цель идеи: игрок, потративший боеприпасы на уничтожение миграционной группы, может получить часть расходников обратно как награду.

Конкретные class names патронов и предметов пока не выбраны. Механика выдачи, вероятность, количество и способ присоединения лута требуют отдельной задачи на проектирование и реализацию.

## Идея 3. Информационное сообщение «Зенит сообщает»

Статус:

- `ИДЕЯ`;
- `ТРЕБУЕТ ИССЛЕДОВАНИЯ`;
- `НЕ РЕАЛИЗОВАНО`.

В будущем предлагается выводить атмосферное игровое сообщение о появлении или обнаружении крупной миграционной группы.

Концепция сообщения:

> Зенит сообщает: возле `<название поселения>` наблюдается большое скопление заражённых, движущееся в направлении `<направление / название поселения>`.

Игроки должны получать предупреждение о движении большой группы заражённых в определённой части карты.

Перед реализацией необходимо определить:

- момент отправки сообщения;
- получателей: всех игроков или только игроков в определённой зоне;
- механизм вывода: UI, notification или chat;
- источник названия ближайшего поселения;
- способ определения направления движения;
- сообщать точную цель или только приблизительное направление;
- нужна ли случайная задержка;
- может ли информация быть приблизительной или неполной.

Код уведомлений в рамках этой идеи пока не создан.

## Масштабирование миграционной группы по игрокам возле точки назначения

Статус:

- `ТРЕБОВАНИЕ`;
- `ПЛАНИРУЕТСЯ К РЕАЛИЗАЦИИ`;
- `НЕ РЕАЛИЗОВАНО`.

Это принятое направление для дальнейшей реализации.

### Основная идея

В сценарии существуют:

- `spawnPosition` — точка появления группы;
- `targetPosition` — точка назначения;
- `infectedCount` — базовое количество infected.

Перед фактическим спавном миграционной группы сервер должен определить, сколько живых реальных игроков находится возле `targetPosition`.

### Зона проверки

Используется логическая круглая зона вокруг `targetPosition`.

Предварительно принятый радиус:

`playerScanRadius = 1000.0`

Физическую collision-сущность создавать не требуется. Проверка должна выполняться серверно и математически по расстоянию между игроком и `targetPosition`.

Для определения расстояния используется только горизонтальная плоскость X/Z. Высота Y не учитывается.

### Какие сущности учитывать

Учитывать только:

- реальные `PlayerBase`;
- живых игроков;
- уникальных игроков;
- игроков внутри `playerScanRadius`.

Не учитывать:

- NPC;
- AI;
- заражённых;
- животных;
- мёртвых игроков.

### Расчёт количества infected

`infectedCount` остаётся базовым количеством миграционной группы.

Каждый найденный игрок, включая первого, добавляет к базовому количеству отдельное случайное число infected. Предварительно принятый диапазон: от `2` до `5` infected на каждого игрока.

Случайный бонус рассчитывается независимо для каждого игрока.

Пример для одного игрока:

- `infectedCount = 10`;
- найден один игрок;
- его случайный бонус может быть `+2`, `+3`, `+4` или `+5`;
- итог: от `12` до `15` infected.

Пример для двух игроков:

- `infectedCount = 10`;
- игрок 1 получает бонус `+2`;
- игрок 2 получает бонус `+5`;
- итог: `17` infected.

При другом запуске независимые бонусы могут составить `+4` и `+3`, что также даст итог `17` infected.

Если игроков нет, дополнительный бонус отсутствует:

- `infectedCount = 10`;
- `playersInTargetRadius = 0`;
- `finalInfectedCount = 10`.

### Момент расчёта

Расчёт производится один раз непосредственно перед созданием конкретной миграционной группы.

После того как `finalInfectedCount` рассчитан и группа создана, её размер больше не меняется из-за:

- входа нового игрока;
- выхода игрока;
- перемещения игрока;
- смерти игрока;
- изменения количества игроков в радиусе.

### Предполагаемые будущие настройки

Рабочие названия параметров:

- `playerScalingEnabled = 1`;
- `playerScanRadius = 1000.0`;
- `infectedBonusPerPlayerMin = 2`;
- `infectedBonusPerPlayerMax = 5`.

Также предусматривается будущая настройка `maxInfectedCount` как защитный верхний предел количества infected для одной миграционной группы.

Названия параметров пока считаются рабочими, а не окончательным JSON-контрактом.

### Формула по смыслу

`finalInfectedCount = infectedCount + случайный бонус первого игрока + случайный бонус второго игрока + ... + случайный бонус каждого следующего игрока`

Каждый отдельный бонус находится в диапазоне:

`infectedBonusPerPlayerMin ... infectedBonusPerPlayerMax`

После суммирования будущая реализация должна применять защитный предел `maxInfectedCount`, если он задан.

### Важно

В рамках этой документационной задачи:

- код не создаётся;
- подсчёт `PlayerBase` не реализуется;
- runtime-конфиг не меняется;
- spawn не меняется;
- formation offset не меняется;
- AI и маршруты не меняются.

Раздел фиксирует только принятое требование для будущей отдельной реализации.

## Независимый жизненный цикл миграционных групп и защита от повторного запуска

Статус:

- `ТРЕБОВАНИЕ`;
- `ПЛАНИРУЕТСЯ К РЕАЛИЗАЦИИ`;
- `НЕ РЕАЛИЗОВАНО`.

Это принятое правило будущей системы миграций.

### Основной принцип

Каждый сценарий миграции должен иметь собственный независимый жизненный цикл.

Условно один JSON-сценарий описывает одну конкретную миграцию:

- свой `scenarioId`;
- свою точку `spawnPosition`;
- свою точку `targetPosition`;
- своё базовое `infectedCount`;
- свои настройки типов infected;
- свои будущие настройки времени и повторения;
- свою созданную миграционную группу.

### Защита от повторного запуска одного сценария

Один и тот же `scenarioId` не должен создавать новую миграционную группу, пока предыдущая группа этого же сценария ещё считается активной.

Если из ранее созданной группы данного сценария существует хотя бы один живой migration infected, повторный запуск этого же сценария блокируется.

Пример:

- `MIGRATION_SCENARIO_001` создал 30 infected;
- 29 infected уничтожены;
- 1 infected остаётся жив;
- `MIGRATION_SCENARIO_001` всё ещё считается активным;
- новую группу `MIGRATION_SCENARIO_001` создавать нельзя.

### Завершение активной группы

Когда в группе конкретного сценария больше не остаётся ни одного живого migration infected, группа считается завершённой.

После этого данный `scenarioId` снова может быть разрешён к последующему запуску согласно своей будущей системе расписания, cooldown или random-событий.

### Важно: сценарии независимы друг от друга

Блокировка действует только внутри одного `scenarioId`.

Например, сценарии:

- `MIGRATION_SCENARIO_001`;
- `MIGRATION_SCENARIO_002`;
- `MIGRATION_SCENARIO_003`

могут иметь активные группы одновременно.

Если группа `MIGRATION_SCENARIO_001` ещё существует, это не должно запрещать запуск `MIGRATION_SCENARIO_002` или `MIGRATION_SCENARIO_003`.

Таким образом, в будущем несколько разных миграционных групп могут одновременно физически находиться на карте.

### Учёт infected конкретной группы

Система должна уметь отличать migration infected, созданных разными сценариями. Каждая группа должна быть связана со своим `scenarioId`.

Общее количество всех infected на сервере для определения активности сценария использовать нельзя.

В расчёт активности сценария входят только те migration infected, которые были созданы именно этим сценарием.

### Предварительная логика состояния

На концептуальном уровне сценарий может иметь состояния:

- `INACTIVE`;
- `ACTIVE`.

`ACTIVE` означает, что хотя бы один созданный этим сценарием migration infected жив.

`INACTIVE` означает, что живых migration infected данного запуска больше нет.

Конкретную структуру классов, массивов и переменных следует определить в отдельной задаче реализации.

### Отдельный вопрос для будущей реализации

Перед реализацией необходимо отдельно определить поведение при рестарте сервера:

- должна ли активная группа переживать рестарт;
- требуется ли persistence состояния сценария;
- или после рестарта предыдущая группа считается завершённой и сценарий начинает новый жизненный цикл.

Пока это остаётся отдельным открытым вопросом. Конкретное решение ещё не принято.

### В рамках текущей задачи

Не реализуются:

- менеджер нескольких сценариев;
- повторные события;
- cooldown;
- persistence;
- сохранение групп;
- удаление infected;
- проверка `IsAlive`;
- новые JSON-поля.

Раздел фиксирует только принятое требование для будущей отдельной реализации.

## Общее правило статуса

Перенос идеи в реализацию выполняется только отдельной задачей после необходимых исследований и согласования конфигурации. До этого все перечисленные возможности считаются не реализованными независимо от полноты их описания в документе.
