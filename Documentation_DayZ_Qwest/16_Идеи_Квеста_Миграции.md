# Roadmap Silver_77_Migrate

Короткий список будущих возможностей server-only migration-мода `Silver_77_Migrate_server`. Порядок пунктов не является приоритетом; подробности оформляются отдельной задачей после выбора направления пользователем.

1. **Persistence migration infected** — active и уже `RELEASED` infected должны переживать restart с устойчивым ID, связью с scenario/runtime group, классом, последней позицией и нужным route/state. Позиции планируется сохранять примерно раз в минуту распределённо, а смерть фиксировать немедленно, чтобы погибший infected не восстановился.

2. **Persistent counters** — учитывать живых infected, созданных только migration-модом: отдельно по runtime group, по `scenarioId` и суммарно, включая `RELEASED` и восстановленных после restart до их смерти.

3. **Configurable limits новых групп** — задавать допустимое число живых migration infected для каждого scenario и при превышении уменьшать либо блокировать новый spawn. Старые и новые группы могут сосуществовать, пока соблюдаются выбранные лимиты.

4. **Cleanup старых migration infected** — добавить настраиваемую очистку по реальному возрасту, малому остатку или проценту группы, а также административное удаление выбранной runtime group. Конкретные сроки и пороги пока не утверждены.

5. **Manual/random scheduler** — запускать события по реальному server/calendar time в ручном или случайном режиме, с JSON-настраиваемым разрешённым окном и количеством событий за цикл. Выбранное расписание и состояние цикла должны храниться отдельно от основного конфига и переживать restart.

6. **Индивидуальные правила route points** — для каждой точки отдельно выбирать stimulus on/off, накопление группы, radius/threshold/strength, продолжение manager control или будущий permanent release именно на этой точке. Допустима точка накопления без AI stimulus.

7. **AI stimulus tuning** — runtime-тестами определить практическую дальность и силу текущих route/final/recovery perception stimuli, при необходимости исследовать другие vanilla presets и реакцию разных infected templates без обещания forced `CHASE`.

8. **Масштабирование группы по игрокам** — один раз перед spawn увеличивать базовый размер группы с учётом живых реальных игроков возле нужной области.

9. **Специальный migration loot** — добавить отдельный настраиваемый шанс предметов и их количества для migration infected, не затрагивая обычных vanilla infected.

10. **Автоматический выбор infected по территории** — подбирать типы infected по CE / infected territory и сохранить ручной `infectedTypes` как полноценный режим.

11. **«Зенит сообщает»** — отправлять игрокам атмосферное сообщение о замеченной миграции, районе её появления и приблизительном направлении движения.

12. **Слышимая атмосфера события** — отдельно от AI-only stimulus рассмотреть слышимые игроку сирены, предупреждения и другие атмосферные звуки.

13. **Weather hold/recovery и tuning** — добавить управляемые фазы transition, удержания мрачной погоды и возврата, а также подобрать overcast/fog/storm по runtime-тестам. Значение overcast около `0.8` остаётся вариантом настройки, а не утверждённым default.

14. **Исследование tint/цвета неба** — проверить, существует ли безопасный vanilla server-side способ менять тон неба или атмосферы без client mod; техническая возможность пока не подтверждена.

15. **Web-редактор MigrationConfig** — создать простой визуальный редактор для scenarios, infected, координат, route points, formation, activation, weather и будущих scheduler/persistence settings.

16. **Quest → World Event / квестовые динамические события** — активный незавершённый квест и подтверждённое условие будущего trigger могут инициировать подготовленный world event / migration scenario по устойчивому идентификатору. Квестовая система только принимает решение о запуске, а отдельная event-система исполняет событие как часть мира; точный JSON/API contract остаётся `TBD`.

### Заметка: Quest → World Event

- **Архитектурная граница** — Quest System проверяет наличие и этап активного незавершённого квеста, trigger-условие и необходимость запуска. World Event / Migration System отвечает за spawn и состав группы, route points, destination, stuck recovery, AI handoff, final hold и дальнейший жизненный цикл; migration AI logic не должна дублироваться внутри Quest System.
- **Возможные условия и сценарии** — будущий trigger может быть связан с геозоной, NPC, предметом, действием или другим quest condition. Событие может начать движение сбоку или позади игрока, пересечь его предполагаемый маршрут, прийти в район раньше или позже него и остаться возле цели, а не обязательно напрямую атаковать игрока.
- **Не только infected** — обобщённый слой World Event в будущем может рассматривать собак, животных и другие AI entities, если это позволит DayZ API и отдельная реализация. Текущий `Silver_77_Migrate` управляет только `DayZInfected` и не имеет подтверждённой поддержки других типов AI.
- **Контракт и защита от повторов** — предпочтительное направление: квест хранит условие запуска и ссылку на стабильный внешний `eventId`, а полный маршрут исполняет event-система. Внутренний `scenarioId` и динамический `runtimeGroupId` не являются квестовым контрактом. Потенциальные настройки trigger coordinates/radius, delay, spawn area, route points, destination, lifetime, repeat/cooldown/one-shot рассматриваются только как будущие потребности; окончательные имена полей, возможность quest-side overrides, глобальный или индивидуальный scope события, несколько runtime groups и проверка существующей группы должны быть определены отдельной задачей.
- **Время и текущая база** — delay, lifetime, cooldown, cleanup, despawn и persistence события пока не утверждены. Реализация TASK 139 даёт концептуальную основу крупного маршрута, stuck recovery, временного vanilla AI и final hold, поэтому будущему quest event потенциально не потребуется множество мелких ручных route points; статус реализации остаётся `IMPLEMENTED / WAITING FOR RUNTIME`.

#### Мост Silver_77_Quests → Silver_77_Migrate / внешняя инициация события

Статус: `АРХИТЕКТУРНОЕ НАПРАВЛЕНИЕ / НЕ РЕАЛИЗОВАНО`.

`Silver_77_Quests` должен только определить, что подтверждённое quest condition выполнено, и один раз запросить запуск подготовленного события. Квестовый мод не должен знать или копировать spawn infected, состав группы, route points, navigation, stuck recovery, Route Progress Watchdog, vanilla AI handoff, final hold либо lifecycle migration group. Всё фактическое исполнение остаётся внутри `Silver_77_Migrate`.

Концептуальная цепочка:

`Quest condition / NPC / item / action → bridge / public entry point → Silver_77_Migrate → поиск event по eventId → запуск подготовленного event/scenario → существующая migration mechanics`.

В `Silver_77_Migrate` планируется небольшая единая server-side facade / public entry point концептуального вида `StartEvent(eventId)` или `S77MigrateAPI.StartEvent(eventId, source)`. Это только направление: точные имя класса, функция, сигнатура, тип результата и dependency contract остаются `TBD`. Внешний источник не должен вызывать внутренние методы `S77MigrateManager` напрямую.

Идентификаторы разделяются по назначению:

- `eventId` — предпочтительный стабильный внешний идентификатор события; именно его в будущем хранят Quest System и другие инициаторы;
- `scenarioId` — внутренний blueprint ID конкретного migration scenario, известный event-системе;
- `runtimeGroupId` — динамический ID уже созданного runtime-экземпляра группы; он никогда не хранится в квесте.

На первом этапе один `eventId` может соответствовать одному `scenarioId`. В дальнейшем один event потенциально сможет запускать несколько scenarios, несколько групп с задержками или другие части world event без изменения Quest JSON, пока внешний `eventId` остаётся стабильным.

Ту же точку входа должны использовать `QUEST`, `ZONE`, `CALENDAR / SCHEDULER`, `RANDOM`, `ADMIN` и другие server-side источники. Scheduler или zone trigger только определяет `eventId` и вызывает entry point; он не спавнит infected и не содержит migration AI logic. Способ инициации не должен менять механику самого события.

Будущая Quest System / Quest Editor сможет связать нужный action или trigger с операцией «Запустить World/Migration Event» и выбранным `eventId`. Точные Quest JSON-поле, UI-контрол, checkbox/dropdown, момент подтверждения action и обработка результата пока `TBD` и в текущую реализацию не входят.

Entry point должен централизованно проверять существование и enabled-состояние event, active instance, repeat/cooldown/one-shot, завершение и лимиты runtime groups. Это особенно важно, когда несколько игроков почти одновременно выполняют одно условие: одинаковый глобальный event не должен размножаться без явно выбранного правила. Multiplayer scope и repeat protection остаются `TBD`. Полезный будущий результат вызова может различать `STARTED`, `ALREADY_ACTIVE`, `NOT_FOUND`, `DISABLED`, `COOLDOWN` и `LIMIT_REACHED`, но точный тип результата не утверждён.

Bridge должен быть событийным: уже сработавшее условие выполняет один вызов entry point. Постоянный polling Migration Manager, scan мира или infected для самого bridge не предусматривается. Для дешёвого поиска в будущем предпочтителен registry/index по `eventId`; постоянной runtime-нагрузки bridge добавлять не должен.

Перед реализацией отдельно исследуется безопасная DayZ-script dependency между `Silver_77_Quests` и public API `Silver_77_Migrate`: прямая server-side dependency, небольшой integration layer или другой контракт. Технический вариант пока не выбран; core Quest System в любом случае не должен получать копию migration logic.
