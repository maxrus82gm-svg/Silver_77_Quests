# Roadmap Silver_77_Migrate

Короткий список будущих возможностей server-only migration-мода `Silver_77_Migrate_server`. Порядок пунктов не является приоритетом; подробности оформляются отдельной задачей после выбора направления пользователем.

1. **Persistence migration infected** — policy принадлежит GROUP. Active и уже `RELEASED` infected persistent runtime-группы должны переживать restart с устойчивым ID, связью с `groupId` / runtime group, классом, последней позицией и нужным route/state. Состояние планируется сохранять одним configurable manager-level snapshot cadence; около `5 sec` рассматривается только как кандидат для runtime-теста. Смерть фиксируется приоритетно, чтобы погибший infected не восстановился.

2. **Persistent counters** — учитывать живых infected, созданных только migration-модом: отдельно по runtime group, по `groupId` и суммарно, включая `RELEASED` и восстановленных после restart до их смерти. Restore существующего persistent member не считается новым spawn и не должен удваивать counters.

3. **Configurable limits новых групп** — задавать допустимое число живых migration infected для каждого `groupId` и при превышении уменьшать либо блокировать новый spawn. Старые и новые runtime-группы могут сосуществовать, пока соблюдаются выбранные лимиты.

4. **Cleanup старых migration infected** — добавить настраиваемую очистку по реальному возрасту, малому остатку или проценту группы, а также административное удаление выбранной runtime group. Конкретные сроки и пороги пока не утверждены.

5. **Activation / Global Event Director** — отдельный activation-layer решает, когда по реальному server/calendar time вызвать выбранный `groupId` или one-shot `eventId`; он не становится свойством migration-группы. Будущий GLOBAL EVENT DIRECTOR периодически проверяет eligible GROUP, независимо разыгрывает их group-level chance и может создать ноль, одну или несколько волн. JSON-настраиваемое окно, количество событий за цикл, restart persistence, online-check и минимальный delay после restart остаются будущей реализацией.

6. **Индивидуальные правила route points** — для каждой точки отдельно выбирать stimulus on/off, накопление группы, radius/threshold/strength, продолжение manager control или будущий permanent release именно на этой точке. Допустима точка накопления без AI stimulus.

7. **AI stimulus tuning** — runtime-тестами определить практическую дальность и силу текущих route/final/recovery perception stimuli, при необходимости исследовать другие vanilla presets и реакцию разных infected templates без обещания forced `CHASE`.

8. **Масштабирование группы по игрокам** — один раз перед spawn увеличивать базовый размер группы с учётом живых реальных игроков возле нужной области.

9. **Специальный migration loot** — добавить отдельный настраиваемый шанс предметов и их количества для migration infected, не затрагивая обычных vanilla infected.

10. **Автоматический выбор infected по территории** — подбирать типы infected по CE / infected territory и сохранить ручной `infectedTypes` как полноценный режим.

11. **«Зенит сообщает»** — отправлять игрокам атмосферное сообщение о замеченной миграции, районе её появления и приблизительном направлении движения.

12. **Слышимая атмосфера события** — отдельно от AI-only stimulus рассмотреть слышимые игроку сирены, предупреждения и другие атмосферные звуки.

13. **Weather hold/recovery и tuning** — добавить управляемые фазы transition, удержания мрачной погоды и возврата, а также подобрать overcast/fog/storm по runtime-тестам. Значение overcast около `0.8` остаётся вариантом настройки, а не утверждённым default.

14. **Исследование tint/цвета неба** — проверить, существует ли безопасный vanilla server-side способ менять тон неба или атмосферы без client mod; техническая возможность пока не подтверждена.

15. **Web-редактор MigrationConfig** — создать визуальный редактор с отдельными разделами `Groups`, `Events`, `Activation / Scheduler` и presets. Техническую очистку координат из полного DayZ clipboard-блока должен выполнять общий parser для всех world-position полей.

16. **Quest → World Event / квестовые динамические события** — Quest System только решает, когда запросить GROUP/PRESET и передаёт разрешённый `LaunchContext`; весь chance roll, spawn, маршрут, AI, persistence и lifecycle исполняет `Silver_77_Migrate`. Точный JSON/API contract остаётся `TBD`.

### Persistence runtime groups / A-B snapshots

Статус: `АРХИТЕКТУРНОЕ ТРЕБОВАНИЕ / НЕ РЕАЛИЗОВАНО`.

#### Persistence model и identity

Persistence охватывает только infected, созданных `Silver_77_Migrate`, и сохраняет структуру `runtime groups → living members`, а не безымянный список координат. Для группы требуется persistent identity, достаточная для связи с исходным событием и blueprint: как минимум `runtimeGroupId`, `groupId` и при необходимости `eventId`. Для живого member нужны устойчивый ID внутри группы, class name, последняя world position, logical route progress, индивидуальный route offset / migration target и долгосрочный movement intent, если без них нельзя корректно продолжить lifecycle.

Решение о persistence относится к GROUP, а не к EVENT или ACTIVATION. Концептуальные режимы `NONE` и `RESTORE` обозначают нужное поведение, но имя поля и окончательный JSON enum остаются `TBD`. Непостоянная patrol/startup GROUP после restart может создать новый runtime-запуск; persistent GROUP должна сначала восстановить сохранённую runtime-группу и только её surviving members, не дополняя состав до исходного `infectedCount`.

Restore не является новой ACTIVATION, новым random roll, запуском scheduler или новым событием для counters. Он сохраняет существующую runtime identity. Для уже созданной persistent GROUP требуется раннее включение в durable state; точная transaction/save-точка между созданием runtime identity, spawn и первой записью остаётся `TBD`.

Persistence должна хранить remaining lifetime либо эквивалентный абсолютный expiry. Restart не выдаёт восстановленным members новый полный `groupLifetimeSeconds`. Это правило распространяется и на `RELEASED` infected, пока они остаются живыми и принадлежат persistent runtime-группе.

Предварительно пару `runtimeGroupId + infectedId` следует проверить как persistent member identity до введения отдельного глобального UUID. Обычные vanilla infected этой системой не сохраняются. Погибшие members в active snapshot не входят; пустая группа после смерти всех members не должна бесконечно оставаться active persistence.

#### A/B snapshot model

Используются ровно два чередующихся основных slot, концептуально `MigrationState_A.json` и `MigrationState_B.json`; точные имена остаются `TBD`. Запись идёт `A → B → A → B`, поэтому система хранит latest и предыдущий snapshot для rollback, но не создаёт бесконечную историю файлов и не пишет отдельный файл для каждого infected.

Каждый snapshot должен содержать metadata как минимум с `schemaVersion`, монотонным `generation` и данными групп; timestamp допустим как дополнительная диагностика. На startup оба slot читаются и структурно проверяются. Выбирается валидный snapshot с наибольшим `generation`, а не просто файл с более новым modification time. Если newest slot оборван, повреждён, не парсится или не проходит validation, система откатывается к предыдущему валидному slot. Если оба invalid, дальнейшая политика запуска остаётся отдельным implementation-решением и не должна молча выдавать повреждённое состояние за пустой корректный snapshot.

Новая запись должна готовиться в inactive/older slot, не уничтожая последний хороший snapshot. Только полностью сформированный и успешно проверенный slot становится latest generation. Возможность temp-file + replace/rename и фактическую atomicity DayZ FileIO необходимо отдельно доказать; TASK 145 её не утверждает.

#### Periodic save и производительность

Save interval должен быть configurable. Значение около `5 sec` рассматривается как runtime-кандидат для небольшой потери position progress при crash, но не является окончательным default до измерений на реальном сервере с ориентировочно `100`, `200` и `500` tracked infected.

Persistence использует один manager-level cadence: один проход по tracked migration state, построение одного coherent snapshot всех runtime groups и одна запись в выбранный A/B slot. Per-infected timers и FileIO внутри movement loop `250 ms` не предусматриваются. Обычный snapshot не должен создавать per-member log spam; достаточно generation, slot, groups/members count и результата операции.

#### Death priority и durability risk

Подтверждённая смерть migration infected немедленно удаляет member из active persistent in-memory state и инициирует срочную durable фиксацию, не ожидая очередного periodic interval. Цель — не восстанавливать погибшего после restart.

Остаётся честно зафиксированный crash edge case: если процесс завершился ровно между death и успешным завершением urgent save, предыдущий валидный A/B snapshot ещё может считать infected живым. Для строгой гарантии `dead never resurrects` будущая реализация должна исследовать immediate forced A/B save, небольшой death tombstone/journal либо другой transaction mechanism. Конкретный механизм пока `TBD`; абсолютная crash-гарантия до его выбора не заявляется.

#### Startup restore order и защита от duplicate spawn

Restore выполняется до разрешения новых events/groups:

1. загрузить `MigrationConfig.json`;
2. прочитать и validate slot A/B;
3. выбрать newest valid generation либо предыдущий valid fallback;
4. восстановить surviving runtime groups и только их живых members на saved world positions;
5. создать manager state и заново построить paths;
6. только затем разрешить scheduler, `StartEvent(...)`, `StartGroup(...)` и fresh groups.

`RestoreRuntimeGroup(...)` концептуально отличается от нового event: использует сохранённый `runtimeGroupId`, membership и positions, не создаёт новый runtime instance, не возвращает группу в исходную `spawnPosition`, не дополняет её до configured `infectedCount` и не восстанавливает погибших members. Изменение GROUP config между restart не должно молча вызывать повторный spawn; точный набор blueprint-данных, необходимый старой живой группе для продолжения, остаётся `TBD`.

#### Route state restore

Heading и runtime navmesh waypoints сохранять не требуется: это производные runtime-данные. После restore infected создаётся возле saved world position, получает сохранённый logical route progress / intent, а manager вызывает новый `BuildPath()` от актуальной позиции.

Transient `AGGRO`, vanilla target, `STUCK_RECOVERY`, cooldown timers, stuck sample и Route Progress Watchdog baseline нельзя буквально продолжать со старыми значениями. Они инициализируются заново, а transient mode переводится в безопасный долгосрочный intent; точное mapping остаётся `TBD`. `HOLD_FREE`, `RETURN_TO_HOLD` и уже `RELEASED` infected необходимо учитывать отдельно, чтобы дошедший до final area member после restart не начинал миграцию сначала.

#### Server profile и диагностика

Snapshots являются server-owned runtime state и хранятся отдельно в `$profile:Silver_77_Migrate/...`. Они не являются пользовательским `MigrationConfig.json`, не копируются из source/PBO как defaults и не должны перезаписывать config. В будущих логах нужны результаты load A/B и validation, выбранные slot/generation, fallback, save success/failure, counts восстановленных groups/members, удаление death из persistence и failure urgent save.

Точный JSON schema, имена файлов, validation contract, state mapping, обработка двух invalid slot, atomic write strategy и tombstone/journal остаются отдельной implementation-задачей.

### Архитектура GROUP / EVENT / ACTIVATION

Статус: `БАЗОВЫЙ RUNTIME-ФУНДАМЕНТ РЕАЛИЗОВАН В TASK 154 / РАСШИРЕНИЯ В ROADMAP`.

Базовая модель разделяет три независимых вопроса:

- `GROUP` — что существует и как себя ведёт;
- `EVENT` — какие группы запускаются вместе;
- `ACTIVATION` — почему и когда выполняется запуск.

Расширенная модель добавляет ещё три самостоятельных понятия:

- `Persistence` — должна ли конкретная GROUP и её runtime members переживать restart;
- `PRESET` — переиспользуемые defaults состава и поведения без обязательной привязки к мировому маршруту;
- `LaunchContext` — разрешённые значения и overrides только для одной попытки запуска.

Эти уровни не подменяют друг друга: GROUP остаётся полным world blueprint, EVENT не становится scheduler, ACTIVATION не хранит AI-механику, PRESET не является размещённой группой, LaunchContext не изменяет canonical config, а Persistence не считается новым запуском.

Canonical JSON schema TASK 154 использует `groups`, `events` и `activations`. Реализованы STARTUP/EXTERNAL activation, dispatcher, `bool`-результат public facade и совместимость старого `scenarios[]/scenarioId` без перезаписи runtime profile. Расширенный result contract, cooldown/limits/persistence и дополнительные activation-типы остаются будущими задачами.

#### GROUP

Migration group является обычным независимым blueprint с устойчивым уникальным `groupId`, понятным человеку названием/описанием и собственными параметрами infected, `spawnPosition`, `routePoints`, destination/`targetPosition`, lifetime, formation, stuck recovery, final hold, weather/effects и другими свойствами самой группы.

Группа не знает, почему и каким способом её запустили. Не вводятся отдельные типы вроде random-group, quest-group или timed-group. Один `groupId` в будущем может быть запущен вручную, scheduler/random-механизмом, по времени, квесту, trigger/zone или как часть другого world event без копирования blueprint.

Текущие stable ID `MIGRATION_TEST_001` и `MIGRATION_TEST_002` сохранены как `groupId`. У каждой GROUP появилось отдельное информационное `name`, которое не участвует в lookup. Для legacy runtime `scenarioId` служит in-memory fallback `groupId`; файл profile не переписывается.

GROUP всегда остаётся универсальной. Запрещено размножать blueprint-типы `quest group`, `random group`, `startup group`, `global group` или `patrol group`: способ запуска задаётся ACTIVATION, принадлежность к мировому запуску — EVENT, а циклическое движение — route-настройками самой GROUP.

#### Group-level persistence и chance

Политика persistence принадлежит GROUP. EVENT или ACTIVATION могут запускать persistent и non-persistent GROUP вместе, но не меняют смысл их восстановления. Restore existing runtime group выполняется до fresh activations и не считается новым spawn, chance attempt или scheduler event.

Базовая вероятность появления также принадлежит GROUP; рабочее понятие — `spawnChancePercent`, окончательное имя поля остаётся `TBD`. Нужны дробные значения вроде `0.5`, а также обычные `5`, `30` и `80` процентов. Это вероятность на одну попытку/check, поэтому фактическая частота зависит ещё и от интервала проверок, который пока не утверждён.

Если внешний источник передал chance override через LaunchContext, приоритет имеет значение текущего request; иначе используется GROUP/PRESET default. `Silver_77_Migrate` валидирует диапазон, выполняет random roll и логирует результат. Override никогда не записывается обратно в GROUP/PRESET и не меняет последующие запуски.

#### Loop / patrol route

Для GROUP требуется будущий циклический маршрут произвольной длины: например `A → B → C → A`. Концептуальные варианты `ONCE / LOOP` или отдельный loop-флаг допустимы, но окончательное имя JSON-поля остаётся `TBD`. Взаимодействие loop-маршрута с `targetPosition`, final activation и hold требует отдельного решения и в TASK 155 не утверждается.

#### EVENT

Event имеет устойчивый `eventId` и содержит список `groupId`. Он объединяет несколько групп в один логический мировой запуск и позволяет внешней системе вызвать их одной командой, не перечисляя все группы при каждом запросе.

Пример по смыслу:

`EVENT_GLOBAL_MIGRATION → MIGRATION_TEST_001 + MIGRATION_TEST_002`.

Manager поддерживает запуск одной `GROUP` по `groupId` и `EVENT` по `eventId`. EVENT сначала разрешает все ссылки и отклоняется целиком при неизвестном `groupId`; существующие disabled GROUP пропускаются явно. Текущий event запускает runnable-группы одним batch после общей delay/weather preparation. Сложные правила порядка, индивидуальные задержки и rollback после фактической ошибки spawn остаются будущими вопросами.

Обычный one-shot EVENT сохраняется для quest, trigger, admin и других единичных запусков. Он не смешивается с будущим `GLOBAL EVENT DIRECTOR` — долгоживущим orchestrator, который через настраиваемые интервалы проверяет набор `groupId`, оценивает eligibility и независимо выполняет group-level chance roll. Один director-check может выбрать ноль, одну, несколько или все подходящие GROUP.

GROUP должна считаться eligible с учётом уже существующих runtime instances и живых tracked members, чтобы director не создавал бесконечные дубли одной живой группы. Точные лимиты, cooldown, thresholds и правила повторного допуска остаются `TBD`; фраза «через час» может быть только примером настройки, но не default.

Само существование director не меняет погоду. Общий weather transition разрешён только если текущий check действительно выбрал хотя бы одну GROUP, которая запрашивает weather, и root `weatherEnabled` это допускает. Если не выбрана ни одна GROUP, погодного события нет. DayZ weather остаётся глобальной для всех одновременно присутствующих групп.

One-shot EVENT и GLOBAL EVENT DIRECTOR должны сосуществовать. Окончательные `mode`/schema director, cadence, restart state и result model остаются будущей implementation-задачей.

#### ACTIVATION

Activation отвечает только на вопрос: почему и когда нужно запустить выбранный `groupId` или `eventId`. В TASK 154 реализованы типы `STARTUP` и `EXTERNAL`: первый автоматически проходит через dispatcher при инициализации, второй сам ничего не делает и ждёт public API. Источники `RANDOM`, `SCHEDULE`, `QUEST`, `TRIGGER / ZONE`, `ADMIN / MANUAL` остаются будущими server-side инициаторами поверх этого фундамента.

Random и scheduler являются собственной логикой migration-мода поверх Group/Event, а не свойствами группы. Недельные лимиты, allowed time window, online-check, restart persistence, minimum delay после restart и правила внеочередного quest-запуска остаются отдельной implementation-задачей; конкретные значения вроде количества запусков в неделю сейчас не утверждаются.

В будущем несколько enabled `STARTUP` activations должны выполняться надёжно: последовательно, объединённым batch либо через другую доказанную очередь. Текущий временный `LAUNCH_BUSY` TASK 154 не должен приводить к молчаливой потере второй и последующих startup-заявок. Конкретный механизм очереди/aggregation остаётся `TBD`.

#### Единая server-side точка входа и identity

Внешние системы не должны знать внутреннюю реализацию blueprint или вызывать внутренние методы `S77MigrateManager` напрямую. Реализована facade `S77MigrateAPI` с операциями:

- `Activate(activationId)`;
- `StartGroup(groupId)`;
- `StartEvent(eventId)`.

Операции возвращают простой `bool`: принят ли request для подготовки. Детальная причина (`NOT_FOUND`, `DISABLED`, invalid target, no runnable groups или `LAUNCH_BUSY`) записывается в server log. После запроса `Silver_77_Migrate` самостоятельно отвечает за spawn, маршруты, AI handoff, recovery, hold, weather и lifecycle.

Entry point централизованно проверяет существование и enabled-состояние GROUP/EVENT/ACTIVATION, ссылки и временный preparation busy. Очереди пока нет: во время delay/weather новый request возвращает `false`, а после завершения preparation снова разрешён. Живые runtime-группы сами по себе не блокируют повторный запуск. Repeat/cooldown/one-shot, завершение, limits и расширенный enum/result contract остаются будущими задачами.

Идентификаторы разделяются строго:

- `groupId` — устойчивый ID blueprint группы;
- `eventId` — устойчивый ID логического события со списком групп;
- `runtimeGroupId` — динамическая identity конкретного уже созданного запуска; никогда не хранится как внешний ID в квесте, scheduler или Web-редакторе.

#### PRESET

PRESET — будущий переиспользуемый шаблон состава и behavior defaults: типы сущностей, количество, lifetime и допустимые базовые настройки поведения. Он не обязан содержать `spawnPosition`, `targetPosition` или `routePoints` и сам по себе не обозначает размещённую в мире GROUP.

GROUP остаётся полноценным world blueprint с координатами и маршрутом. PRESET вместе с LaunchContext может создать динамическую runtime-группу для квестового encounter. Должна ли canonical GROUP ссылаться на PRESET либо копировать его значения, а также окончательное имя `GroupPreset` / `EncounterPreset` остаются `TBD`.

#### LaunchContext и whitelist overrides

LaunchContext — данные одного запроса, а не ещё один config blueprint. Он может выбрать GROUP или PRESET и передать разрешённые overrides. Предварительный whitelist:

- chance текущей попытки;
- `spawnPosition`;
- `targetPosition`;
- `routePoints`;
- lifetime.

Count либо multiplier могут быть добавлены после отдельного решения. Произвольная передача внутренних stuck/recovery/manager/persistence параметров запрещена: внешний мод не должен собирать `S77MigrateManager` из низкоуровневых переключателей.

Приоритет разрешения значений:

`LaunchContext override → GROUP/PRESET default → reject, если обязательное значение отсутствует`.

LaunchContext не изменяет source `MigrationConfig.json`, runtime profile, GROUP или PRESET. Точный класс, JSON/API signature, validation errors и result contract остаются `TBD`.

#### Quest → World Event / Migration

`Silver_77_Quests` проверяет активный незавершённый квест, этап и подтверждённое quest condition, выбирает GROUP/PRESET, формирует только разрешённый LaunchContext и один раз отправляет запрос. Квестовый мод отвечает за quest progress, success/fail conditions и requested chance/coordinates, но не копирует spawn infected, navigation, stuck recovery, Route Progress Watchdog, vanilla AI handoff, final hold или lifecycle.

`Silver_77_Migrate` проверяет допустимость запроса и данных, выполняет random roll, создаёт runtime identity и полностью отвечает за фактический spawn, AI, route, aggro handoff, recovery, lifetime, persistence, lifecycle, cleanup и технический результат. Migration-мод не должен знать сюжетную логику конкретного квеста.

Будущее quest condition может быть связано с геозоной, NPC, предметом, действием или другим trigger. Событие может прийти сбоку или позади игрока, пересечь его предполагаемый маршрут, прибыть раньше или позже и остаться возле цели, а не обязательно напрямую атаковать игрока. Trigger coordinates/radius, delay, quest-side overrides, global/individual scope и repeat rules остаются `TBD`.

Концептуальная цепочка:

`Quest condition / NPC / item / action → public entry point + LaunchContext → Silver_77_Migrate → GROUP / PRESET / EVENT → существующая migration mechanics`.

Ту же точку входа в будущем используют Quest, Zone, Scheduler, Random и Admin. Bridge остаётся событийным и не добавляет polling, scan мира или постоянную нагрузку. Quest JSON/UI, dependency между модами, repeat protection, multiplayer scope, cooldown/one-shot и обработка результата остаются `TBD`.

Перед реализацией отдельно исследуется безопасная DayZ-script dependency между `Silver_77_Quests` и public API `Silver_77_Migrate`: прямая server-side dependency, небольшой integration layer или другой контракт. Обобщённый World Event layer позднее может исследовать собак, животных и другие AI entities, если это позволит DayZ API; текущий `Silver_77_Migrate` подтверждён только для `DayZInfected`.

#### Multiplayer shared encounter — TBD

Если несколько игроков с одним Quest входят в одну encounter-zone, нельзя без проверки создавать для каждого независимую одинаковую пачку AI. Возможное направление — shared encounter identity для пары Quest + zone/objective: первый подходящий participant создаёт encounter, следующие присоединяются к нему, а количество AI при необходимости масштабируется от participants.

Точная формула scaling не утверждается. Отдельно должны быть решены combat/objective zone, выход и fail condition, частичное уничтожение группы, повторный вход и защита от ошибочного duplicate spawn. Это будущая Quest/Encounter implementation-задача, а не часть TASK 155.

#### Web-редактор MigrationConfig

`MigrationConfig.json` остаётся техническим форматом. Будущий визуальный Web-интерфейс логически разделяется на `Groups`, `Events`, `Activation / Scheduler` и `Presets`. Quest Web-редактор должен позволять выбрать GROUP/PRESET и задать только разрешённые LaunchContext-поля: requested chance, координаты, route и lifetime override. Подробный UI и точный contract пока не проектируются.

Для всех world-position полей должен использоваться один общий parser. Основной пользовательский ввод — полный clipboard-блок DayZ без ручного удаления служебных строк:

```text
Position: <13055.417969, 117.316383, 13108.957031>
Orientation: <87.821983, 0.000000, -0.000000>
Config-Type: SurvivorM_Rolf
```

Поле координат должно принимать весь блок одной вставкой. Пользователь не удаляет вручную подпись `Position`, угловые скобки, `Orientation` или `Config-Type`.

Parser должен найти строку `Position`, извлечь ровно три координаты `X/Y/Z`, проигнорировать `Orientation` и `Config-Type` и преобразовать результат во внутренний формат редактора/JSON. Один и тот же parser используется минимум для `spawnPosition`, `targetPosition`, `routePoints`, будущих trigger/zone coordinates и других world-position полей.

Дополнительно желательно принимать прямой ввод только трёх координат. Если корректная строка `Position` не найдена либо координат не три, редактор не угадывает значения, показывает ошибку и не сохраняет повреждённые координаты.

Parser и Web UI в TASK 152 не реализованы. Это требование к будущей отдельной задаче.
