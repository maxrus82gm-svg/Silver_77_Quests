# AGENT TASK LOOP

Файл для управления задачами агента.

Главная идея:
- ChatGPT ставит задачу
- пользователь вставляет задачу в этот файл
- агент читает задачу
- агент возвращает отчёт в чат
- пользователь присылает отчёт ChatGPT
- ChatGPT даёт проверку и следующую задачу
- пользователь вручную обновляет этот файл

БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА

TASK 065 FIX 5 — Исправить DayZ layout viewer: нормальный stack-парсер вложенных виджетов

Контекст:
Предыдущая версия стала ближе к цели:

- неправильный формат position[] / size[] / color[] убран
- теперь распознаётся правильный формат:

Но результат всё ещё не принят.

Главная проблема:
Парсер использует один currentElement / inElement.
Для DayZ .layout это неправильно, потому что layout — вложенное дерево виджетов.

Пример:

PanelWidgetClass QuestPanel {
 position 0 0
 size 920 560
 {
  TextListboxWidgetClass QuestListbox {
   position 30 82
   size 330 250
  }

  ButtonWidgetClass AcceptButton {
   position 390 420
   size 220 48
   {
    TextWidgetClass AcceptButtonText {
     position 0 0
     size 1 1
     text "ВЗЯТЬ КВЕСТ"
    }
   }
  }
 }
}

Почему currentElement ломается:
1. Когда найден QuestPanel, currentElement = QuestPanel.
2. Потом найден QuestListbox, currentElement перезаписывается на QuestListbox.
3. QuestPanel теряется как текущий родитель.
4. Потом найден AcceptButton, currentElement снова перезаписывается.
5. Потом AcceptButtonText перезаписывает AcceptButton.
6. Вложенность и parent-child связи теряются.
7. Невозможно правильно посчитать absolute position:
   child.absoluteX = parent.absoluteX + child.position.x

Правильное решение:
Нужен stack nodes, а не один currentElement.

Принцип:
- stack хранит текущий путь вложенности.
- Последний элемент stack — текущий активный виджет.
- Новый виджет становится child текущего верхнего элемента stack.
- При закрывающей скобке } верхний элемент stack закрывается через pop.
- Свойства position/size/color/text/font пишутся в верхний элемент stack.

2. Реализовать нормальный parseLayout(text):

Псевдокод:

function parseLayout(text) {
    const lines = text.split(/\r?\n/);
    const nodes = [];
    const stack = [];
    let nextId = 1;

    for each rawLine in lines:
        line = rawLine.trim();

        if line == "" continue;
        if line.startsWith("//") continue;

        if line == "{" continue;

        if line == "}":
            if stack.length > 0:
                stack.pop();
            continue;

        widgetMatch = line.match(/^([A-Za-z0-9_]+WidgetClass)\s+([A-Za-z0-9_]+)\s*\{$/);

        if widgetMatch:
            parent = stack.length > 0 ? stack[stack.length - 1] : null;

            node = {
                id: nextId++,
                type: widgetMatch[1],
                name: widgetMatch[2],
                parentId: parent ? parent.id : null,
                parentName: parent ? parent.name : "",
                children: [],
                position: null,
                size: null,
                color: null,
                text: "",
                font: "",
                props: {},
                absX: 0,
                absY: 0
            };

            if parent:
                parent.children.push(node);

            nodes.push(node);
            stack.push(node);
            continue;

        if stack.length == 0:
            continue;

        current = stack[stack.length - 1];

        parse property line into current.

    computeAbsolutePositions(nodes);
    return nodes;
}

5. computeAbsolutePositions(nodes):

Для каждого node в порядке nodes:
- localX = node.position ? node.position.x : 0
- localY = node.position ? node.position.y : 0
- parent = найти по parentId
- если parent есть:
  node.absX = parent.absX + localX
  node.absY = parent.absY + localY
- если parent нет:
  node.absX = localX
  node.absY = localY

Reason: !!! String CORRUPTED - FIX OnStoreLoad() !!!
Silver_77_Quests/scripts/4_World/questclientrpc.c:70 Function OnRPC

Сервер при этом корректно:
- получал quest progress request RPC;
- загружал player progress из JSON;
- видел реальные статусы active/completed;
- сериализовал PlayerQuestData;
- отправлял payload клиенту.

Проблема:
Player data JSON отправлялся одной строкой через RPC.
Для DayZ/Enforce такой способ оказался ненадёжным: строка повреждалась при передаче/чтении RPC.

Решение:
Player data sync переведён на chunked sync по аналогии с config sync.

Итоговая архитектура:
- сервер режет player data payload на chunks;
- каждый chunk отправляется через Param3<int,int,string>;
- клиент читает ctx прямо в OnRPC case;
- клиент собирает chunks в отдельный player data buffer;
- после сборки полного payload вызывает Silver77_HandleQuestPlayerDataPayload(payload);
- ParamsReadContext не передаётся в helper-функции.

Проверка в игре:
- ошибка String CORRUPTED больше не проявляется;
- UI начал получать реальные статусы квестов;
- вместо повторного “ВЗЯТЬ КВЕСТ” отображается корректное состояние “УЖЕ АКТИВЕН”.

Вывод:
TASK 064 успешно решил проблему client-server sync.
Полученный опыт нужно закрепить в правилах агента: любые JSON/string payload для DayZ RPC передавать чанками, а не одной строкой.

# 🟫 БЛОК 4.2 — DAYZ CLIENT-SERVER RPC И СИНХРОНИЗАЦИЯ
================================================================================

Этот блок обязателен для задач, связанных с:

- DayZ RPC
- client/server sync
- PlayerBase.OnRPC
- ParamsReadContext
- RPCSingleParam
- Param1 / Param2 / Param3 / Param4
- JSON payload
- config sync
- player data sync
- quest progress sync
- UI, который зависит от server data

--------------------------------------------------------------------------------
ГЛАВНОЕ ПРАВИЛО:
--------------------------------------------------------------------------------

Не отправлять JSON, progress, config, dialog data или другой длинный string payload одной строкой через RPC.

Для DayZ/Enforce это ненадёжно.

Возможная ошибка клиента:

Reason: !!! String CORRUPTED - FIX OnStoreLoad() !!!

Если такая ошибка появилась при ctx.Read string payload — не искать первопричину в UI.
Сначала проверить транспорт RPC и перевести передачу payload на chunked sync.

--------------------------------------------------------------------------------
ПРАВИЛО CHUNKED SYNC:
--------------------------------------------------------------------------------

Любые крупные или потенциально сложные данные передавать чанками.

Рекомендуемый формат:

Param3<int, int, string>

param1 = chunkIndex
param2 = totalChunks
param3 = chunkPayload

Рекомендуемый размер чанка:
- 512 байт
- либо уже существующая константа проекта для chunk sync

--------------------------------------------------------------------------------
ОТДЕЛЬНЫЕ BUFFER ДЛЯ РАЗНЫХ ТИПОВ ДАННЫХ:
--------------------------------------------------------------------------------

Для каждого типа payload должен быть отдельный buffer.

Правильно:
- config chunks отдельно
- player data chunks отдельно
- dialog data chunks отдельно
- future inventory/snapshot chunks отдельно

Неправильно:
- складывать config и player data в один общий map buffer
- переиспользовать один expectedChunkCount для разных RPC payload
- собирать разные payload-типы в одной функции без явного разделения

--------------------------------------------------------------------------------
ПРАВИЛО ParamsReadContext:
--------------------------------------------------------------------------------

ctx.Read выполнять прямо внутри соответствующего case в OnRPC.

Не передавать ParamsReadContext в helper-функции.

Правильно:

case SILVER77_QUEST_RPC_PLAYER_DATA:
{
    Param3<int, int, string> data = new Param3<int, int, string>(0, 0, "");
    if (!ctx.Read(data))
    {
        Print("[Silver_77_Quests][CLIENT_PROGRESS_DEBUG] ERROR: ctx.Read failed");
        return;
    }

    string payload = Silver77_StorePlayerDataSyncChunk(data.param1, data.param2, data.param3);
    if (payload == "")
        return;

    Silver77_HandleQuestPlayerDataPayload(payload);
    return;
}

Неправильно:

case SILVER77_QUEST_RPC_PLAYER_DATA:
    Silver77_HandleQuestPlayerData(ctx);
    return;

private void Silver77_HandleQuestPlayerData(ParamsReadContext ctx)
{
    ctx.Read(...);
}

Helper-функции должны получать обычные значения:
- string payload
- int chunkIndex
- int totalChunks
- PlayerQuestData
- Silver77_QuestConfig

--------------------------------------------------------------------------------
ДИАГНОСТИКА RPC ПО ЦЕПОЧКЕ:
--------------------------------------------------------------------------------

При проблемах client-server sync проверять строго по этапам.

1. Клиент отправил request?
Искать client log:
- Sending ... request RPC

2. Сервер получил request?
Искать server RPT:
- Received ... request RPC

3. Сервер загрузил реальные данные?
Искать server RPT:
- LoadPlayerData
- FileExist=true
- progressCount
- questId/status

4. Сервер подготовил payload?
Искать:
- payloadLength
- Serialize...

5. Сервер отправил response?
Искать:
- Sent ... to client
- Sent ... in X chunks

6. Клиент получил chunks?
Искать client RPT:
- Received ... chunk 1/X
- Received ... chunk X/X

7. Клиент собрал payload?
Искать:
- Reassembled ... payload
- SUCCESS: Reassembled ...

8. Клиент десериализовал payload?
Искать:
- JsonSerializer.ReadFromString succeeded
- PlayerQuestData deserialized successfully

9. Клиент применил данные?
Искать:
- ApplySyncedPlayerData
- ApplySyncedPlayerData completed

10. UI обновился после apply?
Искать:
- реальные status active/completed
- кнопки “УЖЕ АКТИВЕН”, “СДАТЬ КВЕСТ”, “НАГРАДА”
- отсутствие ложного available

--------------------------------------------------------------------------------
ЕСЛИ КЛИЕНТ ПАДАЕТ В ctx.Read:
--------------------------------------------------------------------------------

Сначала проверить:

1. Совпадает ли RPC ID на сервере и клиенте.
2. Совпадает ли Param-тип на сервере и клиенте.
3. Не читает ли super.OnRPC или другой обработчик ctx раньше нашего case.
4. Не передаётся ли ParamsReadContext в helper.
5. Не отправляется ли длинная string одной строкой.
6. Нет ли в логе:
   Reason: !!! String CORRUPTED - FIX OnStoreLoad() !!!

Если есть String CORRUPTED:
- не начинать с UI
- не начинать с JSON-логики квестов
- не начинать с HasSyncedPlayerData
- не начинать с кнопок
- сначала перевести payload на chunked sync

--------------------------------------------------------------------------------
SERVER IS SOURCE OF TRUTH:
--------------------------------------------------------------------------------

Сервер является источником правды.

Сервер:
- хранит progress
- загружает progress из profile JSON
- меняет quest status
- выдаёт rewards
- сохраняет player data
- отправляет sync клиенту

Клиент:
- запрашивает config/player data
- получает sync
- отображает UI
- не должен считать default available реальным progress
- не должен решать server-side outcome самостоятельно

--------------------------------------------------------------------------------
UI НЕ ДОЛЖЕН МАСКИРОВАТЬ ПРОБЛЕМЫ SYNC:
--------------------------------------------------------------------------------

Если HasSyncedPlayerData == false:
- UI может показывать loading
- UI не должен отображать окончательные статусы
- UI не должен активировать кнопки на основе default available
- UI не должен создавать впечатление, что квест реально available, если server sync ещё не получен

Функции типа EnsurePlayerProgress/GetQuestStatus не должны подменять отсутствие server sync настоящим progress.

Default available допустим только как временная заглушка, но не как источник истины.

--------------------------------------------------------------------------------
МИНИМАЛЬНЫЕ ЗАДАЧИ:
--------------------------------------------------------------------------------

При RPC/client-server проблемах не менять сразу:

- UI
- JSON
- server progress
- client manager
- RPC format
- layout

одновременно.

Делать маленькие задачи:

1. Подтвердить request.
2. Подтвердить server data.
3. Подтвердить server send.
4. Подтвердить client receive.
5. Подтвердить ctx.Read.
6. Подтвердить deserialize.
7. Подтвердить ApplySyncedData.
8. Подтвердить UI update.

После каждого шага проверять server/client logs.
