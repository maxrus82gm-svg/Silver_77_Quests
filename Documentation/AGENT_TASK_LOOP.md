# AGENT TASK LOOP

Файл для управления задачами агента.

Главная идея:
- ChatGPT ставит задачу
- пользователь вставляет задачу в этот файл
- агент читает задачу
- агент возвращает отчёт в чат
- пользователь присылает отчёт ChatGPT
- ChatGPT даёт проверку и следующую задачу
- пользователь вручную обновляет этот файл

Этот файл — рабочий журнал взаимодействия:

- пользователь

Главная цель файла:

- хранить текущую задачу
- хранить последний отчёт агента
- хранить последний review ChatGPT
- хранить правила работы
- хранить историю задач
- хранить пользовательские подсказки по UI, смыслу и техническому опыту

--------------------------------------------------------------------------------
ОБЩИЙ ПРОЦЕСС:
--------------------------------------------------------------------------------

1. ChatGPT формирует задачу.
2. Пользователь вставляет задачу в БЛОК 1.
3. Агент читает БЛОК 1.
4. Агент выполняет только текущую задачу.
5. Агент возвращает отчёт в чат.
6. Пользователь отправляет отчёт ChatGPT.
7. ChatGPT проверяет отчёт.
8. ChatGPT даёт:
   - чистый AGENT REPORT для БЛОКА 2
   - REVIEW для БЛОКА 3
   - следующую задачу для БЛОКА 1, если она нужна
9. Пользователь вручную обновляет файл.
10. Git commit / push делает только пользователь.

--------------------------------------------------------------------------------
КТО ЗА ЧТО ОТВЕЧАЕТ:
--------------------------------------------------------------------------------

Пользователь:

- принимает финальные решения
- проверяет результат в игре
- контролирует Git
- делает commit / push
- обновляет этот файл вручную
- даёт визуальные, смысловые и технические подсказки

ChatGPT:

- ставит задачи
- формирует безопасные инструкции
- проверяет отчёты агента
- пишет REVIEW
- следит за архитектурой, рисками и порядком задач
- помогает вести этот файл
- помогает извлекать правила из успешно решённых проблем

Агент / Kiro:

- читает текущую задачу из БЛОКА 1
- выполняет только указанную задачу
- возвращает отчёт в чат
- не пишет отчёт в этот файл
- не делает commit / push
- не принимает архитектурные решения без отдельного указания

# 🟦 БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА ДЛЯ АГЕНТА

БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА

TASK 066 — Исправить DayZ layout viewer: точное позиционирование, z-order и отображение текста

Цель:
Довести DayZ_layout/dayz_layout_viewer.html от rough preview до более точного read-only renderer-а DayZ .layout.

Нужно добиться:
- более точного позиционирования элементов
- корректных размеров
- правильного перекрытия элементов
- отображения настоящего текста из layout
- разделения debug-подписей и игрового текста

Контекст:
Viewer уже умеет:
- читать реальный текстовый формат DayZ .layout
- находить WidgetClass элементы
- читать position / size / color
- строить parent / children
- читать text / font / props
- считать absX / absY
- примерно рисовать UI-блоки

Но текущий визуал НЕ соответствует расположению элементов в игре.

Что сейчас не так:
1. Позиционирование слишком грубое.
   Сейчас используется логика вроде:
   absX = parent.absX + position.x
   absY = parent.absY + position.y

2. Это не соответствует DayZ layout.
   В DayZ на итоговый прямоугольник влияет:
   - parent rect
   - position
   - size
   - halign
   - valign
   - hexactpos
   - vexactpos
   - hexactsize
   - vexactsize

3. Root с:
   size 1 1
   hexactsize 0
   vexactsize 0
   сейчас может восприниматься неправильно.
   Это НЕ 1px x 1px.
   Это 100% родителя / viewport.

4. center_ref сейчас не работает как в игре.
   Например QuestPanel с:
   position 0 0
   size 920 560
   halign center_ref
   valign center_ref
   должен быть по центру viewport, а не в левом верхнем углу.

5. Есть жёсткое умножение координат/размеров на 2.
   Это неправильно.
   Масштаб отображения должен быть отдельной renderScale, а не частью layout math.

6. Перекрытие элементов пока неправильное.
   Parent/панели могут перекрывать children.
   Текст может быть под панелями/кнопками.
   Нужно управлять z-order.

7. Текст отображается недостаточно правильно.
   Нужно показывать настоящий node.text для TextWidgetClass / MultilineTextWidgetClass.
   Debug label с node.name не должен заменять игровой текст.

Где работать:
ТОЛЬКО:
DayZ_layout/dayz_layout_viewer.html

Запрещено менять:
- Documentation/AGENT_TASK_LOOP.md
- Documentation/QUEST_LOGIC_SPEC.md
- Silver_77_Quests_Client/
- Silver_77_Quests_Server/
- любые .layout файлы проекта
- любые .json файлы
- любые файлы вне DayZ_layout/
- Git

Что НЕ делать:
- НЕ переписывать viewer с нуля без необходимости
- НЕ возвращать DOMParser/XML
- НЕ возвращать position[] / size[] / color[]
- НЕ делать Export
- НЕ делать Generate
- НЕ сохранять файлы
- НЕ использовать внешние библиотеки/CDN
- НЕ использовать random color
- НЕ трогать файлы мода

Что сделать:

1. Добавить finalRect каждому node.

Каждый node должен получить:

node.finalRect = {
  x: number,
  y: number,
  w: number,
  h: number
}

renderLayout должен использовать именно finalRect, а не absX/absY напрямую.

2. Добавить viewport/canvas rect.

Например:

const VIEWPORT_WIDTH = 1280;
const VIEWPORT_HEIGHT = 720;

или:

const VIEWPORT_WIDTH = 1920;
const VIEWPORT_HEIGHT = 1080;

Главное:
- root элементы считаются относительно viewport
- root size 1 1 при hexactsize 0/vexactsize 0 = весь viewport
- canvas в браузере может быть масштабирован, но layout math считается в viewport units

3. Добавить функцию computeFinalRects.

Примерная логика:

function computeFinalRects(rootNode, viewportRect) {
    computeNodeRect(rootNode, viewportRect);
}

function computeNodeRect(node, parentRect) {
    // 1. получить local size
    // 2. получить local position
    // 3. применить halign / valign
    // 4. записать node.finalRect
    // 5. рекурсивно обработать children
}

4. Правильно считать размер.

Использовать:
- node.size
- node.props.hexactsize
- node.props.vexactsize
- parentRect

Правило для ширины:
- если hexactsize == "1":
  width = node.size.w
- если hexactsize == "0":
  width = parentRect.w * node.size.w

Правило для высоты:
- если vexactsize == "1":
  height = node.size.h
- если vexactsize == "0":
  height = parentRect.h * node.size.h

Если exact flag отсутствует:
- считать как exact = 1 для обычных элементов
- для root с size 1 1 можно считать как relative 100%

Пример:
FrameWidgetClass QuestMenuRoot {
 size 1 1
 hexactsize 0
 vexactsize 0
}

Если viewport 1280x720:
QuestMenuRoot finalRect.w = 1280
QuestMenuRoot finalRect.h = 720

Пример:
PanelWidgetClass QuestPanel {
 size 920 560
 hexactsize 1
 vexactsize 1
}

QuestPanel finalRect.w = 920
QuestPanel finalRect.h = 560

5. Правильно считать position.

Использовать:
- node.position
- node.props.hexactpos
- node.props.vexactpos
- parentRect

Правило для localX:
- если hexactpos == "1":
  localX = node.position.x
- если hexactpos == "0":
  localX = parentRect.w * node.position.x

Правило для localY:
- если vexactpos == "1":
  localY = node.position.y
- если vexactpos == "0":
  localY = parentRect.h * node.position.y

Если position нет:
localX = 0
localY = 0

6. Правильно учитывать halign.

Свойство:
node.props.halign

Поддержать минимум:

halign left_ref:
x = parentRect.x + localX

halign center_ref:
x = parentRect.x + (parentRect.w - width) / 2 + localX

halign right_ref:
x = parentRect.x + parentRect.w - width - localX

Если halign отсутствует:
считать как left_ref

Почему это важно:
QuestPanel:
position 0 0
size 920 560
halign center_ref
hexactpos 1

Должен быть по центру parent/viewport:
x = parentRect.x + (parentRect.w - 920) / 2

7. Правильно учитывать valign.

Свойство:
node.props.valign

Поддержать минимум:

valign top_ref:
y = parentRect.y + localY

valign center_ref:
y = parentRect.y + (parentRect.h - height) / 2 + localY

valign bottom_ref:
y = parentRect.y + parentRect.h - height - localY

Если valign отсутствует:
считать как top_ref

Почему это важно:
QuestPanel:
position 0 0
size 920 560
valign center_ref

Должен быть по центру parent/viewport:
y = parentRect.y + (parentRect.h - 560) / 2

8. Убрать жёсткое умножение *2 из layout math.

Плохо:
left = node.absX * 2
top = node.absY * 2
width = node.size.w * 2
height = node.size.h * 2

Правильно:
left = node.finalRect.x * renderScale
top = node.finalRect.y * renderScale
width = node.finalRect.w * renderScale
height = node.finalRect.h * renderScale

9. Добавить renderScale.

Минимум:
let renderScale = 0.5;

Лучше:
select с вариантами:
- 50%
- 75%
- 100%

Но если select пока сложно — достаточно константы renderScale = 0.5.

Важно:
renderScale влияет только на отображение в браузере.
renderScale НЕ должен влиять на layout math.

10. Исправить z-order.

Нужно, чтобы:
- parent рисовался ниже child
- children поверх parent
- TextWidgetClass поверх PanelWidgetClass / ButtonWidgetClass
- порядок элементов сохранял порядок layout там, где возможно
- большие панели не скрывали дочерний текст/кнопки

Минимальная логика:
- zIndex = node.id
- плюс depth bonus:
  zIndex = node.id + nodeDepth * 100
- для TextWidgetClass добавить ещё +1000
- для MultilineTextWidgetClass добавить ещё +900

Можно добавить node.depth при парсинге:
node.depth = parent ? parent.depth + 1 : 0

11. Разделить debug label и настоящий игровой текст.

Настоящий текст:
- node.text из TextWidgetClass / MultilineTextWidgetClass

Debug label:
- node.name для понимания, какой это элемент

Правило:
- Для TextWidgetClass и MultilineTextWidgetClass отображать node.text, если он есть.
- Если node.text пустой, можно показывать node.name маленьким debug label.
- Для PanelWidgetClass / ButtonWidgetClass можно показывать маленький debug label node.name, но он не должен мешать игровому тексту.

12. Отображать TextWidgetClass как текст, а не как тяжёлую панель.

Для TextWidgetClass:
- backgroundColor лучше transparent
- border можно сделать очень тонкий dashed только для debug
- textContent = node.text || node.name
- цвет текста можно пока сделать белым или чёрным в зависимости от фона
- pointer/debug tooltip оставить

13. Отображать MultilineTextWidgetClass как текстовый блок.

Для MultilineTextWidgetClass:
- textContent = node.text || node.name
- white-space: pre-wrap
- overflow: hidden
- background transparent или слабая debug-рамка

14. Для ButtonWidgetClass:
- рисовать прямоугольник кнопки
- child TextWidgetClass должен быть поверх кнопки
- если внутри есть текстовый child, он должен быть виден

15. Для PanelWidgetClass:

# 🟫 БЛОК 4.2 — DAYZ CLIENT-SERVER RPC И СИНХРОНИЗАЦИЯ
================================================================================

Этот блок обязателен для задач, связанных с:

- DayZ RPC
- client/server sync
- PlayerBase.OnRPC
- ParamsReadContext
- RPCSingleParam
- Param1 / Param2 / Param3 / Param4
- JSON payload
- config sync
- player data sync
- quest progress sync
- UI, который зависит от server data

--------------------------------------------------------------------------------
ГЛАВНОЕ ПРАВИЛО:
--------------------------------------------------------------------------------

Не отправлять JSON, progress, config, dialog data или другой длинный string payload одной строкой через RPC.

Для DayZ/Enforce это ненадёжно.

Возможная ошибка клиента:

Reason: !!! String CORRUPTED - FIX OnStoreLoad() !!!

Если такая ошибка появилась при ctx.Read string payload — не искать первопричину в UI.
Сначала проверить транспорт RPC и перевести передачу payload на chunked sync.

--------------------------------------------------------------------------------
ПРАВИЛО CHUNKED SYNC:
--------------------------------------------------------------------------------

Любые крупные или потенциально сложные данные передавать чанками.

Рекомендуемый формат:

Param3<int, int, string>

param1 = chunkIndex
param2 = totalChunks
param3 = chunkPayload

Рекомендуемый размер чанка:
- 512 байт
- либо уже существующая константа проекта для chunk sync

--------------------------------------------------------------------------------
ОТДЕЛЬНЫЕ BUFFER ДЛЯ РАЗНЫХ ТИПОВ ДАННЫХ:
--------------------------------------------------------------------------------

Для каждого типа payload должен быть отдельный buffer.

Правильно:
- config chunks отдельно
- player data chunks отдельно
- dialog data chunks отдельно
- future inventory/snapshot chunks отдельно

Неправильно:
- складывать config и player data в один общий map buffer
- переиспользовать один expectedChunkCount для разных RPC payload
- собирать разные payload-типы в одной функции без явного разделения

--------------------------------------------------------------------------------
ПРАВИЛО ParamsReadContext:
--------------------------------------------------------------------------------

ctx.Read выполнять прямо внутри соответствующего case в OnRPC.

Не передавать ParamsReadContext в helper-функции.

Правильно:

case SILVER77_QUEST_RPC_PLAYER_DATA:
{
    Param3<int, int, string> data = new Param3<int, int, string>(0, 0, "");
    if (!ctx.Read(data))
    {
        Print("[Silver_77_Quests][CLIENT_PROGRESS_DEBUG] ERROR: ctx.Read failed");
        return;
    }

    string payload = Silver77_StorePlayerDataSyncChunk(data.param1, data.param2, data.param3);
    if (payload == "")
        return;

    Silver77_HandleQuestPlayerDataPayload(payload);
    return;
}

Неправильно:

case SILVER77_QUEST_RPC_PLAYER_DATA:
    Silver77_HandleQuestPlayerData(ctx);
    return;

private void Silver77_HandleQuestPlayerData(ParamsReadContext ctx)
{
    ctx.Read(...);
}

Helper-функции должны получать обычные значения:
- string payload
- int chunkIndex
- int totalChunks
- PlayerQuestData
- Silver77_QuestConfig

--------------------------------------------------------------------------------
ДИАГНОСТИКА RPC ПО ЦЕПОЧКЕ:
--------------------------------------------------------------------------------

При проблемах client-server sync проверять строго по этапам.

1. Клиент отправил request?
Искать client log:
- Sending ... request RPC

2. Сервер получил request?
Искать server RPT:
- Received ... request RPC

3. Сервер загрузил реальные данные?
Искать server RPT:
- LoadPlayerData
- FileExist=true
- progressCount
- questId/status

4. Сервер подготовил payload?
Искать:
- payloadLength
- Serialize...

5. Сервер отправил response?
Искать:
- Sent ... to client
- Sent ... in X chunks

6. Клиент получил chunks?
Искать client RPT:
- Received ... chunk 1/X
- Received ... chunk X/X

7. Клиент собрал payload?
Искать:
- Reassembled ... payload
- SUCCESS: Reassembled ...

8. Клиент десериализовал payload?
Искать:
- JsonSerializer.ReadFromString succeeded
- PlayerQuestData deserialized successfully

9. Клиент применил данные?
Искать:
- ApplySyncedPlayerData
- ApplySyncedPlayerData completed

10. UI обновился после apply?
Искать:
- реальные status active/completed
- кнопки “УЖЕ АКТИВЕН”, “СДАТЬ КВЕСТ”, “НАГРАДА”
- отсутствие ложного available

--------------------------------------------------------------------------------
ЕСЛИ КЛИЕНТ ПАДАЕТ В ctx.Read:
--------------------------------------------------------------------------------

Сначала проверить:

1. Совпадает ли RPC ID на сервере и клиенте.
2. Совпадает ли Param-тип на сервере и клиенте.
3. Не читает ли super.OnRPC или другой обработчик ctx раньше нашего case.
4. Не передаётся ли ParamsReadContext в helper.
5. Не отправляется ли длинная string одной строкой.
6. Нет ли в логе:
   Reason: !!! String CORRUPTED - FIX OnStoreLoad() !!!

Если есть String CORRUPTED:
- не начинать с UI
- не начинать с JSON-логики квестов
- не начинать с HasSyncedPlayerData
- не начинать с кнопок
- сначала перевести payload на chunked sync

--------------------------------------------------------------------------------
SERVER IS SOURCE OF TRUTH:
--------------------------------------------------------------------------------

Сервер является источником правды.

Сервер:
- хранит progress
- загружает progress из profile JSON
- меняет quest status
- выдаёт rewards
- сохраняет player data
- отправляет sync клиенту

Клиент:
- запрашивает config/player data
- получает sync
- отображает UI
- не должен считать default available реальным progress
- не должен решать server-side outcome самостоятельно

--------------------------------------------------------------------------------
UI НЕ ДОЛЖЕН МАСКИРОВАТЬ ПРОБЛЕМЫ SYNC:
--------------------------------------------------------------------------------

Если HasSyncedPlayerData == false:
- UI может показывать loading
- UI не должен отображать окончательные статусы
- UI не должен активировать кнопки на основе default available
- UI не должен создавать впечатление, что квест реально available, если server sync ещё не получен

Функции типа EnsurePlayerProgress/GetQuestStatus не должны подменять отсутствие server sync настоящим progress.

Default available допустим только как временная заглушка, но не как источник истины.

--------------------------------------------------------------------------------
МИНИМАЛЬНЫЕ ЗАДАЧИ:
--------------------------------------------------------------------------------

При RPC/client-server проблемах не менять сразу:

- UI
- JSON
- server progress
- client manager
- RPC format
- layout

одновременно.

Делать маленькие задачи:

1. Подтвердить request.
2. Подтвердить server data.
3. Подтвердить server send.
4. Подтвердить client receive.
5. Подтвердить ctx.Read.
6. Подтвердить deserialize.
7. Подтвердить ApplySyncedData.
8. Подтвердить UI update.

После каждого шага проверять server/client logs.

ОПЫТ ПО DayZ .layout VIEWER:
--------------------------------------------------------------------------------

- DayZ .layout в проекте НЕ XML.
- Нельзя использовать DOMParser.
- Нельзя использовать формат position[] = {x,y}, size[] = {w,h}, color[] = {r,g,b,a}.
- Реальный формат проекта:
  position 30 82
  size 330 250
  color 0.0824 0.0824 0.0824 0.96

- Начало виджета:
  <WidgetClassType> <ElementName> {

  Примеры:
  FrameWidgetClass QuestMenuRoot {
  PanelWidgetClass QuestPanel {
  TextListboxWidgetClass QuestListbox {
  ButtonWidgetClass AcceptButton {
  TextWidgetClass AcceptButtonText {

- Отдельная строка "{" не создаёт node.
  Это только начало блока children.

- Строка "}" закрывает текущий node.

- Для парсинга нужен stack nodes:
  новый WidgetClass → создать node, связать с parent, nodes.push, stack.push
  строка } → stack.pop
  свойства → писать в stack[stack.length - 1]

- Нельзя использовать один currentElement для вложенного layout.
  Он ломает parent/children, потому что каждый новый вложенный виджет перезаписывает текущий элемент.

- Для визуального отображения нужны absX / absY:
  child.absX = parent.absX + child.position.x
  child.absY = parent.absY + child.position.y

- Если у node нет position, это не ошибка:
  local position считать как 0,0
  children всё равно нужно обрабатывать.

- Если у node нет color:
  использовать transparent background + видимую рамку.
  Не использовать random color, потому что визуал должен быть стабильным между обновлениями.

- DayZ layout viewer должен быть read-only:
  ничего не сохранять
  ничего не генерировать
  не изменять .layout
  не форматировать .layout
