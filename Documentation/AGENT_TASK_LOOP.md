TASK 105 — Analysis / Design: спроектировать безопасную систему выдачи наград с attemptId, pendingRewards и deliveredRewards для повторяемых квестов

Статус:
Аналитико-проектная задача. Код, JSON, layout, документацию и server profile не менять.

--------------------------------------------------------------------------------
КОНТЕКСТ
--------------------------------------------------------------------------------

По результату TASK 104 выяснено:

1. Предметы NPC при выдаче обычно сначала пытаются попасть в инвентарь.
2. Если инвентарь полный, есть fallback на землю.
3. Но успешность финального создания предмета не проверяется надёжно.
4. Квест / Completion / Reward может засчитаться, даже если предмет фактически не был выдан.
5. Нет отдельного учёта того, какие предметы награды уже выданы, какие остались к выдаче.
6. Нет защиты от сложных случаев:
   - частичная выдача награды;
   - повторное нажатие игроком;
   - рестарт сервера;
   - повторяемые квесты;
   - старые delivered-награды не должны засчитываться для нового повтора квеста.

Нужно спроектировать безопасную систему учёта выдачи предметов по квестам.

Главная идея:

- questId — тип квеста;
- attemptId / runId / cycleId — конкретное прохождение повторяемого квеста;
- rewardId — конкретная выдача внутри этой попытки;
- pendingRewards — награды, которые ещё надо довыдать;
- deliveredRewards — награды, которые уже успешно выданы для конкретной попытки.

Важно:

Если квест повторяемый, старая успешная выдача награды не должна блокировать новую выдачу в новой попытке.

Нельзя проверять только:

questId + reward

Нужно проверять минимум:

questId + attemptId + stage + triggerId/actionId

МОЁ МНЕНИЕ / ПРЕДПОЧТИТЕЛЬНОЕ РЕШЕНИЕ
--------------------------------------------------------------------------------

Моё мнение:

Нужно делать не глобальный список "этот квест уже выдал награду", а историю выдач по конкретным попыткам.

Правильная модель:

questId = тип квеста
attemptId = конкретное прохождение / повтор квеста
rewardId = конкретная выдача внутри этой попытки

Пример rewardId:

quest_05:attempt_2:reward:hunter_trigger
quest_05:attempt_2:completion:rasputin_trigger
quest_05:attempt_2:offer:hunter_trigger

Старые delivered-награды можно хранить как историю, но они не должны работать как подтверждение выдачи для нового attemptId.

Новый повтор квеста должен работать так:

1. Предыдущая попытка полностью финализирована.
2. Нет pendingRewards по предыдущему attemptId.
3. Все обязательные награды delivered.
4. Стартует cooldown.
5. Cooldown завершился.
6. Создаётся новый attemptId.
7. Только после этого квест снова доступен.

Если награда не выдалась полностью:

- квест не считается полностью финализированным;
- pendingRewards остаются;
- cooldown не стартует;
- новый attemptId не создаётся;
- игрок может довыдать остаток позже.

Главное правило:

Нет полной финализации текущего attemptId — нет нового повтора квеста.
