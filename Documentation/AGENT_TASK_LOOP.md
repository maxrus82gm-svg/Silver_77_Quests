# AGENT TASK LOOP

Файл для управления задачами агента.

Главная идея:
- ChatGPT ставит задачу
- пользователь вставляет задачу в этот файл
- агент читает задачу
- агент возвращает отчёт в чат
- пользователь присылает отчёт ChatGPT
- ChatGPT даёт проверку и следующую задачу
- пользователь вручную обновляет этот файл

ОБЩИЙ ПРОЦЕСС:
--------------------------------------------------------------------------------

1. ChatGPT формирует задачу.
2. Пользователь вставляет задачу в БЛОК 1.
3. Агент читает БЛОК 1.
4. Агент выполняет только текущую задачу.
5. Агент возвращает отчёт в чат.
6. Пользователь отправляет отчёт ChatGPT.
7. ChatGPT проверяет отчёт.
8. ChatGPT даёт:
   - чистый AGENT REPORT для БЛОКА 2
   - REVIEW для БЛОКА 3
   - следующую задачу для БЛОКА 1, если она нужна
9. Пользователь вручную обновляет файл.
10. Git commit / push делает только пользователь.

БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА

TASK 077 — Привести UI и редактор к реальному JSON-контракту мода: objectives вместо requiredItems, dialogText вместо dialogue, правильное разделение DescriptionPanel и DialogPanel

Цель:
Исправить расхождение в терминах и отображении данных между Quest JSON Editor, JSON-контрактом и UI мода.

Контекст:
TASK 076 показал, что критического schema mismatch между editor и mod нет, но есть важные нюансы:

1. requiredItems как отдельного поля в JSON нет.
   Его роль выполняет:
   quests[].objectives[]

2. dialogue как отдельного поля в JSON нет.
   Реальный контракт диалога:
   triggerActions[].dialogText

3. Offer / Completion / Reward реализованы через:
   offerTriggerIds[]
   completionTriggerIds[]
   rewardTriggerIds[]

   и через:
   triggerActions[] с actionType = offer / completion / reward

Пользователь хочет привести редактор и UI к этой реальной модели, чтобы не было ложных ожиданий.

Главная видимая проблема:
В игре текст диалога NPC сейчас отображается в верхнем DescriptionPanel, а также повторяется в нижнем диалоговом журнале.

Ожидаемое поведение:
- Верхний DescriptionPanel должен показывать описание квеста и техническую/игровую информацию:
  - описание квеста
  - цели
  - что нужно принести
  - прогресс
  - что дадут
  - требования
  - статус

- Нижний DialogPanel должен показывать именно диалог NPC:
  - triggerActions[].dialogText
  - текст текущего NPC-блока Offer / Completion / Reward
  - диалоговый журнал, если он нужен

То есть:
DescriptionPanel = “что за квест и что делать”
DialogPanel = “что сказал NPC”

--------------------------------------------------------------------------------
ГЛАВНОЕ ПРАВИЛО:
--------------------------------------------------------------------------------

Не отправлять JSON, progress, config, dialog data или другой длинный string payload одной строкой через RPC.

Для DayZ/Enforce это ненадёжно.

Возможная ошибка клиента:

Reason: !!! String CORRUPTED - FIX OnStoreLoad() !!!

Если такая ошибка появилась при ctx.Read string payload — не искать первопричину в UI.
Сначала проверить транспорт RPC и перевести передачу payload на chunked sync.

--------------------------------------------------------------------------------
ПРАВИЛО CHUNKED SYNC:
--------------------------------------------------------------------------------

Любые крупные или потенциально сложные данные передавать чанками.

Рекомендуемый формат:

Param3<int, int, string>

param1 = chunkIndex
param2 = totalChunks
param3 = chunkPayload

Рекомендуемый размер чанка:
- 512 байт
- либо уже существующая константа проекта для chunk sync

--------------------------------------------------------------------------------
ОТДЕЛЬНЫЕ BUFFER ДЛЯ РАЗНЫХ ТИПОВ ДАННЫХ:
--------------------------------------------------------------------------------

Для каждого типа payload должен быть отдельный buffer.

Правильно:
- config chunks отдельно
- player data chunks отдельно
- dialog data chunks отдельно
- future inventory/snapshot chunks отдельно

Неправильно:
- складывать config и player data в один общий map buffer
- переиспользовать один expectedChunkCount для разных RPC payload
- собирать разные payload-типы в одной функции без явного разделения

--------------------------------------------------------------------------------
ПРАВИЛО ParamsReadContext:
--------------------------------------------------------------------------------

ctx.Read выполнять прямо внутри соответствующего case в OnRPC.

Не передавать ParamsReadContext в helper-функции.

Правильно:

case SILVER77_QUEST_RPC_PLAYER_DATA:
{
    Param3<int, int, string> data = new Param3<int, int, string>(0, 0, "");
    if (!ctx.Read(data))
    {
        Print("[Silver_77_Quests][CLIENT_PROGRESS_DEBUG] ERROR: ctx.Read failed");
        return;
    }

    string payload = Silver77_StorePlayerDataSyncChunk(data.param1, data.param2, data.param3);
    if (payload == "")
        return;

    Silver77_HandleQuestPlayerDataPayload(payload);
    return;
}

Неправильно:

case SILVER77_QUEST_RPC_PLAYER_DATA:
    Silver77_HandleQuestPlayerData(ctx);
    return;

private void Silver77_HandleQuestPlayerData(ParamsReadContext ctx)
{
    ctx.Read(...);
}

Helper-функции должны получать обычные значения:
- string payload
- int chunkIndex
- int totalChunks
- PlayerQuestData
- Silver77_QuestConfig

--------------------------------------------------------------------------------
ДИАГНОСТИКА RPC ПО ЦЕПОЧКЕ:
--------------------------------------------------------------------------------

При проблемах client-server sync проверять строго по этапам.

1. Клиент отправил request?
Искать client log:
- Sending ... request RPC

2. Сервер получил request?
Искать server RPT:
- Received ... request RPC

3. Сервер загрузил реальные данные?
Искать server RPT:
- LoadPlayerData
- FileExist=true
- progressCount
- questId/status

4. Сервер подготовил payload?
Искать:
- payloadLength
- Serialize...

5. Сервер отправил response?
Искать:
- Sent ... to client
- Sent ... in X chunks

6. Клиент получил chunks?
Искать client RPT:
- Received ... chunk 1/X
- Received ... chunk X/X

7. Клиент собрал payload?
Искать:
- Reassembled ... payload
- SUCCESS: Reassembled ...

8. Клиент десериализовал payload?
Искать:
- JsonSerializer.ReadFromString succeeded
- PlayerQuestData deserialized successfully

9. Клиент применил данные?
Искать:
- ApplySyncedPlayerData
- ApplySyncedPlayerData completed

10. UI обновился после apply?
Искать:
- реальные status active/completed
- кнопки “УЖЕ АКТИВЕН”, “СДАТЬ КВЕСТ”, “НАГРАДА”
- отсутствие ложного available

--------------------------------------------------------------------------------
ЕСЛИ КЛИЕНТ ПАДАЕТ В ctx.Read:
--------------------------------------------------------------------------------

Сначала проверить:

1. Совпадает ли RPC ID на сервере и клиенте.
2. Совпадает ли Param-тип на сервере и клиенте.
3. Не читает ли super.OnRPC или другой обработчик ctx раньше нашего case.
4. Не передаётся ли ParamsReadContext в helper.
5. Не отправляется ли длинная string одной строкой.
6. Нет ли в логе:
   Reason: !!! String CORRUPTED - FIX OnStoreLoad() !!!

Если есть String CORRUPTED:
- не начинать с UI
- не начинать с JSON-логики квестов
- не начинать с HasSyncedPlayerData
- не начинать с кнопок
- сначала перевести payload на chunked sync

--------------------------------------------------------------------------------
SERVER IS SOURCE OF TRUTH:
--------------------------------------------------------------------------------

Сервер является источником правды.

Сервер:
- хранит progress
- загружает progress из profile JSON
- меняет quest status
- выдаёт rewards
- сохраняет player data
- отправляет sync клиенту

Клиент:
- запрашивает config/player data
- получает sync
- отображает UI
- не должен считать default available реальным progress
- не должен решать server-side outcome самостоятельно

--------------------------------------------------------------------------------
UI НЕ ДОЛЖЕН МАСКИРОВАТЬ ПРОБЛЕМЫ SYNC:
--------------------------------------------------------------------------------

Если HasSyncedPlayerData == false:
- UI может показывать loading
- UI не должен отображать окончательные статусы
- UI не должен активировать кнопки на основе default available
- UI не должен создавать впечатление, что квест реально available, если server sync ещё не получен

Функции типа EnsurePlayerProgress/GetQuestStatus не должны подменять отсутствие server sync настоящим progress.

Default available допустим только как временная заглушка, но не как источник истины.

ОПЫТ ПО DayZ .layout VIEWER
--------------------------------------------------------------------------------

- DayZ .layout в проекте НЕ XML.
- Нельзя использовать DOMParser.
- Нельзя использовать формат:
  position[] = {x, y}
  size[] = {w, h}
  color[] = {r, g, b, a}

- Реальный формат DayZ .layout в проекте такой:

  FrameWidgetClass QuestMenuRoot {
   ignorepointer 0
   color 0.1765 0.1765 0.1765 0.9
   position 0 0
   size 1 1
   halign center_ref
   valign center_ref
   hexactpos 1
   vexactpos 1
   hexactsize 0
   vexactsize 0
   {
    PanelWidgetClass QuestPanel {
     position 0 0
     size 920 560
     halign center_ref
     valign center_ref
     hexactpos 1
     vexactpos 1
     hexactsize 1
     vexactsize 1
    }
   }
  }

- Начало виджета выглядит так:

  <WidgetClassType> <ElementName> {

- Примеры:

  FrameWidgetClass QuestMenuRoot {
  PanelWidgetClass QuestPanel {
  TextListboxWidgetClass QuestListbox {
  ButtonWidgetClass AcceptButton {
  TextWidgetClass AcceptButtonText {
  MultilineTextWidgetClass DescriptionText {

- Свойства идут отдельными строками:

  position 30 82
  size 330 250
  color 0.0824 0.0824 0.0824 0.96
  text "ВЗЯТЬ КВЕСТ"
  font "gui/fonts/metron22"
  ignorepointer 0
  halign left_ref
  valign top_ref
  hexactpos 1
  vexactpos 1
  hexactsize 1
  vexactsize 1
  "text halign" center
  "text valign" center

- Отдельная строка "{" НЕ создаёт node.
  Это только начало блока children.

- Отдельная строка "}" закрывает текущий блок.

- Для корректного парсинга нужен blockStack, а не простой nodeStack.

- Причина:
  В реальных .layout есть отдельные child-блоки:

  PanelWidgetClass QuestPanel {
   position 0 0
   size 920 560
   {
    TextWidgetClass TitleText {
     ...
    }
   }
  }

  Если делать nodeStack.pop() на каждую "}", можно закрыть не тот node.
  Поэтому stack должен различать:
  - node block
  - group block

- Правильная идея:

  blockStack.push({ kind: "node", node })
  blockStack.push({ kind: "group" })

  При поиске текущего parent нужно брать последний blockStack item с kind === "node".

--------------------------------------------------------------------------------
ОПЫТ ПО DayZ .layout: PIXELS / PERCENT / FINAL RECT
--------------------------------------------------------------------------------

- DayZ layout нельзя считать только как:
  absX = parent.absX + position.x
  absY = parent.absY + position.y

- Правильная модель:

  parentRect + local position + local size + align + exact flags = finalRect

- parseLayout() должен только читать .layout и строить дерево nodes.
- computeFinalRects() должен считать итоговые прямоугольники.
- renderLayout() должен только рисовать готовые finalRect.

- renderLayout НЕ должен сам придумывать координаты.
- renderLayout НЕ должен менять смысл position/size.
- renderLayout НЕ должен содержать layout math.
- renderLayout должен рисовать:

  node.finalRect.x * renderScale
  node.finalRect.y * renderScale
  node.finalRect.w * renderScale
  node.finalRect.h * renderScale

- В проекте принято правило:

  exact = 1 → значение в пикселях
  exact = 0 → значение как доля parentRect / проценты

- То есть:

  hexactpos 1 = position.x в пикселях
  vexactpos 1 = position.y в пикселях
  hexactsize 1 = size.w в пикселях
  vexactsize 1 = size.h в пикселях

  hexactpos 0 = position.x как доля ширины parentRect
  vexactpos 0 = position.y как доля высоты parentRect
  hexactsize 0 = size.w как доля ширины parentRect
  vexactsize 0 = size.h как доля высоты parentRect

- Пример пиксельного элемента:

  TextListboxWidgetClass QuestListbox {
   position 30 82
   size 330 250
   hexactpos 1
   vexactpos 1
   hexactsize 1
   vexactsize 1
  }

  Значит:
  localX = 30 px
  localY = 82 px
  width = 330 px
  height = 250 px

- Пример относительного root:

  FrameWidgetClass QuestMenuRoot {
   position 0 0
   size 1 1
   hexactpos 0
   vexactpos 0
   hexactsize 0
   vexactsize 0
  }

  Это НЕ 1px x 1px.
  Это 100% parent / viewport.

  Если viewport = 1280x720:
  finalRect.w = 1280
  finalRect.h = 720

- Для size:

  if hexactsize == 1:
      width = node.size.w
  else:
      width = parentRect.w * node.size.w

  if vexactsize == 1:
      height = node.size.h
  else:
      height = parentRect.h * node.size.h

- Для position:

  if hexactpos == 1:
      localX = node.position.x
  else:
      localX = parentRect.w * node.position.x

  if vexactpos == 1:
      localY = node.position.y
  else:
      localY = parentRect.h * node.position.y

- Для halign:

  left_ref:
      x = parentRect.x + localX

  center_ref:
      x = parentRect.x + (parentRect.w - width) / 2 + localX

  right_ref:
      x = parentRect.x + parentRect.w - width - localX

- Для valign:

  top_ref:
      y = parentRect.y + localY

  center_ref:
      y = parentRect.y + (parentRect.h - height) / 2 + localY

  bottom_ref:
      y = parentRect.y + parentRect.h - height - localY

- Нельзя принудительно clamp/обрезать child внутри parentRect на этапе layout math.

- Причина:
  Элемент может выходить за пределы parent.
  Обрезка/clip — это отдельное поведение контейнера.
  Если насильно менять x/y/w/h, finalRect перестаёт соответствовать layout.

редактор должен формировать JSON строго под то, что реально читает мод.

--------------------------------------------------------------------------------
ПРАВИЛЬНАЯ МОДЕЛЬ РОЛЕЙ
--------------------------------------------------------------------------------

Текущая концепция NPC Flow считается правильной:

1. Offer
- место / NPC, где игрок берёт квест
- стартовый диалог
- условия доступности
- может выдавать стартовые предметы через giveItems
- не должен быть финальным закрытием квеста

2. Completion
- промежуточный этап / сдача части задачи
- может быть 0, 1 или несколько
- может быть на другом NPC / trigger
- может иметь свой triggerActions[].dialogText
- может принимать objectives
- может выдавать промежуточную награду через triggerActions[].rewards

3. Reward
- финальное закрытие квеста
- обычно исходный NPC, но может быть другой trigger
- выдаёт финальную награду
- закрывает квест

Текущая runtime-модель мода:
- Offer и Reward фактически single-trigger роли
- Completion может быть несколько
- это совпадает с желаемой логикой:
  один Offer → несколько Completion → один Reward

--------------------------------------------------------------------------------
РЕАЛЬНЫЙ JSON-КОНТРАКТ
--------------------------------------------------------------------------------

Не вводить ложные поля.

В контракте нет отдельного поля:

requiredItems

Его роль выполняет:

quests[].objectives[]

Особенно:
objectives[] с type == "item"

Правильная терминология:
- Objectives
- Цели
- Цели: предметы
- Что нужно принести / сдать

Неправильная терминология, если она подразумевает отдельное JSON-поле:
- requiredItems[]
- отдельный блок requiredItems в JSON

--------------------------------------------------------------------------------

В контракте нет отдельного поля:

dialogue

Реальный текст NPC хранится здесь:

triggerActions[].dialogText

Правильная терминология:
- Dialog Text
- Текст диалога NPC
- triggerActions[].dialogText

Неправильная терминология, если она подразумевает отдельное JSON-поле:
- dialogue
- dialogueText как отдельная сущность вне triggerActions

--------------------------------------------------------------------------------
РАЗДЕЛЕНИЕ DESCRIPTION И DIALOG
--------------------------------------------------------------------------------

В UI мода и редакторе нужно строго разделять смысл:

Description / DescriptionPanel:
- описание квеста
- смысл задачи
- цели
- прогресс
- что нужно принести
- что уже сдано
- награды
- требования
- статус квеста

Dialog / DialogPanel:
- что говорит NPC
- текст текущего action-блока
- triggerActions[].dialogText
- контекст разговора Offer / Completion / Reward

Правильный маппинг:

quest.description / objectives / rewards / progress / status
→ DescriptionPanel / DescriptionText

triggerActions[].dialogText
→ DialogPanel / DialogText

Нельзя использовать triggerActions[].dialogText как основное описание квеста в DescriptionPanel.

Если нужен диалоговый журнал, он может быть отдельной частью DialogPanel, но не должен подменять DescriptionPanel.

--------------------------------------------------------------------------------
СПРАВОЧНИК СТЕКОВ
--------------------------------------------------------------------------------

Справочник стеков item-stack-rules.json является важной частью редактора.

Он нужен, чтобы редактор мог правильно считать количество предметов с учётом стеков.

Это особенно важно для серверов с модами, где размер стака может отличаться от vanilla DayZ.

Примеры:
- патроны
- деньги
- дрова
- палки
- вода
- топливо
- любые модовые предметы с изменённым размером стака

Правило:
не удалять и не упрощать справочник стеков.
не заменять его жёстко прописанными vanilla-значениями.
не считать, что quantity всегда означает количество отдельных физических предметов.

Для item-objectives учитывать:
- quantity
- useItemQuantity
- allowPartialTurnIn
- removeOnComplete
- item-stack-rules.json

Смысл:
редактор должен помогать пользователю правильно рассчитать требования к предметам до запуска игры.

--------------------------------------------------------------------------------
ЧТО НЕ ЛОМАТЬ
--------------------------------------------------------------------------------

Не переделывать визуальную концепцию редактора с нуля без отдельной задачи.

Считать правильными направлениями:
- NPC Flow
- Offer / Completion / Reward
- Objectives вместо requiredItems
- triggerActions[].dialogText вместо dialogue
- Rewards как отдельный блок наград
- Stack Rules / справочник стеков
- визуальное разделение блоков по ролям

Не добавлять новые JSON-поля без отдельного решения:
- requiredItems[]
- dialogue
- dialogueText вне triggerActions[]
- rewardBlock
- completionBlock
- offerBlock

Если нужно расширять функционал, сначала проверить:
1. поддерживает ли это мод;
2. где это читается в client/server коде;
3. как это должно выглядеть в JSON;
4. только потом добавлять UI в редактор.
