# PROJECT CONTEXT

## Что это за проект

Это локальный редактор JSON для квестов и триггеров, ориентированный на пользователей, которые не являются программистами.

Основная задача редактора:

- загружать JSON с квестами и trigger/NPC
- редактировать его по человеческим блокам, а не вручную в сыром JSON
- валидировать структуру
- сохранять итоговый JSON обратно в рабочий файл
- создавать резервную копию
- сохранять черновик работы, чтобы изменения не терялись между запусками

Базовый ориентир структуры:

- `Silver_77_Quests.json`

## Главные продуктовые решения

### 1. Интерфейс сделан двуязычным

Поля показываются в формате:

- `English (русское пояснение)`

Примеры:

- `Class Name (код предмета)`
- `Use Item Quantity (считать внутреннее количество)`
- `Remove On Complete (забирать после сдачи)`
- `Hint Text (подсказка для игрока)`

Это сделано для двух целей:

- не терять связь с оригинальными JSON-полями
- сделать интерфейс понятным русскоязычным пользователям

### 2. Квест теперь обязательно привязан к trigger / NPC

Это важное архитектурное решение.

Пользователь больше не должен думать в терминах:

- `я вручную правлю trigger.questIds`

Теперь логика такая:

- у квеста есть обязательное поле выбора `Trigger ID (кому принадлежит квест)`
- редактор сам добавляет `quest.id` в `trigger.questIds`
- при смене trigger связь автоматически переносится
- при смене `quest.id` ссылки также обновляются

Это было сделано, потому что для обычного пользователя логика "какой NPC выдает квест" намного понятнее, чем ручная работа с массивом `questIds`.

### 3. Экспорт теперь рассчитан на рабочий файл по пути

Редактор больше не только скачивает JSON через браузер.

Если редактор запущен через локальный сервер и запускатель:

- он читает путь сохранения из локального конфига
- и сохраняет итоговый JSON прямо поверх рабочего файла

### 4. Добавлен backup

При запуске через `start-editor.cmd` выполняется резервное копирование:

- исходный рабочий файл копируется в backup-файл

Пути для рабочего файла и backup настраиваются отдельно.

### 5. Добавлен файловый черновик

Чтобы изменения не терялись при перезапуске браузера или смене режима запуска, добавлен отдельный файловый черновик:

- `editor-draft.json`

Теперь черновик живет не только в `localStorage`, а еще и рядом с проектом.

## Как сейчас работает запуск

Рекомендуемый способ запуска:

- запускать через `start-editor.cmd`

Что происходит при запуске:

1. Читается `editor-config.json`
2. Берется `savePath`
3. Если рабочий файл найден, он копируется в `backupPath`
4. Поднимается локальный сервер
5. Открывается редактор в браузере
6. Если есть `editor-draft.json`, редактор восстанавливает его
7. Если черновика нет, редактор открывает JSON по `savePath`

## Как сейчас работает сохранение

### Если запуск через `start-editor.cmd`

Кнопка `Экспорт JSON`:

- проверяет валидацию
- если есть критичные ошибки, экспорт блокируется
- если все в порядке, JSON сохраняется прямо в файл по `savePath`
- после успешного сохранения файловый черновик очищается

### Если редактор открыт не через сервер

Тогда полноценное прямое сохранение в файл недоступно, и редактор использует браузерную выгрузку файла.

## Что важно знать про черновик

Раньше состояние могло жить только внутри браузера.
Из-за этого можно было потерять изменения, если:

- открыть редактор другим способом
- сменить origin
- закрыть вкладку
- перейти с прямого `index.html` на локальный сервер

Теперь добавлен файловый черновик:

- `editor-draft.json`

Он нужен именно для того, чтобы изменения между запусками не терялись.

Текущая логика:

- во время редактирования черновик автосохраняется
- при следующем запуске черновик поднимается первым
- после успешного прямого сохранения черновик очищается

## Что остается потенциально опасным или неидеальным

### 1. Блок `Quest IDs` у trigger пока еще редактируем вручную

Хотя основная логика теперь должна идти через квест и его поле выбора trigger, ручное редактирование `trigger.questIds` все еще возможно.

Это значит:

- опытный пользователь может этим пользоваться
- неопытный пользователь все еще теоретически может сломать связь вручную

Рекомендуемое следующее улучшение:

- сделать `Quest IDs` у trigger только для чтения
- или перенести его в режим "информация", а не "ручное редактирование"

### 2. Черновик пока без явных управляющих кнопок

Сейчас черновик работает автоматически, но в интерфейсе пока нет отдельных кнопок:

- `Сохранить черновик сейчас`
- `Очистить черновик`
- `Восстановить черновик`

Это можно добавить следующим шагом.

### 3. Нет отдельного режима сравнения

Пока есть только:

- форма
- preview JSON

Но нет режима:

- сравнить исходный JSON и текущий
- подсветить конкретные изменения

Это тоже хороший следующий шаг.

### 4. Возможные проблемы совместимости с Windows PowerShell

Во время разработки уже встретилась реальная ошибка:

- в интерфейсе появлялось сообщение `Не удалось сохранить пути на локальном компьютере.`

При этом проблема была не в выборе trigger у квеста.
Trigger мог быть выбран правильно, но ошибка относилась именно к сохранению локальных путей:

- `savePath`
- `backupPath`

Причина:

- в PowerShell-скриптах использовался разбор JSON через `ConvertFrom-Json -AsHashtable`
- на части Windows-сред, особенно в Windows PowerShell 5.1, это может работать не так, как ожидается, или ломать совместимость

Что было сделано:

- логика разбора JSON была переписана без зависимости от `-AsHashtable`
- исправлены:
  - `server.ps1`
  - `start-editor.ps1`

Что важно помнить дальше:

- при добавлении новых PowerShell-скриптов лучше избегать решений, завязанных на более новые возможности PowerShell, если проект должен работать в обычной Windows-среде без отдельной установки PowerShell 7
- если в UI снова появится ошибка локального сохранения, сначала нужно проверять не логику редактора квестов, а локальные server/launcher-скрипты

### 5. Возможная проблема со "старым" локальным сервером

Во время разработки выявился еще один важный сценарий:

- скрытый локальный сервер мог продолжать работать в фоне
- после изменений в `server.ps1` или `app.js` редактор мог открываться поверх старого серверного процесса
- из-за этого пользователь видел поведение от старой версии кода

Что было сделано:

- добавлен механизм остановки фонового сервера через `/api/shutdown`
- `start-editor.ps1` теперь старается перезапускать сервер при новом запуске редактора

Что важно помнить дальше:

- если после правок в серверной логике пользователь сообщает, что "ошибка осталась", это может означать не то, что фикс не сработал, а то, что редактор все еще работает через старый серверный процесс
- при изменениях серверной части нужно отдельно помнить про жизненный цикл фонового процесса

## Дополнительная заметка по запускателю

Во время отладки сохранения путей выяснился еще один важный нюанс Windows:

- локальный сервер на `HttpListener` может показываться на порту `4173` как процесс `System`
- из-за этого попытка искать и останавливать старый сервер только через `Get-NetTCPConnection` и `OwningProcess` может не сработать
- при этом статические файлы (`index.html`, `app.js`) уже могут отдаваться в новой версии, а серверные маршруты (`POST /api/config`) оставаться от старого процесса

Что было изменено:

- `start-editor.ps1` теперь сначала пытается мягко остановить сервер через `/api/shutdown`
- если процесс все еще жив, запускатель ищет именно `powershell.exe` с `server.ps1` в командной строке и завершает его уже по PID процесса

Почему это важно помнить дальше:

- если после правок в `server.ps1` пользователь пишет, что старая ошибка "осталась", нужно проверять не только код, но и то, какая версия серверного процесса реально запущена

```text
profiles\Silver_77_Quests\Silver_77_Quests.json
```

сервер должен пересоздать уже новый минимальный набор.

Важно:

- для текущей split-схемы менять клиентский мод под это не нужно
- под этот конкретный апдейт пересобирать/обновлять нужно только серверную часть

### Что сделано по редактору сверх старой базы

- дефолтный конфиг редактора переведен в переносимый вид
- локальные пути, draft и backup отделены от исходников
- редактор больше не должен затягивать закоммиченный draft поверх рабочего JSON
- улучшена логика запуска локального сервера редактора
- исправлен сценарий, когда после успешного сохранения черновик мог внезапно воскреснуть из таймера

### Что уже подготовлено под механику стеков

В редакторе добавлена отдельная минималистичная оснастка для ручного справочника стеков:

- новый блок `Стаки` в левой колонке
- отдельный файл `item-stack-rules.json`
- отдельные маршруты локального сервера `/api/stack-rules`
- хранение `className` + `stackSize` вне основного quest JSON

### Что важно не перепутать по стековой логике

На текущем этапе сделана именно основа под справочник.

Пока еще НЕ сделано:

- автоматическое преобразование "3 набора" в итоговое `quantity`
- отдельный режим objective, который будет использовать этот справочник при редактировании

Текущая договоренность с пользователем:

- значения стеков он будет заполнять вручную через web UI
- парсер должен хранить этот справочник отдельно
- позже на этот справочник будет навешена удобная авторская логика для objective
